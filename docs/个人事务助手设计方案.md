## 一、问题定义

### 1.1 用户描述

- 同一个人同时在扮演多个角色（工作、家庭、创作、跑腿等）。
- 各个角色里产生的事务混在一起流进来，没有区分脉络。
- 切换角色时要重新捡上下文，成本高。
- 不同角色里的事务优先级冲突，常常靠直觉/责任感博弈，缺少明确依据。

### 1.2 要解决的具体断点

1. **入口散** — 事务来自不同渠道、不同角色，进来之后混成一团。
2. **形状不清** — 「处理一下」、「看看这个」、「别忘了」，是动作还是提醒，边界模糊。
3. **断点恢复成本高** — 中途被叫走，回来还得从头捡上下文。
4. **角色混导致的决策负担** — 都是「事情」，看不出哪个是哪个角色的，排序难。

### 1.3 V1 覆盖哪些断点

| 断点 | V1 是否覆盖 | 说明 |
|---|---|---|
| 入口散 | **不覆盖** | 多渠道自动采集明确排除在外（见第十四、十五章）。V1 输入全部手工录入。 |
| 形状不清 | 覆盖 | `kind` 字段把事务显式分成动作/等候/提醒三类。 |
| 断点恢复成本高 | 覆盖 | 恢复契约（第八章）给出可验证定义。 |
| 角色混导致决策负担 | 部分覆盖 | 角色视图解决「看不出是哪个角色的」；排序只给透明弱信号，不做取舍（第七章）。 |

V1 不覆盖断点 1 是有意识的取舍，不是遗漏。代价与判定标准见第十四章。

## 二、核心设计原则

### 原则 1：事务按「脉络」分开看，但不强求精确分类

- 一个事务可以带一个或多个角色标签。
- 角色标签不等于永久的分类体系 — 用户可以在任何时候合并、折叠、重新归属。
- 系统可以帮忙推断角色脉络，但用户能纠正。

### 原则 2：视图按「角色」组织，展现按「今天」组织

- 存储层面：事务按角色关联（多对多）。
- 展示层面：给用户看的时候，拼出「今天的视图」：
  - 今天能动的事务
  - 今天到时间的提醒 / 等候件到点了的
  - 角色打标信息仍然保留，但展示时不堆所有角色的大类容器

### 原则 3：每个事务都有可恢复的状态

- 事务不只是标题，它有：
  - 状态（见第四章，三个正交字段）
  - 上次活动的位置（做到了哪一步、存了什么草稿、为什么卡住）
- 你可以从任何事务进入，恢复上下文，而不是从头开始。
- **可验证定义见第八章「恢复契约」。**

### 原则 4：不同脉络里的事，可以有不同的完成标准

- 专业交付脉络中的事务，可能需要更成熟的草稿、多步执行。
- 家庭/朋友脉络中的事务，可能只需要轻量的结果。
- 用户能对角色或单个事务说明「这个脉络里先给我能用的就行」，系统按那个标准处理。

> **落地约定（V1.1 补齐）**：完成标准是一等字段，不再停留在原则层面。
> - 事务级：`Task.definition_of_done: str | None`
> - 角色级默认值：`Role.default_definition_of_done: str | None`
> - 生效规则：`事务自身 definition_of_done` → 缺失则回落到 `主角色的 default_definition_of_done` → 仍缺失则为「未声明，由用户口头判断完成」
> - 恢复契约（第八章）会把这个「生效完成标准」一起返回，因为它是助手判断「做完没有」的依据。
> - 交互上，用户说「这个脉络里先给我能用的就行」即写入该角色的 `default_definition_of_done`。

### 原则 5：轻度维护，热的时候才活跃

- 用户不是每天都要维护一堆分类。
- 近期没活动的角色可以折叠/静置（`Role.active = False`）。
- 系统不因为「你有一堆角色」而逼着你一直操作。

## 三、角色视图模型

### 3.1 角色是什么

角色是一个**用户心智中的事务脉络**。它不是人事意义上的身份，而是事务来自的语境。

例如用户可能心里有这些角色：

- 工作项目 A
- 工作项目 B
- 家庭/孩子事务
- 个人创作
- 给朋友的小帮忙
- 跑腿杂项

### 3.2 角色的结构

- `name`：一个标识，用户能认出。**唯一**（重名报错）。
- `note`（可选）：这个角色大致是什么样的事务集合。
- `default_definition_of_done`（可选）：该脉络的默认完成标准（见原则 4）。
- `active`：活跃 / 静置。静置角色不出现在默认列表里，但数据完整保留。
- `icon` / `color`（可选）：方便区分视图。
- `merged_into`：合并指向（见 3.5）。

### 3.3 事务和角色的关系：多对多

```text
Task.role_ids: tuple[str, ...]   # 非空；顺序只影响展示（第一个是展示主角色），语义上平级
```

规范：

1. **至少属于一个角色**。空 `role_ids` 视为数据损坏，读取时抛 `InvariantViolation`。
2. **可以属于多个角色**（例如「这件事同时是工作里的事、又是给朋友帮的忙」）。
3. **角色之间平级**。系统不假设某角色比另一角色重要。
4. **「移到另一个角色视图」= 编辑 `role_ids`**，不改变事务的任何其他属性。这条必须无歧义，否则「快速移动」会产生副作用。

> **V1.0 已废弃**：原 `main_role_id` + `extra_role_ids` 的单主多从结构已删除。该结构是两头不靠的最坏形态 ——
> 存储上是单角色，概念上却是多角色；「快速移动」语义未定义；「角色可合并」时引用会成孤儿。改为纯多对多。

### 3.4 角色视图能做什么

- 展示该角色下所有事务，按状态/时间排。
- 从该视图新建事务（自动带上这个角色）。
- 快速把某件事从一个角色视图移到另一个（= 增删 `role_ids` 中的 id）。
- 合并角色视图（例如今天想一起看「家庭 + 跑腿」）。
- 沉淀脉络级信息：把「这个角色下我做过什么、我的口径是什么」写进 `note`。

### 3.5 角色合并：重定向语义（规范性）

角色可合并是原则 1 的核心能力，必须有确定的引用处理规则，否则会产生孤儿数据。

```text
Role.merged_into: str | None
```

**读时解析（resolve）**：给定任意 role id，沿 `merged_into` 链**传递追踪**到根角色。已合并角色不出现在常规列表中，但永远可被解析，因此历史事务引用不会失效。

**写时重定向（repoint，事务性）**：合并 A → B 时，在一个数据库事务内完成：

1. 取出所有 `role_ids` 含 A 的事务；
2. 把每处 A 替换为 B；
3. **去重并保持原有顺序**（若某事务原本已有 B，则 A 被吸收而非产生重复项）；
4. 每条受影响事务追加一条 `TaskRecord(type=role_change)`，内容写明 `A → B`；
5. 最后才写 `A.merged_into = B`。

**异常处理**：
- 合并链成环（A→B→A）视为数据损坏，抛 `ValidationError`。
- A 已经是合并态时，应先把 A 解析到根再合并，不允许制造多级歧义链。
- 被合并角色若仍被某事务引用，说明 repoint 未完成，抛 `ConflictError` 而不是静默继续。

**角色删除**：
- 该角色下 **零事务** 时：允许硬删除。
- 该角色下 **有事务** 时：必须先合并到别的角色（或用户逐条改归属），否则抛 `ConflictError` 并提示走合并流程。

### 3.6 角色知识与「来源自报」（规范性，V1.8）

`Role.note` 是**自由文本**：能读，不能检索。脉络级知识要能被找到，所以另立一张
可检索的知识表。

```text
RoleKnowledge:
  id / role_id / kind ∈ {偏好, 口径, 历史决策}
  content      # 原文，**唯一真源**
  search_text  # CJK bigram 形态，由 Python 算好后写入
  source_ref   # 可空：这条知识的出处
  created_at
```

**分类只允许那三类**，写入时校验、非法即抛。多出第四类会让分类既不能用于检索
也不能用于呈现 —— 两个用途同时失效。

**空内容拒绝**；**角色必须存在** —— 否则记下一条永远不会被检索到、也永远不会被
看见的孤儿知识。

#### 检索必须自报来源（这一条是重点）

与第七章同构：排序信号必须附理由、必须标注「启发式提示，不是评分」。
**检索同理** —— 只列结果不列来源，等于要求用户盲信。所以返回值**不只给命中项**：

```text
RetrievalResult:
  hits                        # 每项带 via（怎么找到的）与 score
  truncated                   # **是否被截断** —— 静默截断等于隐瞒
  bm25_hits / tail_hits       # 来源分解
  vector_hits                 # 恒为 0
  vector_unavailable_reason   # 恒有值
  degraded / degraded_reason  # 检索整体不可用时
```

四条硬要求：

1. **`via` 只有 `bm25` / `tail` 两种**，不许加「其他」—— 让「说不清怎么找到的」
   变得可表达，正是最不该可表达的东西。
2. **`tail`（近期回落）必须标出来**，且 **`score` 为 `None`**。给一个假的 `0.0`
   会让人以为「它不相关」，而它只是「最近写的」。
3. **截断必须报**。多取一条用来判断是否截断，然后**说出来**。
4. **空结果也有说法**：「搜过，没找到」与「压根没搜」是两件事。

#### 两条腿，不是三条

| 腿 | 状态 | 理由 |
| --- | --- | --- |
| BM25 | ✅ 走 SQLite FTS5，**零依赖** | 见下 |
| tail | ✅ BM25 落空时回落最近若干条 | 有界，不是「全倒出来」 |
| 向量 | ❌ **刻意没有** | 要 embedding 就得联网，而「断网照常能用」是硬性质 |

所以 `vector_unavailable_reason` **永远有值**，且内容是「本项目刻意不做向量检索」
而不是「向量检索没命中」—— **「刻意不做」与「没命中」必须能区分**。

#### 分词：必须自己切（实测，别凭直觉改）

FTS5 的内置分词器对中文**不可用**：

| 分词器 | 实测结果 |
| --- | --- |
| `unicode61` | 整串中文当**一个 token** → `MATCH '周报'` **0 命中** |
| `trigram` | `销售周报`（3 字）命中，但 `周报` / `王工`（2 字）**0 命中** |

而中文查询大量是 2 字词。所以写入前把 CJK 切成**重叠二元组**
（`交付销售周报` → `交付 付销 销售 售周 周报`），查询用同样形态。

**空格分隔是 AND（实测，与直觉相反）**：所有二元组都必须出现才命中。
所以**长查询比短查询严格**，粗的是短查询。2 字词能搜到是刻意换来的，
代价就是精度更松 —— 界面呈现时必须给出命中数与内容让用户自己判断。

#### 索引同步

FTS5 用**外部内容表**（`content='role_knowledge'`）只存索引，原文永远在
`content` 列。同步交给**三个触发器**，所以索引不会与真源漂移。

- delete / update 触发器必须是 **BEFORE**（外部内容表的 FTS5 不存正文，
  「删掉这一行」要回内容表读该行的值才知道该移除哪些 token；AFTER 时行已经没了）。
- `search_text` 是**一列**而不是触发器里算 —— SQLite **没有 bigram 函数**，
  触发器里做不了这个变换。所以变换由 Python 算好写进该列，触发器只负责复制。
- 验证同步时**不要用 JOIN 查**：内容行删掉后 JOIN 必然返回空，那个结果与
  索引是否同步**无关**。正确姿势是直接查索引
  （`SELECT rowid FROM role_knowledge_fts WHERE ... MATCH ?`），
  再补一句 `VALUES('integrity-check')`。

## 四、事务模型（正交化）

### 4.1 为什么重写：三个维度混进了一个枚举

V1.0 用单一 `status` 枚举表达 `新收集/未排/今日/进行中/等候中/已完成/略过`，这实际上把三个互不相干的维度塞进了同一个字段：

| 混进来的维度 | 原本的表达 |
|---|---|
| 生命周期 | 新收集 → 进行中 → 已完成 / 略过 |
| 调度属性 | 未排 / **今日** |
| 阻塞态 | **等候中** |

后果是**无法表达组合状态**。一个事务完全可能「既是进行中、又被排进今天」，而在旧模型里只能二选一。另外「等候中」与 `category: wait` 语义重复，等于同一件事定义了两次。

### 4.2 正交化后的三个字段

```text
Task.state           : TaskState   # 生命周期
Task.kind            : TaskKind    # 事务形状（解决断点 2「形状不清」）
Task.scheduled_for   : date | None # 调度属性（取代旧「今日」状态）
```

#### `state: TaskState`（生命周期）

| 值 | 含义 |
|---|---|
| `INBOX` | 新收集 / 未排。刚进来，尚未开始。 |
| `ACTIVE` | 进行中。 |
| `BLOCKED` | 等候中，卡在别人/别的系统/某个时间点。 |
| `DONE` | 已完成。 |
| `DROPPED` | 略过 / 放弃。 |

> **「新收集」与「未排」已合并为 `INBOX`。** 旧模型区分二者的依据只是「有没有写大致意图」，这个差异太软。合并后，是否已澄清意图由 `Task.intent is None` 直接表达，语义更准确。
>
> `INBOX` 期间允许继续补充 `intent` / `definition_of_done`；`intent` 为空时视为「意图待澄清」，恢复契约会提示用户先说清楚。

#### `kind: TaskKind`（形状）

| 值 | 含义 | 完成标准 |
|---|---|---|
| `ACTION` | 动作类，有明确的「做到某个 deliverable」目标。 | 必需 |
| `WAIT` | 等候类，等别人/别的系统回复，或等某个时间点。 | 可选（等到即完成） |
| `REMINDER` | 提醒类，不推进，只在某个时间点通知你。 | 可选（到点即完成） |

`kind` 决定 UI 呈现方式和助手介入方式：动作类才需要草稿和多步执行；等候类等的是外部事件；提醒类到点即销账。

#### `scheduled_for: date | None`（调度）

- `None` = 未排进任何一天。
- 非空 = 已排进指定日期，在该日的「今天视图」出现。
- 与 `state` **完全正交**：`ACTIVE` 且 `scheduled_for = 今天` 是合法且常见的组合。

### 4.3 不变式（规范性，必须在服务层校验）

1. **未结束**事务满足 `kind == WAIT` ⟹ `state == BLOCKED` **且** `waiting_on IS NOT NULL`。
   终态（`DONE` / `DROPPED`）不受此约束 —— 等候类是「到期即销账」的：
   `等对方回复合同条款` 在回复到达时应能直接标记完成，因此 `DONE` 是它的合法去向。
2. `state == BLOCKED` ⟹ `waiting_on IS NOT NULL`（不论 `kind`）
3. `state ∈ {DONE, DROPPED}` ⟹ `waiting_on IS None`（结束即清空阻塞）
4. `role_ids` 非空，且去重后长度不变（不允许重复 id）
5. `state == DONE` ⟹ `completed_at IS NOT NULL`；`state == DROPPED` ⟹ `dropped_at IS NOT NULL`
6. `kind == REMINDER` 的事务**允许没有** `definition_of_done`；`kind == ACTION` 且 `state ∈ {ACTIVE, DONE}` 时若 `definition_of_done` 与角色默认值都缺失，视为「完成标准未声明」，恢复契约需提示用户确认

违反任一条抛 `InvariantViolation`。

> **V1.1 修正**：V1.0 初稿里不变式 1 没有「未结束」这个限定，会导致等候类事务永远无法完成 —— 它成了死状态。
> 现在明确了等候类的生命周期：**进 → 等 → 到期销账（DONE）或转成动作（kind 改为 ACTION）**。

### 4.4 合法状态迁移

保持 V1.0 的原意：**不做死板流转，允许简单前后移动**。下表只禁止明显矛盾的方向。

| From | 允许迁往 |
|---|---|
| `INBOX` | `ACTIVE`、`BLOCKED`（需 `waiting_on`）、`DONE`、`DROPPED` |
| `ACTIVE` | `INBOX`（放回去）、`BLOCKED`（需 `waiting_on`）、`DONE`、`DROPPED` |
| `BLOCKED` | `ACTIVE`、`INBOX`、`DONE`（等候到期，直接销账）、`DROPPED` |
| `DONE` | `ACTIVE`（撤销完成）、`INBOX` |
| `DROPPED` | `INBOX`（复活）、`ACTIVE` |

禁止的迁移（需先回到 `INBOX`）：`DONE → BLOCKED`、`DONE → DROPPED`、`DROPPED → BLOCKED`、`DROPPED → DONE`。

**离开 `BLOCKED` 时的 kind 处理**：若该事务 `kind == WAIT`，则迁出 `BLOCKED` 的同时**自动把 `kind` 改为 `ACTION`**，并记录一条 `kind_change`。理由是「等」这件事结束后，剩下的是「拿到结果之后要做的动作」，继续标成等候类既不准确也会撞上不变式 1。迁往 `DONE` / `DROPPED` 时不改 `kind`（终态不受不变式 1 约束）。

迁到 `BLOCKED` 必须提供 `waiting_on`（见第九章）。迁出 `BLOCKED` 允许保留 `waiting_on` 作为历史信息，但 `state` 不再是 `BLOCKED` 时按不变式 3 需清空 —— 实现选择：**清空 `waiting_on`，但把内容写进 `TaskRecord`**，历史不丢。

## 五、事务记录与产物

### 5.1 `TaskRecord`：不可变日志，唯一真源

```text
TaskRecord:
  id, task_id, ts, type, content
```

`type` 取值：
`created` / `note` / `status_change` / `kind_change` / `role_change` / `schedule_change` / `artifact_created` / `artifact_accepted` / `artifact_superseded` / `pause` / `resume` / `rollover` / `reminder_fired` / `delegation_dispatched` / `delegation_succeeded` / `delegation_failed`

**规范性约定**：

1. `TaskRecord` **只追加，永不修改、永不删除**。它是事务历史的唯一真源。
2. `Task.progress_note` 是**派生缓存**，可以从 `TaskRecord` 重建（实现须提供 `rebuild_progress_note(task_id)`）。
   > 这一条是 V1.1 的关键修正。V1.0 让 `progress_note`（手记）和 `artifacts`（草稿）并列为数据源，没定义谁是权威，导致草稿改写时会冲突。现在：`TaskRecord` 是权威，`progress_note` 是投影。
3. 任务被删除时，其 `TaskRecord` 一并级联删除（原型不提供软删除任务，避免历史歧义）。

### 5.2 `Artifact`：带版本与采纳语义

```text
Artifact:
  id, task_id, version, title, content,
  status ∈ {DRAFT, ACCEPTED, SUPERSEDED}     # 枚举值 draft / accepted / superseded
  created_at, accepted_at, supersedes
```

规则：

1. `version` 从 `1` 开始，同一任务内**严格递增**。
2. **修改一个已 `ACCEPTED` 的产物** → 新建 `version + 1`，旧版置 `SUPERSEDED`，新版通过 `supersedes` 指向旧版 id。
3. `SUPERSEDED` 的版本**永不删除**（用户可能想回看上一版）。
4. 一个任务**最多只有一个 `ACCEPTED` 产物**。采纳新版时自动把上一个 `ACCEPTED` 置为 `SUPERSEDED`。
5. `Task.current_artifact_id` 指向当前应该呈现给用户的那一版（通常是最新 `DRAFT`，若无草稿则指向 `ACCEPTED`）。
6. 用户对草稿「圈改 / 局部重做」= 走规则 2 的版本递增，不做原地覆写。

## 六、今天视图与顺延规则

> 这是 V1.0 最大的漏洞：**定义了「今天视图」却没定义它怎么收口**。结果是每天累积，inbox 无限膨胀。

### 6.1 「今天」的边界

- 「今天」= 本地日历日。
- 时间来源必须是**可注入的时钟抽象（`Clock`）**，以便测试确定性。绝不在业务逻辑里直接调用系统时间。
- 时区假设：本地系统时间。V1 不处理跨时区。

### 6.2 视图构成

```text
今天视图 = { 事务 | scheduled_for == today }   # 单一列表，全局按权重降序
```

- `state ∈ {DONE, DROPPED}` 的事务**永不**出现在今天视图，也**永不**被顺延。
- `scheduled_for` 在**未来**的事务不进今天视图，但能在角色视图和所有事务视图里看到。
- **全局有序**：所有条目放在一起按 7.3 排序，分区排序会让「权重降序」失去意义。
- 被顺延过来的事务在列表里额外带**「顺延」标记**，不单独分区。

> **V1.1 修正**：V1.0 初稿在这里同时定义了「顺延」和「逾期分区」，但二者是矛盾的 ——
> 顺延在访问时立即执行，事后 `scheduled_for < today` 的集合恒为空，逾期分区永远没内容。
> V1.1 只保留**顺延标记**：逾期信息以「这几条是从之前顺延来的」形式呈现，
> 既保留了可见性，又不会产生一个无人清理的滞留区。
>
> **为什么必须有顺延**：没有收口机制的话，inbox 会无限膨胀 ——
> 每天新增的事务都堆在「未排」里，视图越来越长，最终用户不再打开它。

### 6.3 顺延规则（rollover）

**触发**：每次访问今天视图时，**先**执行一次当日顺延检查。

**动作**：对所有满足 `scheduled_for < today` 且 `state ∉ {DONE, DROPPED}` 的事务：

1. `scheduled_for` 改为 `today`；
2. 追加 `TaskRecord(type=rollover, content="原定 <旧日期>，顺延到 <今天>")`。

**幂等**：同一天内第二次访问不得重复顺延。实现以「顺延后 `scheduled_for == today`」自然满足，测试须显式验证幂等。

**合并通知**：顺延结果**汇总成一条**摘要输出（如「3 条事务从之前的日子顺延到今天」），**绝不逐条弹通知**。这是原则 5「不在没被问的时候高频扰民」的直接体现。被顺延的事务在本日视图里会额外带「顺延」标记。

### 6.4 手动调度

- `pin(task, date)`：排到指定日期（可未来）。
- `unschedule(task)`：置 `scheduled_for = None`，**且不强制把 `state` 打回 `INBOX`** —— 一个进行中的事务被移出今天视图是合法操作。

## 七、排序：透明弱信号

> V1.0 的自相矛盾之处：痛点 4 说「优先级冲突靠直觉、缺少明确依据」，而答案却是「助手不替用户排序，把今天的事摆出来」。如果今天有 5 件事，用户仍要自己从头排 —— 决策负担没降低，只是从 8 件事变成 5 件事。

### 7.1 立场：摆得更清楚 ≠ 替你决定

保留「不替用户做真正的价值取舍」这条底线，但补上**确定性、可解释、可反驳**的弱信号。

每条信号产出 `(code, weight, reason)`：

- `reason` 是**面向用户的中文说明**，必须与任务一起展示。
- 输出结果必须标注「**启发式提示，不是评分**」。
- 用户可以反驳任一信号；被反驳过的信号不应反复出现同一误报。

### 7.2 信号权重表（规范性）

表中同时给出**枚举名**与**枚举值** —— 代码里 `SortSignalCode.OVERDUE_WAIT` 的 `.value` 是
小写 `overdue_wait`，落库与测试断言都用小写形式。

| code（枚举名 / 枚举值） | 权重 | 触发条件 |
|---|---|---|
| `OVERDUE_WAIT` / `overdue_wait` | +50 | `waiting_on.follow_up_at` 已过，且仍未跟进 |
| `DEADLINE_RISK` / `deadline_risk` | +40 | `due_time` 距今 < 24 小时，且未完成 |
| `DEPENDED_ON` / `depended_on` | +30 | 该事务被其他未完成事务依赖（V1 用 `Task.blocked_by: list[str]` 手工标记） |
| `RESUME_STALE` / `resume_stale` | +20 | `state == ACTIVE` 且距「最后一次恢复或最后一次更新」超过 3 天（`last_resumed_at` 为空时回退到 `updated_at`，这样「刚 start 完就再没碰过」也算中断） |
| `WAITING_TOO_LONG` / `waiting_too_long` | +15 | `kind == WAIT` 且 `waiting_on.since` 距今超过 7 天 |
| `SCHEDULED_TODAY` / `scheduled_today` | +10 | `scheduled_for == today` |
| `INBOX_UNSORTED` / `inbox_unsorted` | +5 | `state == INBOX` |
| `ENERGY_FIT` / `energy_fit` | +8 | `reminder_time` 落在用户设置的精力档位（早晨 / 下午 / 晚上） |

权重与触发条件均为规范性内容，代码中的 `SORT_SIGNAL_WEIGHTS` 常量必须与此表逐项一致。

### 7.3 排序算法

1. 排除 `state ∈ {DONE, DROPPED}`。
2. 逐条计算命中的信号，总权重求和。
3. 排序：总权重**降序**；同权重按 `entered_at` **升序**（先进先出）。
4. 每个任务携带其全部命中的信号（不是只有最高的那条），供 UI 展示全部理由。

### 7.4 精力档位

用户可设置三个时段：`早晨` / `下午` / `晚上`（V1 为固定三档，不做自定义）。`ENERGY_FIT` 依据 `reminder_time` 或 `scheduled_for` 落在哪个档位命中。未设置档位时该信号不命中。

## 八、恢复契约

> 原则 3「可以从任何事务进入，恢复上下文」在 V1.0 里只是一句愿望 —— 既没定义「恢复」需要给什么，也没定义三个数据字段谁权威。V1.1 把它变成**可验证的结构**。

### 8.1 恢复契约（RestoreContract）

打开任一事务时，系统**必须**返回 `RestoreView`，包含以下全部内容：

| 字段 | 说明 |
|---|---|
| `task` | 基本信息：`title` / `intent` / `state` / `kind` / `role_ids` |
| `effective_definition_of_done` | **生效**完成标准（事务级 → 角色默认值 → `None`） |
| `current_artifact` | 当前产物：内容 + `version` + `status` |
| `progress_note` | 进度摘要（派生自 `TaskRecord`） |
| `recent_records` | 最近 N 条 `TaskRecord`，默认 N = 20，按时间升序 |
| `waiting_on` | 等候对象（若 `state == BLOCKED`） |
| `next_actions` | 系统生成的下一步建议（中文，`list[str]`） |
**这个结构就是「恢复上下文」的可验证定义**，也是把事务重新装载进助手的输入。少任何一项都算恢复失败。

### 8.2 `next_actions` 的生成规则

`next_actions` 不是空话，按状态分支生成：

| 条件 | 建议内容 |
|---|---|
| `kind == REMINDER` 且已到点 | 「确认这条提醒是否还需要；要取消就销账」 |
| 有 `waiting_on` 且 `follow_up_at` 已过 | 「催一下 <who_or_what>」 |
| 有 `waiting_on` 且 `follow_up_at` 未到 | 「等 <who_or_what>；预计 <follow_up_at> 该跟进了」 |
| `state == ACTIVE` 且有草稿 | 「草稿已到 version N：继续改，还是重写」 |
| `state == ACTIVE` 且无草稿 | 「还没有草稿，可以说『先理一版』让助手起个骨架」 |
| `state == INBOX` 且有草稿 | 「已经有草稿（version N）但还没开始：说『开始做』或直接采纳」 |
| `intent_pending` | 「先说清楚这件事想做到什么程度」 |
| 生效完成标准缺失 且 `kind == ACTION` 且 `state ∈ {ACTIVE, DONE}` | 「先说清楚做到什么程度算完」 |
| `scheduled_for` 已逾期 | 「原定 <日期>，**已逾期**；今天做还是改期」 |

**等候那两行的条件写「有 `waiting_on`」而不是 `state == BLOCKED`**，是因为
`validate_task` 的三条不变式（BLOCKED 必须有 `waiting_on` ／ 非终态 WAIT 必须
BLOCKED ／ 终态不得保留 `waiting_on`）加上 `set_state` 离开 BLOCKED 即清空，
使两者**恒等**。写成 `state == BLOCKED` 也对，但写「有 `waiting_on`」更贴近
代码实际判的东西。

#### 文本必须能从「本函数持有的事实」推出（规范性）

`next_actions` 的**每一句**都必须能从 `build_view()` 真正持有的数据推出来。
**断言本函数无权确认的全局状态 = 说假话**，与实现无关。

> 踩过的坑（V1.9 实测抓到）：逾期那行原写「原定 <日期>，**已顺延**」。
> 顺延由 `TodayService.view()` 触发，而 **`/task` 不调它** —— 用户先跑
> `/task` 时库里 `scheduled_for` 还是旧日期，那句话是假的。
>
> 本函数能断言的是「原定日期已过」（两个持有事实的比较），
> 不能断言「顺延执行过」（一个它无权观察的全局状态）。
>
> 这与 3.6「截断必须报」、第 10 项「tail 回落标成 `tail` 而不是 `bm25`」
> 是同一类毛病：**断言比事实强**。新增任何一条 `next_actions` 时，
> 按这条判一遍。

### 8.3 恢复的量化目标

从打开事务到拿到可执行的下一步，**交互轮数 ≤ 2**。这是 V1 的成功判据之一（第十四章 H2）。

#### 场景 S5 的定义（V1.9 补上）

14.2 引用「场景 S5（跨角色中断恢复）」，而**本文此前从未定义它** ——
只有引用，没有定义，是一处悬空引用。补上：

> **S5（跨角色中断恢复）** = 同时满足三条的事务：
>
> 1. 归属 **≥ 2 个角色**（跨角色）
> 2. **已经开始过、然后中断**（有历史，不是一条刚建的空壳）
> 3. 用户**在丢掉上下文之后**回来 —— 所以只能靠 `/task` 单条命令拿回上下文

「一轮」= **一条命令 + 它的输出**。所以 S5 的标准动作是 `/task <id>`，
判据是这一条命令的输出**是否足以让人开始动手**；不够就得再问一条（那就是 2 轮）。

> 判「可执行」而不是「看到点文字」：`/task` 印草稿**只印前 12 行**
> （`render_task`），所以「继续改还是重写」在稿子更长时**需要**再跑
> `/artifact` —— 那种情况记 2 轮。

#### V1.9 实测结果（`tools/probe_h2_recovery.py`）

| 场景 | 轮数 | 决定性的一步 |
|---|---|---|
| 等候 · 跟进已过 | **1** | 催一下 客户法务 |
| inbox · 有草稿没开始 | **1** | 已经有草稿（version 1）但还没开始 |
| 进行中 · 长草稿 20 行 | **2** | 草稿已到 version 1：继续改，还是重写 |
| 进行中 · 无草稿 | **1** | 还没有草稿，可以说「先理一版」 |
| 原定日期已过 | **1** | 原定 …，已逾期；今天做还是改期 |
| 缺完成标准 | **1** | 先说清楚做到什么程度算完 |

**6 个场景，0 个超过 2 轮 → H2 未被推翻。**

但这个结论要连着三个限制一起读，否则就是过度宣称：

1. **S5 的定义是探针补的**，不是文档原有的（上面那条定义也是这次才写进来的）。
2. **只有 6 个场景**，且是同一个探针选的 —— 不是随机抽样。
3. 判「够不够可执行」有一部分**判据写死在探针里**（长草稿那条规则）。
   换个人来判，S5-3 可能算 1 轮。

所以这是**「不反对 H2」，不是「证明 H2」**。真正的证明要拿真人用。

> 探针顺带抓到的那处假话（逾期行说「已顺延」）已修 —— 见 8.2 的
> 「文本必须能从本函数持有的事实推出」。那个 bug 是**探针跑出来的**，
> 不是读代码看出来的：光读 `restore.py` 只会觉得那句文案挺顺。

## 九、提醒与等候

> V1.0 把「提醒」列为 V1 功能，却没定义通知渠道、错过提醒怎么办，以及 `wait` 类事务到底在等谁。缺了这些，「提醒」根本无法成立。

### 9.1 `WaitingOn`：等候对象

```text
WaitingOn:
  kind ∈ {PERSON, SYSTEM, TIME}
  who_or_what : str        # 等谁 / 等什么系统 / 等到什么时候
  since       : datetime   # 从什么时候开始等（驱动 WAITING_TOO_LONG 信号）
  follow_up_at: datetime | None   # 该跟进的时间（驱动 OVERDUE_WAIT 信号）
  note        : str | None
```

没有这个结构，`BLOCKED` 就是一个黑洞状态，原则 3 的「为什么卡住」根本答不上来。

### 9.2 提醒引擎

- **触发方式**：轮询式（poll-based）。REPL 每次循环、Web 每次加载、以及显式 `/tick` 命令时，检查 `reminder_time <= now` 的未销账提醒。
- **通知渠道（V1）**：终端输出（stdout）、飞书私聊、Web 界面。三条渠道共用同一套判定与渲染（9.4 的合并摘要），只有「送达确认」的位置不同。
- **V1 已知限制（必须在产品内明示）**：**系统不运行时不会通知。** 原型阶段接受这个边界。
- **去重与送达的先后（规范性）**：`REMINDER_FIRED` 去重令牌必须在**送达确认之后**落库，不得在查询阶段提前落库。「已发过」是一个**关于送达的事实陈述**，不是关于「检查过」的记账 —— 提前落库等于在用户没收到的情况下宣称已送达，逾期之后连 9.3 的「已错过」分支都不会再触发它。
- **宁可重发，不可静默丢弃（规范性）**：送达失败时令牌**不落库**，该提醒保持待发。因此系统允许重复送达，**不承诺恰好一次**。这条是上一条的直接推论，且刻意如此 —— 个人事务助手的代价函数里，重复提醒的代价远小于静默吞掉一条提醒。

#### 取与确认分离（规范性 API）

```text
ReminderEngine.due() -> ReminderDigest        # 纯查询：到期且未确认送达的，不写库
ReminderEngine.acknowledge(digest) -> None    # 送达确认后才落去重令牌
```

**不存在**「取走即消费」的入口。曾经有一个 `check()` 同时做两件事，于是三条渠道全部踩坑：

| 渠道 | 曾经的坑 |
| --- | --- |
| `GET /api/reminders` | **GET 有副作用**。刷新、prefetch、探活、监控轮询都会吃掉提醒；并发双加载时第一个消费掉、第二个拿到空；handler 或序列化一抛，令牌已落、提醒永久丢失。 |
| 终端 / `/tick` | `_say()` 写 stdout 失败（管道断裂、编码错误）时令牌已落。 |
| 飞书 | `_notify_operators` 逐个吞掉发送异常且**不报结果**，调用方无从得知失败 —— 于是全部失败时照样落令牌、永久标记成已送达。 |

各渠道的确认点：

- **终端 / `/tick`**：`_say()` 成功返回之后。
- **飞书**：`_notify_operators()` 返回「至少送达一个」。它现在**必须**报出送达与否 —— 以前逐个吞异常且不报结果，调用方只能当成功。
- **Web**：`/api/reminders` 是三条渠道里唯一「加载即送达」的，handler 先查、构造出 payload、**再**落令牌。剩下的极限是「响应构造成功但客户端没渲染」—— HTTP 单向确认测不到这一段，是协议本身的限制。整个 handler 在 `app.lock` 内，所以查与确认之间不会被另一个请求插进来。

### 9.3 错过提醒（missed reminder）

- 若 `now - reminder_time > 6 小时`，该提醒标记为**已错过**。
- 输出必须**如实说明「这条提醒已错过」**，而不是当作刚发生的新提醒急迫呈现。
- 已错过的提醒并入当次摘要，不单独触发。

### 9.4 合并摘要

一个轮询周期内所有到期提醒**合并为一条摘要输出**，不逐条打断。对齐原则 5 与第九章「不做什么」中的「不在没被问的时候高频扰民」。

### 9.5 等候跟进

- `follow_up_at` 到期未跟进 → 触发 `OVERDUE_WAIT` 排序信号（第七章），并在今天视图的信号理由里显示「该催 <who_or_what> 了」。
- 跟进 = 给事务加一条 `TaskRecord(type=note)`，可选择同时更新 `follow_up_at`。

### 9.6 重复提醒：显式时区 + 墙钟时间（规范性）

一次性的提醒存一个瞬时就够。但「每天早上八点」**不是**一个瞬时 —— 它是一条规则，
自动产出的瞬时会随夏令时漂移：不存时区的话，本地时间从 UTC+8 换到 UTC+9，
「八点」会跟着漂一小时。

```text
RecurrenceRule:
  kind       ∈ {DAILY, WEEKLY}
  time       (str)          # 本地墙钟 HH:MM:SS，不带时区
  timezone   (str)          # 显式 IANA 名，如 Asia/Shanghai。**必填，不猜**
  weekdays   (tuple[int])   # ISO 星期几（1=周一…7=周日），只对 WEEKLY 有意义
```

- **`timezone` 必填。** 缺失时**拒绝**而不是回落到某个默认 —— 猜错时区的后果
  是「每天八点」在某天变成九点，而用户不会知道。
- **`kind` 只支持 `DAILY` / `WEEKLY`。** 刻意不做：
  - `every_N_seconds` 量的是**流逝时间**而非墙钟，跨夏令时不会跟着走 ——
    「每 86400 秒」在换表那天不等价于「每天」。两种语义不能混。
  - `cron` 的五字段表达式（步长、范围、`*` 的星号语义）是另一个规模的实现。
- **夏令时**（两条都实测过，见 `tests/test_recurrence.py`）：
  - **空洞**（春季跳表，`02:30` 那天不存在）→ **跳过那天**。
    另一种选择是顺延到 `03:00`，但那会让「八点」在某天变成九点，更不像用户要的。
  - **重叠**（秋季回拨，`01:30` 那天出现两次）→ **取更早的那个**。
    取更晚会让提醒晚一次。
- **规则坏了不降级**：`parse_rule` 抛 `RecurrenceError`，**不**当成「无规则」。
  降级等于把「每天八点」悄悄变成一次性，而用户不会知道。
- **装载规则时立刻对齐** `reminder_time` 到下一次；不推的话这条事务要么永远不响
  （时间落在过去的空档），要么立刻响一次（时间还没到），两种都是错的。
- **卸规则时只清规则、不动时间** —— 留着时间当一次性提醒是合理的降级，
  而清掉时间会静默取消提醒，那是另一种后果，得让用户显式说。
- **规则算不出下一次时不撤销令牌**：那条**确实送达了**，令牌照落，只是不再排下一次。
  反过来做的话，一条坏规则会连累已经发出去的提醒被反复重发。

### 9.7 乐观并发（规范性）

`Task.revision` 每次写入自增。读-改-写时**必须**带上读出来那一刻的 `revision`；
与库里的值不符说明中间有人改过，抛 `StaleRevisionError`（`ConflictError` 的子类）
而**不是覆盖**。

- **为什么不用 `updated_at`**：它是**时间戳**，同一秒内的两次写入分不出先后，
  于是「我读到的还是最新的吗」这个问题用时间戳回答不了。并发控制要的是
  **单调计数**。
- **为什么默认就是安全的**：所有服务方法都是「`get()` → `_replace()` → `update()`」，
  `get()` 读到的就是当前 `revision`，所以它们全都照常工作；冲突只在真有并发写入时触发。
- **覆盖是最后手段** —— 提醒改期与委派状态都是读-改-写，静默覆盖会把对方的改动吃掉，
  症状是「我明明改过了，怎么又变回去了」。

## 十、交互模型

### 10.1 新建事务

- 直接对话丢进来：「帮我盯一下下周五交的报告」、「儿子学校那边要交的材料」。
- 助手调 `LLMProvider.classify()` 推断 `kind` 与角色候选：
  - 角色明确 → 直接带上角色；
  - 角色不明确（置信度低于阈值）→ **问一句**（可选，用户可跳过并归入「未分类」角色）。
- 不需要填一堆字段。**至少标题 + 一句意图即可进来。**
- 创建后状态为 `INBOX`，`intent` 为空时视为「意图待澄清」。

### 10.2 查看事务

- **今天视图**：今天能动的事 + 到点的提醒 + 逾期分区。
- **按角色视图**：某角色下所有事务。
- **所有事务视图**：全览。

视图之间可自由切换，**底层数据始终一份**。

### 10.3 处理事务

- 显式操作：`开始做`（→ `ACTIVE`）、`等会再做`（→ `INBOX`）、`放一放`（→ `BLOCKED` + `WaitingOn`）、`做完啦`（→ `DONE`）、`算了`（→ `DROPPED`）。
- 过程中产生的草稿/内容：用户可直接圈改，或要求局部重做（走 `Artifact` 版本递增，第五章）。
- 中途被打断是**正常路径**而非异常：助手把状态存入 `TaskRecord` 并置 `last_resumed_at`，等用户回来按恢复契约恢复。

### 10.4 助手能做的事（V1 范围）

- 推断 `kind`（动作 / 等候 / 提醒）。
- 推断角色候选，用户可纠正。
- 把零散信息整理成一段可用的东西（生成带 `[TODO]` 占位的结构化草稿）。
- 从已有事务上下文里找相关内容。
- **把大事务拆成几个步骤 —— 只拆，不排序**（`split_steps` 明确不产出优先级）。
- 做事过程中记录进度，保留恢复点。

## 十一、数据模型

### 11.1 角色

```text
Role:
  id
  name                        # 唯一
  note                (str | None)
  default_definition_of_done (str | None)
  active              bool     # 静置
  icon / color        (str | None)
  merged_into         (str | None)
  created_at / updated_at (datetime)
```

### 11.2 事务

```text
Task:
  id
  title                                  # 一句话，必填
  role_ids                (tuple[str])   # 非空，首个为展示主角色
  state                   (TaskState)
  kind                    (TaskKind)
  intent                  (str | None)   # 一句话「想做到什么程度」；None = 意图待澄清
  definition_of_done      (str | None)   # 缺失则回落到角色默认值
  scheduled_for           (date | None)
  due_time                (datetime | None)
  reminder_time           (datetime | None)
  reminder_rule           (str | None)   # 重复提醒的生成器（原始 JSON 文本）；空 = 一次性
  revision                (int)          # 每次写入自增，乐观并发用，见 9.7
  waiting_on              (WaitingOn | None)
  blocked_by              (tuple[str])   # 依赖的其他任务 id
  entered_at / created_at / updated_at  (datetime)
  completed_at / dropped_at / last_resumed_at (datetime | None)
  progress_note           (str | None)   # 派生缓存，非真源
  project_path            (str | None)   # 非空 = 委派事务，见 11.8
  delegate_chat_id        (str | None)   # 委派从哪个飞书会话发起，见 11.9
  delegate_requested_by   (str | None)   # **谁发起的**（人，不是会话），「只有发起人能批」的输入，见 11.8.1
  current_artifact_id     (str | None)
```

> **`reminder_time` 是指针，`reminder_rule` 是生成器。**
>
> `reminder_time` 始终是**下一次触发的瞬时**，`reminder_rule` 是产生它的规则。
> 确认送达后引擎问规则要下一个，把结果写回 `reminder_time`。
> 于是到期查询、合并摘要、错过窗口（9.3）**全都不需要知道规则存在**。
>
> 规则存**原始 JSON 文本**而不是结构化列：规则是**整体替换**的
> （改时间就是换一条规则），没有按字段查询的需求；而文本列让「规则坏了」
> 由 services 层一次校验拦住，不落到 SQL。规则的时间是**墙钟时间** +
> **显式 IANA 时区**，夏令时空洞跳过、重叠取更早 —— 见 9.5。

### 11.8 委派（V1.2 新增）

把一件事交给外部执行器（opencode）在**指定项目目录**里完成。

**不引入新概念** —— 委派复用已有的事务 / artifact / 日志：

| 委派要素 | 载体 |
|---|---|
| 需求 | 一条**事务**（`project_path` 非空） |
| 给执行器的简报 | artifact v1 |
| 执行器的产出 | artifact v2（版本链永不覆写） |
| 全程留痕 | `TaskRecord` |
| 人工闸门 | 状态迁移（`inbox → active`） |

**三道闸门，缺一不可：**

1. **项目白名单** —— `config.json` 的 `delegate.projects`，只接受**绝对路径**。
   链路的终点是本地代码执行，所以能去哪些目录必须是用户预先批准的清单，
   不能由消息内容决定。相对路径一律拒绝（基准随工作目录变，是绕过白名单的常见手法）。
2. **人类确认** —— 只有 `state == ACTIVE` 的委派才会被派发。`inbox` 的绝不碰。
   创建时**必须**是 `inbox`。
3. **执行期逐次授权** —— opencode 动手前必须挂起，由人逐次决定。见 11.8.1。

**执行器是独立进程**（`python -m freeagent.delegate`），只从库里取已确认的委派，
  **不接受任何外部消息作为指令**（命令 / 任务 / 授权都只能经由它自己签发的凭据进入；它会接受对「它自己提出的问题」的文本答复，见 11.8.1「新增的信任面」）。「远程输入」与「本地代码执行」之间的闸门是**代码层的**（`eligible_tasks` / `check_project_allowed` / `ApprovalStore`），**合并进程也绕不过**；进程拆分给的是**纵深防御**，而真正的好处是**交互中桥接重启不丢**（见 11.8.1「拆开还是合并」）。

**幂等**：派过一次的事务不再派发 —— 判定依据是日志里有没有
`delegation_dispatched`，而不是另存一份状态（两处状态必然会出现不一致）。

**失败可重派，但不是「无条件」（规范性，V1.13 补）**

原先只问「最后一条派发相关记录是不是 `delegation_failed`」，是就重派。
这对**执行期**失败是对的（模型偶发 402、opencode 崩了、网络抖了，重试有意义），
但对**派发前就被拒**的失败是灾难 —— 那类阻塞在**任务之外**：

| 失败 | 重试结果 |
| --- | --- |
| 白名单拒绝 | 改配置前重试多少次都是同一个结果 |
| 没有闸门 | 同上（`_dispatch_one` 在 `subprocess_runner` 之前就拒了） |

**实测（`--watch` 常驻，2026-09-30）**：飞书凭据没配 → 执行器常驻 → **180 秒扫了
60 轮、写了 60 个产物版本（v51→v60）**，而真正的委派一条没干成。
每轮都撞同一堵墙，每轮都留痕 —— 而**留痕恰好让重试合法化**。

> 之前的 docstring 预警过「持续失败会反复发批准卡」，但**只覆盖 `--tool-gate`
> 路径**。无闸门时**一张卡都没有**，代价从「刷屏」变成**静默的数据库膨胀**，
> 那句预警完全没提到它。**这是同一类盲区**：预见了带卡的失败，没预见无卡的。

**判据从记录形状推出来，不给失败加标签**：一次尝试里有没有真的
`delegation_dispatched`。没有 ⇒ 压根没跑到执行器 ⇒ 阻塞在任务之外 ⇒ 不重试。

| 最后一次尝试 | 记录形状 | 判定 |
| --- | --- | --- |
| （没有） | — | 没试过 → **派** |
| 派发前被拒 | `failed`（无前置 `dispatched`） | **不重试**（确定性） |
| 执行期失败 | `dispatched` → `failed` | **可重派** |
| 正在跑 | 只有 `dispatched` | 别再派（会**并发**改同一目录） |
| 做完 | `succeeded` | 别再派 |

> ⚠️ **代价，且是一个已知缺口**：「派发前被拒」不再自动重试，意味着**修好配置后
> 这条不会自动恢复**。而落库那句「可以 /note 记下原因后重派」是**空头承诺** ——
> `note` 不是终态记录，什么也重置不了。恢复入口至今**没有实现**。
> 要做常驻执行器之前得先补它，否则「修好配置后重试」这一步只能手工建新事务。


**失败必须留痕**：白名单违规、执行器非零退出、输出不可解析，全都收敛成
`delegation_failed` 记录而不是往上抛 —— 往上抛会中断整批派发，
没记录则该事务会永远停在 `ACTIVE` 反复重试。

`RecordType` 新增三个值：`delegation_dispatched` / `delegation_succeeded` / `delegation_failed`。


#### 11.8.1 执行期逐次授权（**已接线并实现；真机飞书点击未验**）

第三道闸门由 opencode 自己的 permission 机制承担。**不是 fork，不是二开** ——
用它的 HTTP 服务当客户端即可，闸门逻辑全部留在 FreeAgent 这侧。

> **落地状态**：
>
> | 部分 | 状态 |
> |---|---|
> | 机制可行性（挂起 → 回答 → 落盘） | ✅ **已实测跑通** |
> | **版本断言**（挡住 V2 静默接管） | ✅ **已实现** |
> | **飞书接线**（`permission.asked` → 卡片 → 点回 → 送回） | ✅ **已实现** |
> | **「只有发起人能批」** | ✅ **已达成**（V1.17）—— 发起人落库（`tasks.delegate_requested_by`），待批行 / 卡片收件人 / 执行期授权三处统一用它。旧库自动迁移，无身份时落回 approver |
> | 静默超时降级为 `reject` | ⚠️ **复用既有 `wait()` 语义，但真机未验** |
> | **答复载荷形状**（`{"reply": "once"\|"reject"}`） | ✅ **V1.11 真机已验**：两个方向各跑一次，allow 后文件真被改、deny 后文件没动 |
> | **真机点一次飞书卡片** | ⬜ **仍未验** —— 但**范围已缩小**：现在只差「飞书会不会把按钮 `value` 原样带回」，协议形状本身已验过 |
>
> 所以现在跑 `python -m freeagent.delegate --tool-gate` 会**真的**逐次问人；
> 不加 `--tool-gate` 则走**无人值守**老路（那时第三道闸门不存在）。

##### 执行器接缝：协议知识只住一个文件（规范性，V1.7）

V1 → V2 的 permission 字段名全变（`permission` 对象 / `bash` / `task`
→ `permissions` 数组 / `shell` / `subagent`），而**旧字段被静默忽略** ——
不报错、不警告，闸门随之失效，**失效方向恰好是最危险的那侧**（默认回到 allow）。

在有接缝之前，那些字段名**散在三处**（权限配置、事件解析、答复载荷）。改一次协议
要动三个地方，而漏掉一个的后果不是「跑不起来」，是**闸门静默失效**。

所以有这一层（`services/executors.py`）：

```text
ExecutorAdapter:
  executor              # "opencode"
  major                 # 主版本
  verified              # **是否对着真实实例验过**
  field_names           # 该版本的键名（可被测试断言，不埋在拼 dict 里）
  build_permission_config() -> dict
  parse_request(properties) -> ToolPermission | None
  build_reply(decision) -> dict
```

三条规范：

1. **协议知识只住在适配器里。** `opencode_server` 的三个函数保留（delegate 与
   tests 从那里导入），但它们是对适配器的**转发**，不是各自实现。
2. **`verified=False` 的适配器不可派发。** 闸门只放行 `verified=True`。
3. **取不到版本不许回落。** `adapter_for()` 取不到就返回 `None` ——
   回落到 V1 正是那个 bug 的形状。

**「知道」与「能派发」是两个概念。** V2 的适配器**存在**（于是闸门能说
「认识但没验过」而不是笼统的「不认识」），但它 `verified=False`，所以**本次改动
不改变任何运行时行为** —— V2 仍然拒绝派发。

> **V2 为什么未验证**：官方文档给出了键名改名，但**没有给出
> `permissions` 数组元素的形状** —— 那才是能据以接线的部分。猜一个
> 「看起来很像对的」形状比拒绝更危险：它会静默地不生效。
> 那三个方法现在都抛 `UnverifiedExecutorError`，错误信息里写明缺的是什么、
> 要去改哪里。**要接 V2**：对着一个真实 V2 实例实测 → 改那三个
> `_v2_unverified` → `verified` 改 `True` → 同步本节。

`SUPPORTED_OPENCODE_MAJOR` 由注册表**推导**（`dispatchable_majors()` 的第一个），
不是硬编码常量。用「取第一个」而非「取全部」是刻意的：将来 V2 也验证过了，
这里会变成 2，而闸门仍只放行 1 —— 那时要**显式**改这一行，而不是让
「多了一个已验证适配器」自动改变闸门行为。

##### 怎么开

```bash
python -m freeagent.delegate --tool-gate
```

**不加这个开关就没有第三道闸门** —— 老路是 `subprocess` 一次跑到底。
它保留是因为已真机验证过、且能在没有飞书通道的环境下工作；
但**它不是**「安全但安静」，它是**没有执行期闸门**。

##### 模块与调用链

| 文件 | 职责 |
|---|---|
| `services/opencode_server.py` | 服务生命周期 + REST + SSE。**不做审批判定** |
| `services/approval.py` | 判定与落库，**唯一真源**（`request_tool_call()`） |
| `feishu/sender.py` | `send_tool_card()` / `_tool_card()` |
| `feishu/bridge.py` | 卡片点击 → `store.resolve()` |
| `delegate.py` | `run_with_tool_gate()` 循环 + `run_once_with_tool_gate()` 批量 |

**桥接的 `_card_action` 一行都不用改** —— 执行期卡片刻意复用
`allow_once` / `deny` 两个动作名与同样的 `{"action", "id"}` value 形状，
所以那条处理路径**原样适用**。这就是「一份能力一份实现」的直接收益：
新能力不需要第二套审批处理。

**为什么卡片不直接复用 `send_approval_card`**：那张卡写死了
「不点就算拒绝」；执行期要说的是**「只批准这一个动作，下一个还会再问」**。
同一张卡说两套话会让人以为「我允许了这次，后面就都行了」——
而那恰恰不是事实（V1 的 `always` 是会话级，我们刻意不映射过去）。

##### 判定仍然只有一处

`OpenCodeServer` **只搬运，不判定**：
- `permission_from_event()` 把 opencode 的问题原样取出；**认不出返回
  `None`**，绝不用空串凑一个 —— 上层要靠它区分「无法回应」（该报错）
  与「已拒绝」（该继续跑），混起来会让 agent 干等而人这边什么都不知道
- `reply_payload()` 把本地结论翻成 `{"reply": "once" | "reject"}`

**结论一律回库读**（`store.wait()` → `store.decide()`），与 11.9.4 同一条纪律。
不采信任何返回值。

**`reply` 只映射到 `once`，刻意不映射 `always`**：V1 的 `always` 是
**会话级**授权，而本项目明确不做永久授权（11.9.7「明确不做的：永久授权」——
半年后它会变成绕过闸门的后门）。而且每次都问本来就是这个闸门的意义。

##### 没有飞书通道 ⇒ 拒绝派发

`run_with_tool_gate()` 在 `sender is None` 时**直接返回失败**，
**绝不**降级成「无人值守跑」。那正是闸门形同虚设的样子：
通道坏了 = 无人监督 = 拒绝。

##### 「只有发起人能批」（**已达成** —— V1.16 补机制，V1.17 接发起人）

设计文档早就要求这条（抄自 QM 的 *"only the person who requested this
command can approve or deny it"*），但**代码一直没做** ——
飞书白名单里任何一个人都能点掉别人发起的委派。本轮补上：

- `pending_approvals` 加 `requested_by` 列（schema 迁移 **4 → 5**，可空，
  旧行不拦，否则加列会让老卡永远点不动）
- 判定写在 `ApprovalStore.resolve()` —— **唯一写入口**。放在桥接里会
  出现「这条路径查了、那条路径忘了」
- 身份比对用**双向后缀匹配**：飞书同一个人的 `open_id` 与租户级 `user_id`
  是两个不同的串（实测踩过：白名单两种都收），只按单边比会把
  「他自己点自己发起的卡」判成越权 —— 那种误拒比不拦更糟
- 短后缀（< 8 字符）不放行，避免「恰好是后缀」的巧合
- `can_answer()` 只用于给用户**一句准确的话**：`resolve()` 对
  「不是发起人」「已决定过」「已过期」都返回 `False`，而这三件事
  必须显示成完全不同的文案

**同时修了一个既有测试**：`test_delegate_gate.py` 里 `approver="ou_x"`
却用 `ou_tester` 去点。那不是「测试更宽松」，而是**不真实的设置**
（现实里卡只发给 approver）。越权那条另有用例锁。

##### 「只有发起人能批」取值错在哪（V1.16 实测更正 · **V1.17 已修**）

上一小节列的那套机制**是真的**：列在、判定在 `resolve()` 这个唯一写入口、
身份比对是双向后缀匹配（飞书同一个人的 `open_id` 与租户级 `user_id` 是两个
不同的串，只按单边比会把「他自己点自己发起的卡」判成越权）、短后缀不放行、
`can_answer()` 给准确文案。**全部有实现，全部有测试。**

**错的是喂进去的那个值。** 完整证据链：

| 环节 | 事实 |
| --- | --- |
| `tasks` 表 | **没有任何「谁发起的」列** —— 只有 `delegate_chat_id`（会话，不是人）|
| `_cmd_delegate` | 只落 `delegate_chat_id`；签名是 `(self, args)` —— ~~发送者身份压根没进命令层~~ **V1.17 更正：此处记录有误** —— `channel.py:312` 早就设了 `repl.channel_ctx.sender_open_id`，身份**已到命令层**，是**落库时丢的** |
| `build_real_gate` | `approver = next(iter(sorted(cfg.allowed_users)), "")` —— **白名单里排序第一的那个人** |
| `ApprovalGate.context` | `who=self._approver` |
| `request_delegation` | `requested_by=context.who` ← **就是那个人** |

所以规则的**实际效果与文档描述相反**：

- **真正的发起人被挡在门外**（除非他刚好排序第一）
- **一个没发起的人反而能批**
- 群聊更明显：群里任何白名单成员都能 `/delegate` 发起委派，
  但点批准那张卡**只认排序第一的那个人**

也就是说 `requested_by` / `may_be_answered_by` / `_same_person` 这套机制
**在跑、也在被测，但它与「发起人」毫无关系** —— 退化成了「白名单第一人」。

> **三处过头的安全声明，到这里齐了。**
>
> | | 声明 | 实际 |
> |---|---|---|
> | 1 | 「配置隔离」 | **半做**（漏了 `HOME`）—— 但确实隔了配置 |
> | 2 | 「物理隔离」 | **修辞过头** —— 但四道闸门在代码层，是真的 |
> | 3 | 「只有发起人能批」 | **机制真、取值假** —— 判定对，喂进去的值与发起人无关 |
>
> 前两处的修法是「把话说准」。这一处**不能靠改措辞解决** ——
> 得先把发起人接进来。改之前**先在文档里标出来**：
> 一个写着「只有发起人能批」而实际相反的文档，比没有这条规则更危险，
> 因为**它让人不必再查**。

##### TTL 只能算一次（踩过的坑，规范性）

卡上写的 TTL 与实际等待时长**必须来自同一次计算**。踩过的坑（真机端到端
跑出来的）：`ApprovalPolicy.for_context()` 要的是**场景名**，而我传进去的是
`ApprovalContext` **对象** —— 于是落到「认不出的场景一律最严」的分支，
TTL 变成 **0**，卡上写着「0s 内有效」。

更糟的是第二处：`store.wait()` 不查 pending 的真实过期时间，用**自己默认的
600 秒**。于是出现「卡上 0 秒、实际等了 10 分钟」这种**自相矛盾**的表现。

> 用户是**按卡上那个时间**做决定的（11.9.4 同一条纪律）。
> 所以 `_ask_one_tool()` 里 `policy = context.policy` 算一次，
> 卡上文案与 `wait(timeout_seconds=…)` **都用它**。
> 回归测试 `TestTtlIsOneNumber` 断言两者**相等**且**为正** ——
> 只断言「不报错」的话，0 秒那种 bug 照样漏过去。

##### 真机验收的执行顺序（踩过的坑，规范性）

接线做完后要**真机点一次**才算数（静态测试证明的是协议形状对，
不是「飞书会把按钮 `value` 原样带回」）。这一步有个**顺序**要求：

> **桥接必须先就绪，再发卡。** 点击走飞书事件 → 必须有长连接在听 →
> 才会写进 `pending_approvals`。**没起桥接就发卡，点击必然落空**，
> 飞书给用户显示的是 `code 200671` / `processor not found` ——
> 那是「**没人接**」，不是「处理出错」，两者含义完全不同，
> 排查方向也完全不同。

踩过的坑：我发完卡才想起来起桥接，于是第一次点击白点。

**就绪判据用日志里的 `connected to wss://…`，不是端口。** 单实例守卫
（`FEISHU_LOCK_PORT`，默认 8771）用的是**锁文件**、不是常驻监听端口 ——
拿「端口在监听」当就绪信号会拿到**假阴性**，于是把一张明明能用的卡压着不发。

##### `/session/status` **不能**单独判「这轮结束了」（实测纠正）

一度以为「轮询 `/session/status` 就能判忙闲，不必解析 SSE 帧」——
**这个想法是错的**，实测把它否掉了：

| 时刻 | `/session/status` | 实际发生什么 |
|---|---|---|
| t=24.5s 起 20 次轮询 | 一直是 `{"type":"busy"}` | agent **卡在 `permission.asked` 等人批** |

也就是说 `busy` **同时表示「在思考」与「在等人」**，而这两件事需要的
处置**完全相反**：前者别打扰，后者**必须**去处理。

所以判「卡住了」要**两个信号组合**：SSE 收到 `permission.asked`
（人被打断）**或** `session.status` 转 `idle`（这轮结束）。
单看任何一个都会误判。

> 这也说明 Orca 那套 `tui-idle` 的复杂度（5 级证据排序、静默窗口、
> 轮询与超时）**不是白长的** —— 它们要驱动 40+ 种通用 CLI，
> 其中很多没有状态端点，只能靠推断。**opencode 有状态端点，
> 但状态端点单独不够。**

##### 两个授权答复端点，**键名相反**（实测，规范性）

V1 有**两个**能回答授权请求的端点，而它们要的键**不一样**：

| 端点 | 要求的键 | 载荷值 | 官方文档 |
|---|---|---|---|
| `POST /permission/{requestID}/reply` | **`reply`** | `once` / `reject` / `always` | ❌ 未列 |
| `POST /session/{sessionID}/permissions/{permissionID}` | **`response`** | `once` / `reject` / `always` | ✅ 已列 |

交叉组合一律 `400`：

| 发出去的 | 结果 |
|---|---|
| `/session/…/permissions/{id}` + `{"reply":"once"}` | `400 Missing key at ["response"]` |
| `/permission/{id}/reply` + `{"response":"once"}` | `400 Missing key at ["reply"]` |
| 任意端点 + `{"response":"deny"}` | `400 Expected "once" \| "always" \| "reject"` |

> ⚠️ **这是个真陷阱**：**官方文档只写了第二个**（带 `response` 的那个）。
> 而本项目走的是**第一个**（`/permission/{id}/reply` + `{"reply":…}`）——
> 两者都是对的，**但配错就是 400**。
> 将来若有人「照官方文档改成 `/session/…`」，**必须连键名一起改成 `response`**，
> 只换端点会直接坏掉。
>
> 这也解释了为什么**本项目那行注释是对的**：
> `_v1_build_reply` 写着「`{"action":…}` → `400 Missing key ["reply"]`」，
> 那是**对着本项目实际使用的端点**测出来的，与上表第二行吻合。
> ——一度以为那条注释是误记（因为官方文档说 `response`），实测证明它准。

**载荷值只有三个**：`once` / `reject` / `always`。**没有 `deny`** ——
本项目的本地词汇 `allow` / `deny` 由 `build_reply` 翻成 `once` / `reject`
（这层翻译正是适配器存在的理由之一）。

**两个方向都已在真机验过**（V1.11，隔离实例 + 真模型）：

| 发出的 | HTTP | `permission.replied` | 文件 |
|---|---|---|---|
| `{"reply":"once"}` | 200 | 1 次 | **真被改了** ✅ |
| `{"reply":"reject"}` | 200 | 1 次 | **没动** ✅ |

判据是**文件有没有真变**，不是「服务返回 200」—— 200 只说明形状被接受，
不说明结论被执行了。

> `always` 实测也能发（200，文件被改），但**刻意不映射**到它：
> 那是会话级授权，而本项目明确不做永久授权（11.9.7），
> 半年后它会变成绕过闸门的后门。

##### `Gate.check()` 返回 `None` 才是放行（踩过的坑，规范性）

闸门协议是**「有什么理由拒绝吗」**，不是「结论是什么」：

```python
refusal = gate.check(task_id=..., project=..., brief=...)
if refusal is not None:        # 有理由 = 拒绝
    ... summary=f"闸门拒绝（{refusal}）：未执行"
```

我第一版返回 `"allow"`，结果被打印成「闸门拒绝（allow）：未执行」——
**我自己的 Gate 写错了，代码没错**。这个命名极容易反过来读，
所以写在这里：写替身时返回 `None`，别返回 `"allow"`。

另外两条实测结论（都不是 bug，是必须知道的）：

- **`gate=None` 时一条都不派**，报「没有闸门，拒绝派发：委派会执行代码，
  必须先有人批准」。这是**故意的安全底**（`test_no_gate_means_no_run` 锁着）。
- **委派必须显式指定 `*-free` 那批模型**。`model` 留空会用 opencode 默认，
  而默认走 `https://opencode.ai/zen` 的**付费**模型，余额不足直接
  `402 Insufficient account funds`。实测撞过一次，114 秒白跑。
  这条 11.8 早就记着，实测再次确认。

##### 「提问」在 V1 上完全可行（实测，V1.14 —— **推翻了 V1.13 的结论**）

V1.13 这里写过「插话在 V1 上无解」，**那是错的**：把**两件不同的事**混成一件。

| | 谁问 | 答复落在哪 | 污染主线？ | V1 |
| --- | --- | --- | --- | --- |
| `/btw` 旁支提问 | **FreeAgent 打断 agent** | 新 user 轮次 | 会 | ❌ 无解 |
| **agent 卡住提问** | **agent 问，用户答** | **挂起的 tool 调用** | **不会** | ✅ **可行** |

`session.generate` 那个限制**只挡第一种**。第二种实测成立。

**实测闭环**（真 opencode 1.18.31 + 隔离实例，全程 9.2 秒）：

```
t=6.7s  question.asked      agent 问「结果写到哪个文件？请给完整路径」
t=7.2s  question completed  答复 {"answers":[["<绝对路径>"]]} -> 200 true
t=8.8s  permission.asked   agent 要写文件，闸门问的是 **edit**
        放行 edit
t=9.2s  out.md 落地，内容 '1\n2\n3\n'；write completed / session.idle
```

答案附在那个 `question` tool 调用上（`status: completed`），
agent 收到后开的是**新 assistant 轮**而非新 user 轮 —— 所以**不污染主线**。

**载荷：`answers` 是嵌套数组**

```json
QuestionAnswer = { "type": "array", "items": { "type": "string" } }
→ {"answers": [["out.md"]]}    一次 request 可含多个问题，每个答案又是字符串列表
```

> 我为这个形状猜了**四轮**（字符串、对象、`{question,answer}`、6 键一把梭），全被 400。
> 错法都一样：zod 报「Expected QuestionAnswer」时，我把那个名字当成「一个叫这名的标量」，
> 于是连续枚举**一维**形状。**正确做法是读 spec**，而 `/doc` 一直在那儿（162 条路径）。
>
> 教训记下来：**zod 报的 `Expected X` 里的 X 是该位置的完整形状，不是「一个叫 X 的东西」。**
>
> 顺带纠正一个我自己的测量错误：某个探针打印「`/doc` 共 6 条路径」—— 那是 **OpenAPI 顶层键**数
> （`openapi`/`info`/`paths`/`components`…），spec 一直是 162 条，没残缺。

**另外两条实测**：

- **`write` 工具的权限名是 `edit`**，不是 `write`。按 `write` 配规则会漏。
- **本地词汇 ≠ 线上词汇**：`reply_permission` 收 `allow`/`deny`，
  由适配器翻成 `once`/`reject`（且**刻意不映射 `always`** —— 会话级永久授权，11.9.7 不做）。
  传 `always` 会得 `未知结论：'always'`。

**V1.18.31 已经带了 V2 的 question 端点**（`operationId: v2.session.question.reply`，
body 为 `QuestionV2Reply`，元素类型是 `QuestionV2Answer` **对象**而非字符串）。
我打过去吃 400。记这条是因为：**将来若迁 V2，不必等升版** —— 但那是另一件事，
且本项目明确不迁（11.8.1 版本闸门拒非 V1）。

##### 「FreeAgent 主动插话」在 V1 上无解（实测，V1.14 —— 这条限制仍成立）

| 方式 | 带上下文？ | 证据 |
| --- | --- | --- |
| 同会话（对照） | ✅ 继承 | 自造标识符 `zephyrium-7749` 答得出 |
| 子会话 `POST /session {parentID}` | ❌ **不继承** | 模型原话「当前会话里这是你的第一条消息」 |
| `POST /session/{id}/fork` | ❌ **不继承** | 模型原话「这个对话里没有可用的历史记录」 |

`parentID` 只是**组织归属**（`/children` 能列出来），**不是上下文链**。

CodeNomad 的 `/btw` 靠 `session.generate` —— **V1 没有这个端点**
（唯一含 `generate` 的 `/experimental/project/{id}/copy/generate-name` 是项目改名，无关）。

所以：想让 FreeAgent **主动**打断 agent 问一句，V1 做不到。**这条是真空缺**，
而 agent 提问（上一节）不受影响。

##### 「配置隔离」原本漏了 `HOME`（V1.14 修 —— **比今晚那些键名陷阱更值得记**）

11.8.1 一直写着「配置隔离：只写临时 `XDG_CONFIG_HOME`，绝不碰用户的
`~/.config/opencode/opencode.jsonc`」。**那句话是不完整的。**

opencode 解析配置走 `os.homedir()`，而旧代码**只改了 `XDG_CONFIG_HOME`、
没改 `HOME`** —— 于是它一直在读**真实的** `~/.config/opencode/`。

实测证据：改之前委派用的是 `deepseek/deepseek-v4-pro`，而那台机器的
**环境变量里一个凭据都没有**（父环境是全量继承的，所以凭据只能来自
某个文件）—— 结论只能是：provider 配置是从那个目录读来的。

**所以「已隔离」这个说法当时是假的。** 委派出去的 opencode 能读到
用户**所有 provider 的配置与 key**，而它的设计意图恰恰是「碰不到」。
这比「环境变量泄漏」更严重 —— 因为那一项**是被声明为已解决的**。

修法与本节其它隔离项一致：`HOME` / `USERPROFILE` / `APPDATA` /
`LOCALAPPDATA` / `XDG_CONFIG_HOME` / `XDG_DATA_HOME` / `XDG_CACHE_HOME` /
`XDG_STATE_HOME` / `TMPDIR` / `TEMP` / `TMP` **全部**指向一次性 jail 目录，
随 `close()` 一起删。

**代价（产品决策，已定：选 A 完全隔离）**：委派**不再继承**你的 provider
配置。所以「用哪个模型」必须**显式** `--model`，否则由 opencode 自己挑
（实测会落到 `opencode/big-pickle`）。这是**有意的** —— 让「委派用哪个模型」
成为显式声明，而不是「继承你机器上碰巧配了什么」。

**配套新增一条记录**：产物正文写一行 `<!-- 模型：provider/model -->`。
理由是一个实测教训：加完白名单之后委派从 `deepseek/deepseek-v4-pro`
**悄悄**换成了 `opencode/big-pickle`，而产物里**一个字都没留**。

两条细节：

- 取**第一个**带 model 的事件（回答「它是怎么开跑的」）。第一版写成
  无条件覆盖，拿到的是最后一个 —— 与注释矛盾，被回归测试对出来。
- 缺一半的模型名（只有 `modelID` 没有 `providerID`）**宁可留空也不拼**：
  缺一半比没有更坏，看起来像真的。

##### 子进程环境是白名单，不是继承（V1.14）

旧代码 `env = dict(os.environ)`。参照 `D:\GitHub\qm` 的 `cleanEnv` 改成
**从零构造的白名单**：

| | 改前 | 改后 |
| --- | --- | --- |
| 子进程可见变量数（本机实测） | **77** | **22** |
| 凭据类 | 全部继承 | **仅模型凭据** |
| 家目录 / 配置 / 缓存 / 临时 | 真实家目录 | **全部指向 jail** |
| `PATH` | 继承 | 系统目录 + opencode 所在目录 |
| 监听地址 | 靠默认 | 显式 `--hostname 127.0.0.1` |

**OS 必需变量必须放行** —— `SYSTEMROOT` 缺了 Winsock 都初始化不了，
监听端口直接失败。那是「**不工作**」而不是「不安全」的问题，
两者不能混进同一张名单。`COMSPEC` / `PATHEXT` 同理（bash 工具起子进程要用）。

**模型凭据也必须放行**：`build_isolated_config` 只写 permission 配置，
**不写 provider 也不写 key** —— 凭据唯一的来路就是继承的环境。
一刀切会让委派直接 401/402。但**只放行这一类**：`GITHUB_TOKEN`、
`AWS_*`、`SSH_AUTH_SOCK` 这些与「调模型」无关的**一律不传**。

> **不借鉴 qm 的两处**：它把真实 provider key 塞进 opencode 配置
> （key 隔离这项 FreeAgent 更严）；它 `question: false` 把提问工具整个关掉
> （与「中间可以交互」的需求正好相反）。

##### 过程流是**可选开关，默认关**（产品决策，V1.14）

需求方明确：**不要实时看每一步**。所以过程流**不是不做，是做成开关**。

开与关的差别**不是「打不打日志」**，而是**必须先过滤**。一轮 414 条事件的实测分布：

| 类别 | 条数 | 占比 | 处理 |
| --- | --- | --- | --- |
| `message.part.delta` | **298** | **72%** | **增量片段，要累加** |
| `plugin.added` | 45 | 11% | **纯噪声，丢** |
| `message.part.updated` | 19 | 5% | **整块全文，要覆盖** |
| `server.heartbeat` | 6 | 1% | 纯噪声，丢 |
| `session.status` | 8 | 2% | busy→idle，收 |
| 其余（`tool`/`text`/`reasoning`/`step-*`/`file.*`） | ~38 | 9% | 收 |
| **真正有信息** | **~20** | **5%** | |

**开关打开时必须自带这个过滤器**，否则用户看到的是 19 倍重复的垃圾 ——
`message.part.updated` 是整块全文，拿它去累加（而不是覆盖），
同一段文字一轮会重复 19 次。**这正是 Doubao 那个项目的 bug**
（`dispatcher.py` 忽略 delta、累加 updated）。

| 开关 | 行为 |
| --- | --- |
| **关（默认）** | 只收最终结果：产物 + 摘要 + 推送回飞书。零流式开销 |
| **开** | 事件流经上述过滤后逐步推给飞书 |

**完成信号只有一个权威**：`session.idle`。
`session.status` 转 `idle` 次之；`/session/status` 里该 session 键消失**有歧义**
（「不在忙」与「不存在」同形），不作判据。

##### 交互要求执行器**全程存活**——而现状不满足（V1.14）

这是「遇到问题可以交互」在实现上**真正缺的东西**，比协议形状重要得多。

**架构现状：桥接与 opencode 之间没有连接。**

- 桥接只连**飞书**与 **FreeAgent 库**（`FEISHU_BRIDGE_URL` 那条是 opencode→桥接，反向）
- opencode 由**执行器进程**驱动（设计文档断点 3：独立进程；隔离的性质见 11.8.1「信任边界」—— 闸门在代码层，拆分给的是纵深防御）

于是提问 / 授权的真实链路是**绕**的：

```
opencode 提问（或 permission.asked）
  → 执行器（SSE 订阅）
  → 落库 pending（question / approval）
  → 桥接读库 → 发飞书
  → 人回复 / 点卡
  → 桥接落库 answer
  → 执行器读走 → 送回 opencode（会话仍开着）
```

**推论：执行器必须全程活着阻塞等答复。** 而现状是：

| 执行器形态 | 现状 | 问题 |
| --- | --- | --- |
| `run_once` | **一次性，跑完就退** | 答复只从飞书来，退了没人送 —— 交互**必然断** |
| `--watch` | 每 N 秒扫一轮就返回 | 轮询间隙答复无人取；agent 挂起时**空转刷日志** |

两处都要改：等待期间**阻塞在库上**（而不是轮询），
并且**由答复唤醒**（而不是靠固定间隔）。

> ⚠️ 这条与 11.8 刚修的「确定性失败不重派」有张力：那条让**派发前被拒**不再自动重试，
> 理由是「不改配置就永远不会成功」。但**等待答复**不是那种失败 ——
> 它是**正常流程的一部分**，且会有人工答复把它解除。所以阻塞等待**必须**与
> 「确定性失败」区分开，不能共用同一条「不重派」判据，否则**等待答复会被当成拒绝**。

##### 信任边界：那句「物理隔离」说过头了（V1.15 更正）

11.8.1 一直写「执行器…不接受任何外部消息。这样「远程输入」与「本地代码执行」
之间有一道**物理隔离**」。**那句话不准确** —— 实测把它推翻了：

| 该由谁挡 | 实际在哪 |
| --- | --- |
| `/start` 门 + 尚未派过 | `services/delegate.py` 的 `eligible_tasks`（docstring 自称「**闸门在这里，而且只有在这里**」）|
| 项目白名单（留空 = 委派关闭）| `check_project_allowed`（服务层，CLI 建委派与执行器取任务**各调一次**）|
| 逐次授权 | `ApprovalStore` |
| ✅ 「只有发起人能批」 | 机制在 `ApprovalStore`，**发起人从 `tasks.delegate_requested_by` 进来**（V1.17），见下 |

**四道闸门全是函数，不是拓扑。** 所以合并进程**一道都绕不过去** ——
调用方无论在哪个进程里，都得先过 `eligible_tasks`。

进程拆分提供的是**纵深防御**：防的是「将来有人写了一条不经 `eligible_tasks`
就去调 opencode 的路」。它有价值，但**不是**结构性保证。

> 这是本项目**第二处**过头的安全声明。第一处是「配置隔离」只做了一半
> （只改 `XDG_CONFIG_HOME`、漏了 `HOME`，见上一节）。
> 同一把尺用两次，教训是同一句：**安全声明要写成它真正成立的范围** ——
> 宁可窄到偏严，也别宽到让人不必再查。

##### 架构判据：不是进程数，是「有没有时间差」

这一条我先后说错过两次，都记下来：

1. 第一次说「三份外部项目是 opencode 插件，所以与 opencode 同进程，
   所以内存 `Map` 可用」—— **错了**。实测 `opencode-serve-manager.ts` 里是
   `spawn(command, ['serve', '--port', ...])`：它们也把 opencode 起成子进程、
   HTTP 通信，和本项目的执行器**一样**。
2. 第二次说「有时间差 → 必须持久通道 → 所以必须拆进程」——
   **后半句不成立**。doubao 就是一个进程里桥接时间差的
   （任务队列 + SQLite 存交互 + `answer_event` 唤醒）。

**真正的要求是「持久通道」，不是「另一个进程」。** 判据是这一条：

> **听见人说话的那个组件，是不是就是驱动 opencode 的那个组件。**

| | 听见人的 | 驱动 opencode | 内存 `Map` |
| --- | --- | --- | --- |
| opencode-feishu / opencode-bridge | bridge | **同一个 bridge** | ✅ |
| doubao | 同一个 agent 进程 | 同上 | ✅（但落 SQLite）|
| **本项目** | **bridge** | **executor** | ❌ |

为什么它们不需要跨进程：那些是**活聊天** —— 人就在飞书上跟 agent 对话，
**没有「等答复」这个阶段**。所以状态放内存不是选择，
是**题面里根本没有那道题**。

而本项目的委派是**脱离的**：你发一条就走，agent 跑十几分钟，
中途可能卡住一小时等你答。**有时间差，就必须有撑过这段时间的状态。**

##### 拆开还是合并：取舍，不是「做不到」

**必须说清：本项目技术上完全可以做成 doubao 那个形态**（一个进程、SQLite 桥接）。
合并不是做不到，是**要拿下面第一行换第二行**。

| | 拆开（现状） | 合并成单进程 |
| --- | --- | --- |
| **交互中桥接重启** | ✅ **答复仍然生效** —— 答复落在库里，执行器还在等 | ❌ **正在跑的委派直接死掉** |
| 常驻机制 | ❌ 要为执行器建第二套（锁 / 监督 / 状态 / 重启）| ✅ 桥接已在，不用新建 |
| 纵深防御 | ✅ 多一道 | ❌ 少一道（**四道闸门仍在**）|
| 审计 | 审批 / 答复天然在库里 | **仍要在库里**（「谁批的必须查得到」是设计要求）|

**选拆开的理由不是「物理隔离」**（已更正，见上），而是**重启隔离** ——
而它恰恰是为「中间可以交互」这个需求存在的：你在飞书回答一个卡住的 agent，
此刻桥接重启的概率不为零，而那时你已经把答案发出去了。
合并的话那一轮白等。

代价是执行器必须常驻化 —— 那正是本节「交互要求执行器全程存活」那条缺口，
**本来就该做**。而 V1.15 建好的那层（`question_spec` + `wait_complete`）
是**持久通道**，两种形态都用得上，不作废。

##### 新增的信任面：agent 提问、人回答（V1.15）

按上面那句「执行器不接受任何外部消息」的**字面**读，下面这件事越界了：

**一条飞书消息现在能影响一个正在运行的 opencode 会话。**

它是有界的，但边界必须**写下来**，而不是靠「反正有凭据兜着」：

- 凭据由**执行器自己签发**，只对它**自己登记的那一条提问**有效
- 只接受**文本** —— 不接受指令，也不接受授权
- 任何**动作**仍然要过 `edit: ask` 闸门，而闸门是代码层的，合并也绕不过

所以那句「不接受任何外部消息」应收窄为：

> 执行器**不接受任何外部消息作为指令** —— 命令、任务、授权都只能经由它
> **自己签发的凭据**进入。但它**会接受对「它自己提出的问题」的文本答复**。

##### V1 默认 `allow` vs V2 默认 `ask`：失效方向相反（规范性，V1.13）

本项目的闸门**全靠往隔离实例写一份显式 `opencode.json`**（`edit: ask`、
`bash: ask`、`external_directory: deny`）。于是**配置写错**时的后果
完全取决于该版本的默认值：

| | 未命中规则时 | 配置写错的后果 |
| --- | --- | --- |
| **V1** | 大多默认 **`allow`** | 字段被静默忽略 → 全部落回 allow → **裸奔** |
| **V2** | 默认 **`ask`** | 字段被静默忽略 → 落回 ask → **停下来问人** |

**V1 的默认值本身就是危险的那一侧。** 而「配错就停」正是本项目全部闸门的
出发点 —— 也就是说 11.8.1 那道版本闸门在防止的失败模式，**恰好就是 V1 的常态**。

> 这条**不是**说「该升 V2」，而是补上版本陷阱表一直缺的一格：
> 现有表格只说了「V2 未验证所以拒绝」，**没说「V1 的默认值有多危险」**。
> 不写这一格，下一个人做常驻执行器时会以为「配错顶多不生效」——
> 而实际是**配错就裸奔**。
>
> ⚠️ V2 那侧来自官方文档与 11.8.1 已记的版本陷阱表，**我没有真机验过**。
> 要据此决策必须先对着一个真实 V2 实例量（`/doc` 拿 `permissions` 数组
> 元素形状、事件名是否仍与 V1 同形 —— Orca 同时有 `src/main/opencode/` 与
> `src/main/opencode2/` **两套注入插件**，说明 V2 事件形状确有不同）。

  规则看起来对了而真机上人点不动自己的卡

##### 版本断言（已实现，规范性）

V1/V2 字段名全变，而旧字段被**静默忽略** —— 不报错，闸门随之失效，
失效方向恰好是默认 `allow`。所以 `delegate.main()` 在**派发之前**查一次
`opencode --version` 的主版本，不认识就**拒绝派发**（退出码 2），不警告后照跑。

- `SUPPORTED_OPENCODE_MAJOR = 1`，改动它等于承认「已按新版本重新接缝」
- `parse_major_version()` 是**纯函数**（不做 IO）—— 版本解析能被测的前提
- 探不到版本（`None`）与版本不对**同等拒绝**：两者都意味着「不知道在跟什么说话」
- `--dry-run` **也过这一关**：预演的意义之一就是「接缝在真环境成不成立」
- 解析只认**带点号**的版本串（`1.18.31` / `2.0.6`）。裸数字更可能是
  构建号、工具数或日期 —— 把它当版本会得到一个「看起来确定但全错」的主版本。
  但**形状对不等于语义对**（`2026.09` 会解析成 2026），所以真正的保证是
  `version_mismatch_reason()` 那一关，不是正则本身
- 回归测试：`tests/test_delegate_version.py`（含**控制组**：V1 必须放行，
  防「永远拒绝」这种过度拒守）

**接缝：`opencode serve` + 官方 REST。** 认证是 HTTP Basic
（`OPENCODE_SERVER_USERNAME` / `OPENCODE_SERVER_PASSWORD`），端点与载荷
取自服务自身的 OpenAPI（`GET /doc`，OpenAPI 3.1.0）。

| 步骤 | 端点 | 说明 |
|---|---|---|
| 拉起服务 | `opencode serve --port <p>` | 独立进程，`XDG_CONFIG_HOME` 隔离 |
| 建会话 | `POST /session` | 拿到 `sessionID` |
| 发指令 | `POST /session/{id}/prompt_async` | 立即返回，不等完成 |
| 收事件 | `GET /event` | SSE，长轮询 |
| 列出挂起 | `GET /permission` | 恢复现场用（进程重启后） |
| 回答 | `POST /permission/{requestID}/reply` | **必须带对象载荷** |

**权限配置在启动前写文件，不走 `PATCH`** —— 隔离目录里的
`opencode.json` 写好即可。少一次往返，也少踩「PATCH 返回 200 但没落盘」
那个坑（实测踩过）。`opencode_server.delegation_permission_config()` 是
**唯一**生成它的地方，且它的**键序有意义**（deny 必须在最后，见下）。

> **拉服务的坑（实测，规范性）：`terminate()` 杀不掉服务。**
>
> Windows 上 `shutil.which("opencode")` 解析到 npm 装的 `opencode.CMD` ——
> 那是**批处理包装器**。`Popen(...).terminate()` 终止的是包装器，
> 包装器启动的**原生 `opencode.exe` 子进程不会被连带杀掉**，继续占着端口与内存。
> 实测 14 次探针各漏一个服务，累计约 **12.5 GB**。
>
> 所以接线时**必须用进程组 / Windows Job Object 收口**，不能只 terminate 父进程；
> 且启动后要**验端口真的在监听**（返回 200 才算起来），
> 停止后要**验端口真的空了**。理由与 `resolve_command()` 里那条
> `PATHEXT` 坑同源：Windows 上「命令」与「进程」不是一一对应。

##### 配置隔离（实测，规范性）

派发用**独立的 opencode 服务**，且**绝不能用 `PATCH /global/config` 写用户配置** ——
那会落盘改 `~/.config/opencode/opencode.jsonc`（实测踩过：把 `edit`/`bash`
写成了 `ask`）。委派是**无人值守**的，绝不能改用户自己的环境。

两种隔离机制实测对比：

| 机制 | 语义 | 实测结果 | 采用 |
|---|---|---|---|
| `OPENCODE_CONFIG` | **与用户配置合并** | 未指定的键**沿用用户的**（实测漏进 `webfetch: allow`） | ✗ |
| **`XDG_CONFIG_HOME`** | **完全替换** | 只读到隔离文件的内容 | ✅ |

**合并语义是 fail-open 的**：我们只设 `edit: ask` 时，用户配置里的
`bash: allow` 会原样生效。所以必须用 `XDG_CONFIG_HOME` 指向一次性目录。

**顺带的好处**：实测隔离环境下 `plugin` 为 `[]`、`instructions` 为 `null` ——
用户装的 `opencode-vibeguard`、`oh-my-openagent` 等**不会漏进来**。
无人值守场景下攻击面更小，这是**优点不是代价**（代价是隔离环境里的 agent
不认识用户的自定义指令，委派简报必须自足 —— 这与「简报必须单行」是同一条纪律）。

**配置直接写文件、不走 PATCH**：隔离目录里的 `opencode.json` 在**服务启动前**
写好即可，没必要启动后再 `PATCH`。少一次往返，也少一个「PATCH 返回 200
但没落盘」的坑（实测踩过）。

**动作与三态**：`PermissionAction` 是 `["allow","deny","ask"]`。按工具分键
（`read` / `edit` / `glob` / `grep` / `bash` / `task` / `skill` / `lsp` /
`question` / `webfetch` / `websearch` / `external_directory` / `doom_loop`），
`PermissionConfig` 也可按工具入参再分（`PermissionObjectConfig`）。
要人确认的设 `ask`，**永不越界的设 `deny`**。

> **版本陷阱（规范性）**：本节全部字段名对应 **V1**（实测 `opencode 1.18.31`）。
> 官网现已主推 **V2（`/v2/docs`，2.0.6）**，其 permission 模型**字段名全变**：
>
> | | V1（本机实测） | V2（官网主推） |
> |---|---|---|
> | 规则容器 | `permission`（**对象**） | `permissions`（**有序数组**） |
> | shell 动作名 | `bash` | `shell` |
> | 子代理动作名 | `task` | `subagent` |
> | 规则形态 | `{ "*": "ask", "git *": "allow" }` | `[{action,resource,effect}]` |
> | `always` 语义 | **仅本会话** | **持久、项目级** |
> | 未命中时 | 大多默认 `allow` | 默认 `ask` |
>
> 官网 V2 文档有明确 warning：*"V1 uses different field and action names."*
> **升级 opencode 时本节必须整体重写**，否则配置会静默失效。
> 判定当前主版本：`opencode --version` 看第一位，并以服务自报的
> `GET /doc → info` 交叉确认。

**规则求值顺序（规范性，官方原文）**：*"Rules are evaluated by pattern match,
with the **last matching rule winning**."* 惯例是通配 `"*"` 放最前、具体规则放后面。

委派用的配置（`delegation_permission_config()`，键序即安全属性）：

```jsonc
"permission": {
  "*": "allow",                // 底子：read/grep/glob 是干活必需的
  "edit": "ask",               // 改文件 —— 闸门真正要拦的
  "bash": "ask",               // 跑命令，与 edit 同级
  "webfetch": "ask",           // 出网
  "websearch": "ask",
  "task": "deny",              // 不让 agent 拉子代理（与分层一致）
  "external_directory": "deny" // 永不越界 —— 必须放最后
}
```

**为什么 `read`/`grep`/`glob` 不设 `ask`**：全设 ask 会让 agent 一直问、
卡片刷屏，**问到最后就是无脑点** —— 那比不设更糟。要拦的是
「有副作用、且看得出后果」的动作。

> ⚠️ **deny 必须放最后。** 早先本节误抄了 QM 的「deny 前置、永不被覆盖」——
> **方向是反的**。QM 与 opencode 是两套独立引擎，QM 前置是因为它自己
> 先求值；opencode 是**后置覆盖**，deny 写在中间会被后面的 allow 覆盖掉。
> 配错顺序的后果是**静默开洞**，且没有任何报错。

**`external_directory` 是独立护栏，且默认 `ask`**（官方 V1 默认策略）。
它先于该路径的 `read` / `edit` 判定。所以「项目白名单」这一道闸门
（11.8 第 1 条）**必须同时落在 FreeAgent 侧与 opencode 侧**：
FreeAgent 拒相对路径，opencode 拒越界。两侧都拒，才叫闸门；
只拒一侧，另一侧仍会放行。

**shell 的官方警告（影响取舍）**：*"`shell` runs with the host user's
filesystem, process, and network authority. Directory inference from command
text is best effort, so prefer a **narrow shell allowlist** instead of patterns
intended to recognize every dangerous command."*

即：**不要试图用规则枚举所有危险命令**（blacklist 思路），要用**窄白名单**。
另：实验性 `portable_shell_scanner` 官方明说解析不了的命令
*"returns a scanner error, **not a permission denial**"* ——
**解析失败 ≠ 被拦住**，不能拿它当唯一防线。

**挂起事件的载荷足以渲染成卡片**（实测原样）：

```json
{ "id": "per_…", "sessionID": "ses_…",
  "permission": "edit",
  "patterns": ["…\\ANSWER.txt"],
  "metadata": { "filepath": "…\\ANSWER.txt", "diff": "Index: …\n+42" },
  "always": ["*"],
  "tool": { "messageID": "msg_…", "callID": "call_…" } }
```

`metadata.diff` 直接可读，**审批时能看到它到底想改什么**。

**回答载荷必须是对象**，裸字符串会被拒（实测 `400 Expected object`）：

```json
{"reply": "once" | "always" | "reject", "message": "可选说明"}
```

三态语义（**V1 官方原文**）：

| 选择 | `reply` | 实际效果 |
|---|---|---|
| 允许一次 | `once` | 只批准**当前这一条**请求 |
| 本会话允许 | `always` | 批准**工具建议的匹配式**，**仅本 opencode 会话内** |
| 拒绝 | `reject` | 拒绝该请求 |

「工具建议的匹配式」由工具自己给（bash 通常建议命令前缀如 `git status*`），
所以 FreeAgent **不能自己编造** `always` 的范围 —— 必须原样展示
opencode 给的 `patterns`，让用户看到自己在批准什么。

⚠️ **V1 的 `always` 不是永久授权**，进程重启即失效。
FreeAgent 若要「记住这次允许」，得**自己落库**（`pending_approvals` 表已是这个形状），
在下次派发前重新配置 opencode。**不能依赖 opencode 侧持久化** —— 那是 V2 才有的能力。

`once` 之后执行器**继续跑**并落盘 —— 闭环实测成立。

**实测记录（2026-09-29）**：设 `edit: ask` 后跑「创建 ANSWER.txt」，
第 7 秒 `GET /permission` 出现挂起且文件**尚未**被创建（确认真的停住了），
回 `{"reply":"once"}` 后**第 1 秒**文件落盘、内容 `42`。
`--auto` 全程未传。

#### 11.8.2 为什么**不**用「不传 `--auto`」当闸门（**已纠正的错误**）

本节曾写「**刻意不传 `--auto`** —— 委派场景我们宁可它中途停下来」。
**这条是错的，实测已推翻。**

非交互 `subprocess` 下 opencode **不传 `--auto` 也全部自动放行**：

| 探针 | 结果 |
|---|---|
| 在项目目录内写文件 | 执行，**无授权事件** |
| 写到**项目目录外** | 执行，**无授权事件**，还自行 `read` 验证 |
| 事件流权限类关键词 | **零命中** |

根因不是「没有权限系统」，而是**默认 `allow` 加上已有配置**。当时
`external_directory` 正是 `allow` —— 越界写不是疏漏，是配置允许的。

**官方文档印证**：V1 文档明确 *"--auto automatically approve permission requests
that are **not explicitly denied**"*、*"Most permissions default to `allow`"*。
所以「不传 `--auto` 就安全」是把**默认值**当成了**保护**。

**方法论教训**：鉴权要先问「它自己怎么描述自己」（`GET /doc`），
不要猜 header 名。上一轮就是只试了 `Bearer`、而它实际是 Basic，全部 401，
差点误判成「服务端不支持」。

**更根本的教训**：探权限行为时，**默认配置 ≠ 安全配置**。
第一次探针能越界写，根因不是系统没护栏，而是**用户配置里
`external_directory: allow` 覆盖了默认的 `ask`**。
如果当时先读官方默认策略、或者先 dump 当前配置，就会立刻看出这个区别 ——
**「实测现象」和「实测配置」必须一起看，只看现象必然归错因**。

**另一条教训**：`PATCH` 返回 200 **不等于**写入成功，且 `PATCH` 是
**浅合并**（只覆盖给定键，不删除其它键）。必须**回读验证**，
且删键不能靠置 `null`（实测 `400 Expected PermissionRuleConfig`），
要落盘改配置文件再重启进程。

#### 11.8.3 授权规则的三条纪律（规范性，借鉴 QM）

`D:\GitHub\qm` 是同版本的 opencode 使用者，它把审批放在**自己的 core** 而非
harness 层。三条规则值得直接抄：

1. **规则求值方向必须与引擎一致** —— opencode 是**后置覆盖**，
   所以 `deny` **必须放最后**（见 11.8.1）。**不可照抄 QM 的「deny 前置」**：
   两套引擎求值方向相反，抄错会静默开洞。
2. **只有发起人能批** —— 审批不是「谁都能点」。他人批准等于授权越权。
   > ✅ **已达成**（V1.17）：发起人落 `tasks.delegate_requested_by`，待批行与卡片收件人统一用它。
   > 测试覆盖见 `tests/test_delegate_requester.py`；**真机点卡仍未验**。
   QM 原文：`"only the person who requested this command can approve or deny it"`。
3. **审批规则本身是攻击面** —— 若将来允许用户写自定义匹配式，
   需限长并拒绝歧义回溯（opencode V1 用**通配符**而非正则，本身无 ReDoS；
   但 QM 走正则路线，为此写了 160 余行回溯歧义分析）。**先确认目标引擎
   用什么匹配语法，再决定要不要这层防护** —— 不要为不存在的风险写防护。

QM 另有 `Always / session / 长期` 三档，与 opencode 的
`once / always / reject` 同构，**不需额外抽象**。但注意 V1 的 `always`
**仅本会话内**有效（官方原文 *for the rest of the current OpenCode session*），
重启后失效；V2 才有持久化的 `saved` 端点。**FreeAgent 不得把
「已 always」当作跨重启的授权**。

**关于规模**：QM 换掉了整个工具面（自建工具 + 桥回自己的服务），适合
「多人 × 多沙箱 × 多渠道」的公司形态。我们是单人事务助手，
**不抄这个形状**，只抄上面三条纪律。


### 11.9 远程通道（V1.2 新增）

把飞书/Lark 变成**又一个入口**，而不是又一个引擎。

**核心决定：不重写命令，包住终端那一套。** 消息经
`services/channel.py` 转进 `cli.Repl`（把 `out` 换成缓冲区），
于是 30 多个命令 handler 一份实现。业务规则只有一份 ——
否则两边迟早分叉，而分叉方向通常是**权限悄悄变大**。

| 层 | 依赖 | 职责 |
|---|---|---|
| `services/channel.py` | 零 | 白名单、事件去重、按会话保留追问状态 |
| `feishu/events.py` | 零 | 事件解析（纯函数，含 SDK 对象适配器） |
| `feishu/sender.py` | 零 | 发消息（stdlib `urllib`） |
| `feishu/bridge.py` | `lark-oapi` | 长连接握手、心跳、自动重连 |

**只有最后一行需要 SDK**，所以 `lark-oapi` 是可选 extra
（`pip install ".[feishu]"`），核心包 `dependencies` 依然为空。

**六条边界：**

1. **白名单失败关闭** —— `FEISHU_ALLOWED_USERS` 为空则**启动即报错退出**。
   和 `delegate.projects` 同一个原则：链路终点是本机执行，默认必须朝「关」。
2. **群里必须 @「这个 bot 本身」才响应** —— 不是「@ 了某个东西」就响应。
   判定依据是 bot 自己的 `open_id`，见 11.9.1。
3. **事件去重必须跨重启** —— 落盘，带 TTL 与条数上限，见 11.9.2。
4. **3 秒应答** —— 回调只做「解析 + 入队」立刻返回；执行在单工作线程里
   FIFO 串行做（保序，且避开 SQLite 连接非线程安全）。
5. **执行期授权由 11.8.1 承担** —— 飞书通道本身不新增闸门，也不放宽闸门；
   它只是把 11.8.1 的审批**呈现**成飞书卡片、**收回**点击结果。
   一份能力一份实现：闸门判定只在 `ApprovalPolicy` 一处。
6. **单实例** —— 同一台机器只允许一个桥接进程，见 11.9.3。

以上六条都是**规范性**的，`feishu/events.py`、`services/channel.py`、
`feishu/bridge.py` 严格照此实现，并由 `tests/test_feishu*.py` 逐条锁定。

**提醒由通道自己推，不靠消息顺带触发。** `reminders.check()` 是
**消费型**的（写 `REMINDER_FIRED` 且不重发）—— 靠用户发消息触发的话，
一条无关消息就会把提醒吞掉。通道按 `FEISHU_REMINDER_POLL_SECONDS`
轮询，**推给每个白名单用户的私聊**（不推群：提醒是私事）。

**闭环回推：** 从飞书发起的委派把 `Task.delegate_chat_id` 记成来源会话、
执行器跑完**主动把结果推回该会话**（见 11.8）。推送**在本地落库之后**做，
且失败只记日志 —— 通知渠道挂了不等于任务没做完；但通知通了也不等于
任务做完了，所以文案里必须写明「待你验收」。

#### 11.9.1 群聊 @ 门控：必须 @ bot 自己

飞书不在 `content` 里写「@某人」，而是留一个占位符（`@_user_1`），
并在 `event.message.mentions` 里给出该占位符对应的对象，其中含 `id.open_id`
与显示名 `name`。**所以「@ 的是谁」本来就是能判定的。**

原实现只判「`mentions` 非空」，于是群里的 `@张三 你看下这个` 也会触发 bot，
且占位符被剥掉后，bot 拿着一句残缺文本去做意图识别。这与边界 2 直接矛盾 ——
**本文是实现契约，所以矛盾方是实现，不是文档。**

**规范性决定：**

- 启动时探测 bot 自身的 `open_id`（`GET /open-apis/bot/v3/info`，用 tenant token），
  结果缓存到 `<FREEAGENT_HOME>/feishu_bot.json`。`doctor` 有一项专查它。
- 身份缓存的**规范性参数**：

  | 项 | 值 | 理由 |
  |---|---|---|
  | 缓存路径 | `<FREEAGENT_HOME>/feishu_bot.json` | 与数据库同目录，`--db` 换位置时跟着走 |
  | 缓存有效期 | `168` 小时（7 天） | `open_id` 对同一应用不变，长的有效期只是「万一探错还能自愈」的窗口，不是新鲜度要求 |
  | 存储形状 | `{"bot": {...}, "fetched_at": ...}` | **与 API 响应同构**，于是读缓存与读响应走同一个解析器 |
  | 写盘方式 | 临时文件 + `os.replace` | 断电或崩溃不留半截文件 |
  | 文件损坏 | 改名 `.corrupt` 留现场，以「无缓存」启动 | 缓存永远不该让人启动失败，但静默删掉会永远查不出根因 |
  | 文件过期 | **不算损坏**，不改名 | 过期只是「该重探一次」，是正常生命周期的一部分 |

  ⚠️ 「存储形状与响应同构」这条是被 bug 逼出来的：早期实现写的是扁平结构
  （`open_id` 在顶层），读时却调解析响应的那个函数 —— 于是**每写一次缓存，
  下次启动就把它当损坏文件改名留现场**，身份永远命中不了缓存，每次启动都
  重探一遍网络。「写一个形状、读另一个形状」在测试里极容易漏掉，因为写完
  立刻断言文件存在是过的，要等重启才暴露。
- 判定规则：
  - 私聊（`chat_type == p2p`）→ 一律视为被叫到。
  - 群聊 / 话题 → `mentions` 中**存在某个 `id.open_id` 等于 bot 自己的 `open_id`** 才算被叫到。
  - `mentions` 非空但**不含 bot** → **不响应**。这就是「@ 人，bot 不抢答」。
  - **`@all` / `@_all` 不算「@ bot」**（规范性）：飞书把「@所有人」也放在 `mentions`
    里，其 `key` 为 `@all` / `@_all`，`id.open_id` 为 `"all"` 或空串。
    规定它**不指向 bot**，不响应。
    之所以不必额外写过滤器：身份判定用的是 `id.open_id == bot_open_id` 的**精确比对**，
    而 `@all` 的 `open_id` 恒不等于 bot 的 `open_id`，所以它天然被挡住 ——
    已实测三种情形（`@all` 单独 → 拦住；`@all` 且 `open_id` 为空 → 拦住；
    `@all` + 真 @bot → 放行）。
    openclaw / hermes-agent 显式过滤 `@all` 是为了**别的**用途（提示语渲染、转发判定），
    不是因为比对会误判；本项目不做无用的过滤，只用测试把这个行为钉住，
    免得将来有人「优化」成按 `key` 匹配而引入误插话。
  - **富文本（`message_type == "post"`）目前是已知边界，不处理**（规范性）：
    本版本**只把 `message_type == "text"` 当成指令**。富文本消息在门控之前就被
    `Ignored` 拒掉，因此「在门控里回退解析 `tag` 节点」目前是**不可达代码**。
    记录于此是为了避免误判：将来若要支持富文本，门控**必须**同时改成两段式
    （先看 `mentions`；若为空/未命中且 `message_type == "post"`，再解析
    `content` 里的 `tag` 节点取出被 @ 的 `open_id`）。openclaw 与 hermes-agent
    两个独立实现都这么做，因为飞书富文本确实可能不带 `mentions` 数组。
    **只加回退而不加解析，等于什么都没做。**
- **不支持的消息类型要回一句提示，不能沉默**（规范性）：
  图片 / 文件 / 富文本等，`bot` **回一句「我只处理文字消息」然后就此打住**
  （不建事务、不进入派发逻辑）。
  理由同 12.x 的「禁止静默劣化」：用户发图片没反应，会以为「它收到了但不想理」，
  于是去查白名单、查 @ 门控、查网络 —— 而真正原因是**它压根不处理图片**。
  查错方向比不查更费时间。
  - **回复顺序是硬约束**（规范性），且**必须**在「白名单 → 群聊 @ 门控」**之后**：
    1. 先过**白名单**（11.9.4）：不在白名单内的发送者，**连提示都不回** ——
       回一句就等于向任意陌生人确认「这里有个 bot」，那正是白名单要挡的泄露面。
    2. 再过**群聊 @ 门控**（11.9.1）：群里没 @ bot 时**不提示**。否则群里任何人
       随手发张图，bot 就抢着说「我只处理文字」—— 那比沉默更糟，
       等于把「不抢答」这条规矩又破了一次。
    3. 私聊、或群里已 @ 到 bot → 回那一句提示。
  - 提示语要**带上实际收到的类型**（如「收到的是 `image`」），否则用户还得再问一次
    是什么没被处理。
- **占位符替换规则（规范性）**：剥掉的不只是 bot 自己那个 ——
  别人的占位符若只删不替，会把 `@张三` 这个语义主体从句子里抹掉。
  规定：bot 自己 → 删掉；他人 → 替换成 `name` 显示名；`name` 缺失时才退化为删掉
  （**绝不能把 `@_user_2` 这种占位符留在正文里**，它会污染意图识别）。
  处理完 `mentions` 之后还要**按形状兜底扫一遍**残留占位符：飞书正常情况下
  `mentions` 覆盖正文里全部占位符，但「文档说的」不等于「实测过的」，
  一旦对不上，残留占位符会原样进正文且**不留任何痕迹** —— 日志无异常、消息照发，
  只是答非所问。与其赌形状，不如清干净。
- 探测失败时：启动**显著告警**，门控置为**失败关闭**（群里带 @ 的消息一律忽略并记明原因），
  私聊不受影响。和边界 1 同源 —— 判不准的时候朝「关」偏。
- **探测失败要能自愈，不是失败到重启为止**（规范性）：
  「启动那一瞬网络抖了一下」不该让 bot 在群里失聪到下次重启。
  规定：探测失败时**起一个后台线程按退避重试**，探到即写回 `bot_open_id`，
  **群聊门控随之自动生效，不用重启、不用重新订阅**。

  | 项 | 值 | 理由 |
  |---|---|---|
  | 退避序列 | `60, 120, 300, 600, 900` 秒 | 取自 openclaw 的 `monitor.bot-identity.ts`（同为个人助手场景） |
  | 总时长 | 约 33 分钟后放弃 | 覆盖绝大多数瞬时故障（网络抖动、飞书临时 5xx） |
  | 等待方式 | `Event.wait(delay)` 而非 `sleep(delay)` | 桥接退出时被立刻唤醒，不必干等完整个退避周期 |
  | 线程属性 | daemon | 绝不阻止进程退出 |
  | 单次意外 | 记日志后继续下一次 | 一次 `NameError` 之类不该让整条重试白做 |
  | 用尽仍失败 | 保持失败关闭，**不退化成放行** | 判不准时朝「关」偏，与本节开头同源 |
  | 何时**不**起这个线程 | 启动就探到了 | 没得可重试，白挂一个线程只增加出错面 |

  **重试救不了配置错误**：Secret 填错、权限没开，重试多少次都一样。
  所以告警文案要指明「若每次都失败，跑 `doctor`」—— 否则用户会一直等重试，
  而真正该做的是改配置。这条比退避表本身更重要。
- **两种「群里不响应」必须能分开看**：@ 了别人（正常，用户本来就该去问那个人）
  与身份未知（配置问题，不修就一直不响应）。所以被拦下时日志/结构里要带上
  具体原因，且**身份未知那条必须指明私聊仍可用、该跑 `doctor`** ——
  否则用户对着沉默的 bot 无从判断是权限坏了还是身份没探到。
- `doctor` 有一项专查身份，且它**不是致命项**：私聊仍可用，标致命反而会让人
  以为整个通道都废了，更不好定位。

#### 11.9.2 事件去重：必须跨重启

原实现在**进程内**去重（`OrderedDict`，上限 512，无 TTL），并注明
「重启后忘掉是已知且可接受的」。**这个权衡在长连接重连场景下不成立：**
飞书重连时会重投近期事件，于是「重启 → 立刻重连 → 收到重投」恰好落在
「只会短时间内重投」的窗口内，而后果正是重复建事务 —— 也就是去重本身要防的那件事。
所以本节把去重提升为**必须跨重启**。

**规范性参数：**

| 项 | 值 | 理由 |
|---|---|---|
| 落盘路径 | `<FREEAGENT_HOME>/feishu_seen_events.json` | 与数据库同目录，`--db` 换位置时跟着走 |
| `DEDUP_TTL_HOURS` | `24` | 超过 24 小时的 `event_id` 不再视为可能重投 |
| `DEDUP_MAX_ENTRIES` | `2048` | 超上限按时间从旧到新剪 |
| 写盘方式 | 临时文件 + `os.replace` | 断电或崩溃不留半截文件 |
| 文件损坏 | 改名 `.corrupt` 留现场，以空表启动，**日志与 `doctor` 都要报出来** | 既不静默丢证据，也不因为一个坏文件起不来 |

- **去重键的规范性规则**（这条是被真实事件打出来的）：
  | 优先级 | 键 | 何时用 |
  |---|---|---|
  | 1 | `header.event_id` | 正常情况，飞书事件级标识 |
  | 2 | `message.message_id` | `event_id` 为空/缺失时退回（消息级标识，重投时同样稳定） |
  | 3 | **无键** | 两个都缺 → **必须打告警**，并仍然回提示 |

  ⚠️ **绝不允许「无键就静默跳过去重」**。踩过的坑：非文字消息那条路
  （回「我只处理文字」提示）刻意不走 `channel.handle`，于是要自己补记；
  最初写成 `if msg.event_id and dedup.is_duplicate(msg.event_id)` ——
  `event_id` 为空串时整段被跳过，**回提示但不写表**，于是同一张图被重投
  会**再回一次**。离线测试全绿（它们只断言「回了一句」，没断言「记住了」），
  是**真实环境联调**才暴露的：用户看到同一张图被回了两次。
  更糟的是当时**日志里什么都不打**，排查只能靠猜。
  所以规则是：**要么有键并记账，要么明确告警**，不允许无声跳过。
  这与 11.9.1「两种『群里不响应』必须能分开看」同源 ——
  **分不清原因，用户就只能猜。**
- **白名单检查必须在去重之前**：未授权者的 `event_id` 不进表，否则陌生人可以用
  垃圾事件把表撑爆。
  （推论：**无键可用的消息不写表**，否则等于给了一条绕开白名单的记账路径。）
- 实现落在 `feishu/dedup.py`；`services/channel.py` 只依赖一个
  `Deduplicator` 协议（`is_duplicate(event_id) -> bool`），默认实现仍是内存表 ——
  这样 `channel.py` 保持零依赖、可注入、可测，落盘是传输层的选择。
- 协议上的方法名刻意是 `is_duplicate` 而不是 `seen`：前者读作
  「是不是重复」正好对应调用处 `if dedup.is_duplicate(ev)` 的判断方向，
  而 `seen` 会让人以为「见过就返回 True」，恰好与语义相反。
- 落盘版与内存版**参数必须一致**（24 小时 / 2048 条），由
  `tests/test_feishu_dedup.py::TestParityWithChannel` 断言。数值在
  `channel.py` 里是**复制**的（它不能 import 飞书包），所以这个测试就是
  那个复制的人。

#### 11.9.3 单实例守卫

同一个 `app_id` 上跑两个长连接，飞书只会把事件投给其中一个，另一个静默失效，
现场表现为「bot 时好时坏」，且极难定位。所以：

- 启动时 bind 一个回环端口（`FEISHU_LOCK_PORT`，默认 `8771`，可由环境变量改）。
- bind 失败 → **立即退出**，并说清「已有桥接在跑」。
- 选端口而不是锁文件：进程崩溃时端口由系统自动释放，不会留下要人工清理的死锁。
- 默认端口**刻意避开 Web 的 `8770`** —— 两个进程撞端口会互相误杀。
- 锁只 bind 不 listen：占住端口就够了，少一个对外服务的端口。
- `doctor` 要有一项专查端口空不空。这是「bot 突然不响应」的**头号原因**，
  而且几乎没人会想到去查：第二个桥接起不来（或起来了但飞书只把事件投给第一个），
  现场表现和「权限坏了」一模一样。`doctor` 与桥接必须走**同一套**端口解析逻辑
  （`lock_port_from_env()`），否则会出现「doctor 说没占、桥接说占了」这种没法排查的分裂。

#### 11.9.4 本地操作的确认闸门（**已实现，规范性**）

凡是要动本地文件系统的动作，**先问、过时才做**。规范说「做什么」，
`services/localops.py` 是「怎么做」，`services/approval.py` 是「记住答复」。

##### 载荷形状（**实测**，不是照文档猜的）

飞书卡片按钮的 `value` 里的嵌套对象**原样**回到 `card.action.trigger`：

```json
{"event": {
  "action": {"value": {"action": "allow_once", "id": "<凭据>"}, "tag": "button"},
  "operator": {"open_id": "ou_…", "user_id": "2d1b7bec", "union_id": "on_…"},
  "context": {"open_message_id": "om_…", "open_chat_id": "oc_…"},
  "header": {"event_id": "…"}}}
```

三条由此推出的硬要求：

- `msg_type` 必须是 `interactive`，且 `content` 是 **JSON 字符串**（不是嵌套对象）
- 传输层返回的是**双重编码的 JSON 字符串** → 必须 `_decode_twice()`。
  踩过：直接 `raw.get("code")` 永远 `None`，于是把 `code=0 msg=success`
  读成「卡片发不出去」，**而真实 message_id 就在同一份输出里**
- `receive_id_type` **必须和值的形态匹配**。白名单接受 `ou_` 开头
  （open_id）与裸串（user_id，形如 `2d1b7bec`）两种。踩过：写死 `open_id`
  → HTTP 400，表现是「确认卡发不出去」，根因只是 id 形态不对。
  所以按**形状**判断，复用 `send_to_allowlist_entry` 那套，不另写一份

##### 三条不可协商的规则

1. **沉默即拒绝。** 没点 = 拒绝，永远不是「还在等」。
   `ApprovalStore.decide()` 只有三种返回：允许 / 拒绝 / 未答。
   **没有「未答就当允许」这条路径** —— 飞书卡片可能躺一小时没人点。
2. **过期即拒绝。** 超时的唯一安全解释是拒绝（否则请求方会一直等下去，
   或把失效授权当永久授权）。默认 TTL 600 秒。
3. **过期只在写入时判一次。** 答复落库那一刻判过有效期，之后再按时间翻掉
   会造成「用户点了允许、请求方读到却是拒绝」—— 那是最坏的组合。
   所以 `resolve()` 过期时**降级成 deny 且不记点击者**（那次点击无效，
   记下是谁点的会让人误以为它算数）。

##### 轮次化，不写挂起状态机

等待方与桥接是**两个进程**，内存里的同步原语跨不过去。所以：

```
ask（落库，带凭据）→ 发卡（凭据嵌进按钮 value）→ 轮询等答复
```

落盘 + 轮询天然跨进程、跨重启；桥接挂掉时请求方读到的是 deny 而不是无限等。
判据必须走**可注入的钟** —— 踩过：判据用 `time.monotonic()` 而测试注入
`FakeClock`，两个钟各走各的，于是「超时当拒绝」那条真的睡满整个 TTL，
套件卡死十分钟。

##### 点击后的卡片回写（规范性）

点一下之后，**那张卡本身必须变** —— 变成一眼能读的结果，且**不再可点**。
理由是「点了没反应」和「点了之后不知道成没成」都逼用户去猜；
而留着还能点的按钮等于骗人（他会以为还能改主意）。

回写**不调**「更新消息」接口，而是在 action 应答里带卡片就地替换：

```json
{"toast": {"type": "success", "content": "已允许"},
 "card":  {"type": "raw", "data": {<整张卡片 JSON>}}}
```

四条硬要求，每条都对应一次真实失败：

1. **`card` 必须是 `{type, data}` 包装，不能是裸卡片。** 裸卡片
   （`{config, header, elements}`）是**发送**的形状，不是**应答**的形状。
   实测：用户点一下看到「出错了」，而我们侧一切正常（handler 跑完、
   日志齐全、回了一个 1226 字节的应答）—— 证据齐全，判读错了。
2. **回写的卡片必须与发出去的那张同版本。** 官方错误码 **200830**：
   2.0 卡不能更新成 1.0，反之亦然。踩过：发的是 1.0（顶层 `elements`），
   回写却写了 2.0（`schema` + `body.elements`），版本对不上 → 整条应答判失败。
   依据这一条，`tests/test_card_feedback.py::TestVersionMustMatchSentCard`
   断言两张卡都不得出现 `schema` / `body`。
3. **颜色由 `granted` 显式决定，不从正文嗅。** 踩过：
   `line.startswith("已允许")` 判绿，而正文是 `**已允许**（…）` —— 开头是 `*`，
   于是**每张允许的卡都渲染成红色**。从渲染好的文案里反推语义，
   格式一改就悄悄错，且只查文案的测试查不出来。
4. **handler 返回类型要与 SDK 声明一致**（`P2CardActionTriggerResponse`），
   在注册处包一层适配器而不是 `cast` 蒙过去。包一层**先实测再改**：
   SDK 的 `Encoder` 对每个 model 做 `filter_null(vars(o))`，
   所以模型多出的 `toast.i18n=None` 不会发出去 ——
   `tests/test_card_sdk_envelope.py` 断言 `JSON.marshal(model) == JSON.marshal(dict)`，
   逐字节相同。不是「应该没问题」，是「证明了没问题」。

**决策不可篡改**（规范性）：`ApprovalStore.resolve()` 首次决定后不可改写。
第二次点击必须**明说没生效**（如「这次点击没有生效 —— 这张卡先前已被**允许**」），
而不是静默忽略，更不能翻转。绿灯/红灯的最终状态由**库里那一条**决定。

##### 现状与边界

**已实测跑通**（真实凭据、真实点击、真实飞书渲染，2026-09-29）：

- 允许一次 → 决策落 `allow`、卡片转**绿**、按钮消失
- 拒绝 → 决策落 `deny`、卡片转**红**、正文写明「没有访问任何东西」、
  且**确实没有访问目标目录**（拒绝后 `iterdir()` 未被调用）
- 过期点击 → 卡片写明「已过期，未生效」
- 代码位置：`approval.py`（存储）、`localops.py`（闸门）、
  `feishu/bridge.py::_card_action`（点击落库）、`feishu/sender.py`（发卡与回写）

**尚未实现**（列在这里是为了让「为什么没有」可追溯）：

- **只支持 Allow Once / Deny 两档。** 没有 Session / Always
- **不校验点击者。** 只记 `decided_by`。凭据是 `uuid4` 不可猜，
  真正要防的「谁能发起请求」在 ask 之前就卡住了；但「非白名单的人能否
  用捡到的凭据点允许」尚未挡
- **只做只读列举。** 写入/删除走委派链路（11.8），尚未接上这套闸门
- **委派中途审批已接线，但真机点击未验。** `--tool-gate` 那条路会**真的**
  逐次发飞书卡等人批（设计文档 11.8.1）。**不加这个开关就没有第三道闸门** ——
  默认那条是无人值守跑到底。接线时要沿用既有规则：沉默即拒绝（超时降级 deny，
  opencode 那侧会一直等）、只有发起人能批（校验点击人，**已达成，见 11.8.1**）、审批内容如实呈现
  `metadata.diff` 且 `always` 范围不得由 FreeAgent 改写。

  接线时要沿用本节的三条不可协商规则，不能另立一套：
  1. **沉默即拒绝** —— opencode 那侧会一直等，FreeAgent 必须自己设 TTL 并**超时降级 deny**，
     绝不能把「没回」当「等下去」
  2. **只有发起人能批** —— 飞书侧按钮点回时**必须校验点击人 == 委派发起人**，
     否则任何白名单内的人都能替发起人放行
     > ✅ **已达成**（V1.17）：发起人落 `tasks.delegate_requested_by`（schema 12），
     > 待批行、卡片收件人、执行期授权三处统一用它；无身份时落回 approver。剩下的缺口是**真机点卡**，不是判定。
  3. **审批内容要如实呈现** —— 展示 opencode 给的 `metadata.diff` 与 `patterns`，
     **不得由 FreeAgent 改写**。`always` 的范围由 opencode 提议，
     FreeAgent 不得自行收窄或放宽（那是替用户做取舍）

  这三条与 11.8.1 的三条纪律是**同源**的（闸门只有一处、判定只有一份）。

##### 前期验证留档（方法比结论重要）

这套机制落地前做过一次实测，结论是**七环节全通**（发卡 / 订阅 / 接管 /
value 往返 / 身份 / 定位 / 去重键）。留档两点：

- 桥接一开始报 `processor not found, type: card.action.trigger`，
  飞书给用户显示 `code: 200671`。**这不是「飞书不支持」**，
  而是事件早就到了、只是没人注册 handler。差点据此判死整条路。
- 验证脚本自己连错三次（没读 `feishu.env`、引用不存在的 `cfg.timeout`、
  双重编码 JSON 没解），**每次都差点得出「这条路走不通」**。
  一条未送达的请求**证明不了**能力不存在 —— 证据没到位时不要下结论

#### 11.9.5 日志归属与编码（**已实现，规范性**）

桥接**自己**拥有日志文件，并**钉死 UTF-8**：

- 路径 = `state_home(--db 所在目录) / "feishu.log"`，与身份缓存、事件去重表同源
  （`--db` 指到哪儿，日志就跟到哪儿）
- 编码**显式** `encoding="utf-8"`，**不许依赖任何隐式默认**
- stderr handler **保留** —— 控制台仍要看得到日志

**为什么值得单独立契约**（坑比结论重要）：

原先 `logging.basicConfig(...)` 只建了 `StreamHandler(stderr)`，**没建
FileHandler**。于是 `feishu.log` 的内容是**启动器把 stderr 重定向**进去的，
而重定向的编码取决于**启动那个 shell 的代码页**：

| 启动方式 | 写出的中文 |
|---|---|
| UTF-8 终端 | UTF-8 |
| 中文 Windows 的 cmd（936） | **GBK** |

后果不是「日志不好看」，是**排障会被骗**。实测：9826 行合法 UTF-8 里混着
4 行 GBK，而那 4 行恰好是两次真实点击（`【卡片动作】允许` / `【卡片动作】拒绝`）。
用 UTF-8 grep「卡片动作」**一条都搜不到** —— 险些反过来断定「实机证据是假的」。

引申两条教训，比编码本身更值得记：

- **判别编码只能靠「严格解码成功与否」。** 两次栽在同一个坏习惯上：拿
  「某个编码能解出来」当证据。GB18030 是**超集**，几乎任何字节都能解出
  几个汉字，于是「gb18030 解得动」对判别编码**毫无信息量**。同理
  「UTF-8 解不了」只证明「不是 UTF-8」，**不足以**推出「混合编码」——
  得先排除「统一就是另一种码页」，才轮得到「混合」。
- **关键格式不许依赖环境。** 同一份代码在不同终端产出不同字节的日志，
  等于让排障能力取决于「谁敲的启动命令」。

#### 11.9.7 委派闸门（**已实现，规范性**）

11.9.4 的闸门只管**本地只读操作**（`localops.py` 里那个目录列举）。
**委派那条路当时是裸奔的** —— `delegate.py` 拼好 argv 直接跑，没有闸门。
而委派是**唯一**终点在「本机执行代码」的能力，所以它是这条链路上最需要闸门的一条。
本节把闸门覆盖到委派，并定死五条规则。

##### 与 11.9.4 的分工

11.9.4 是闸门的**实现**（存储 + 卡片 + 落库）；本节是它到委派这条路上的
**扩展规则**。两者共用同一个 `ApprovalStore`，不新建第二套 ——
两套闸门必然漂移，而漂移的表现是「本地操作拦得住、委派拦不住」。

##### 五条规则

**规则 1：派发前必须有 pending 记录。** 闸门不是「记得要问」，
而是**发卡之前**先 `ask()` 落库、拿到凭据、再发卡。判据可查：
委派记录存在 ⇒ 对应 `pending_approvals` 有一行未过期且 `decision='allow'`。
反过来任何绕过 `ask()` 就 `Popen` 的路径都是 bug。

**规则 2：批准按场景分档。** 同一件事在不同上下文里该问的**次数**不同：

| 档 | 场景 | 无人应答时 |
|---|---|---|
| `remote` | 远程入口驱动（飞书 → 委派） | 拒绝，且**必须**有人点过 |
| `unattended` | 定时/无人值守跑 | 拒绝（`_unattended_deny`） |
| `local` | 本机交互式 | 拒绝，但可以给更长 TTL |

**规则 3：沉默即拒绝必须是函数，不能是约定。** 原先「不点就算拒绝」只写在
卡片文案的 note 里 —— 那是给用户看的，**不是给代码看的**。现在
`_unattended_deny()` / 过期降级都走同一条代码路径，能被测。
> 抄自 Hermes 的 `_unattended_deny()`：它把这条纪律**命名成了函数**。

**规则 4：绕过态可查询，且只有一个入口。** `is_bypass_active()` 是唯一
判断「当前是否处于绕过批准状态」的地方。理由：`--auto` 这类开关存在，
**必然有人会传**；靠「记得别传」是约定，靠查询才是防线。
> 抄自 Hermes 的 `is_approval_bypass_active()`。它甚至有 `_for_session()` 变体 ——
> 绕过是**会话级**的状态，不是全局的。

**规则 5：deny 优先于白名单，且拦 shell 运算符拼接。**
- 显式 deny 过的命令，**任何白名单都不能覆盖它**（Hermes 叫 `approval_floors`，地板）
- 白名单匹配必须**整条命令**匹配：`git log; rm -rf ~` 不能因为前半段在白名单
  就整体放行。必须拒含 `;` `&&` `||` `|` `` ` `` `$()` 的命令
  （Hermes 的 `_has_allowlist_shell_operator()`）

##### 明确不做的：永久授权

**不实现「永久允许」。** 我们信任边界窄得多（一个人、一台机、一个飞书白名单用户），
而永久授权在这个规模下**只放大风险**：一条被永久放行的白名单，
在半年后会成为绕过闸门的后门。
Hermes 有 `approve_permanent()`，我们不抄 —— 加它将来只是一行，
现在开这个口子却收不回来。

> 顺带记一条 Hermes 自己的教训：它有 `approvals_suggest.py`（扫批准历史给白名单建议）
> 和 `approvals_test.py`（**测试批准规则本身**）。这是对 approval fatigue 的正面承认。
> 我们在只有 0 条委派记录时用不上，但等有了几十条批准记录就该回来做这件事。

##### 顺序（本节的可勾选标准）

| # | 打勾标准 |
|---|---|
| 1 | 委派前过闸门，**派发前库必有 pending 记录** |
| 2 | 批准按场景分档；`unattended_deny` 有测试 |
| 3 | `is_bypass_active()` 有测试，且只有一个入口 |
| 4 | deny 优先于白名单 + shell 拼接有测试 |
| 5 | 真发一条委派 → 推回飞书；**攻击性测试：绕过闸门直接跑必须失败** |

第 5 条要第 1 条先成立才有意义 —— 没有派发路径就没有可攻击的面。

##### 两条配套规则（真机测出来后补的）

**规则 6：失败必须可重派。**

幂等守卫**不是**「有没有派过」，而是看**最后一条**派发相关记录：

| 最后一条是 | 含义 | 该不该再派 |
|---|---|---|
| （没有） | 没派过 | 派 |
| `delegation_dispatched` | 在跑 | **别派**（`--watch` 每轮都扫，会连发几个进程改同一个目录） |
| `delegation_succeeded` | 做完了 | 别派 |
| `delegation_failed` | 失败 | **派**（可重派） |

踩过的坑：原来只问「有没有 `delegation_dispatched`」，于是**一次失败就变成死任务** ——
而落库时写的那条 note 偏偏写着「执行失败，可以 /note 记下原因后重派」。
**文档承诺了重派，守卫禁止它。** 用户只能手工建一条新事务顶替。

⚠️ 副作用（已知，故意不修）：`--watch` 会对**持续失败**的任务每轮重派、
每轮重发一张批准卡。不会静默重跑（闸门仍要人点），但会周期刷卡片。
排查失败任务时**别开** `--watch`。

**规则 7：错因必须落库，不只是出现在终端那一行。**

opencode 失败时给的是**单行 JSON**，而记录上限 300 字符、终端显示另有截断 ——
于是真正的原因（`Upstream request failed: Insufficient account funds`）
常常正好落在被切掉的位置。用户事后**无法自查**。

三条要求：

- **产物链**必须含**完整** detail（上限放宽到 4000；终端短显示与库内存档
  不必用同一个上限 —— 一个给人看，一个给事后查）
- **记录**里要带**挖出来的** `message`，而不是「执行器退出码 1」那种
  没有行动价值的句子。挖的顺序：`error.data.message` → `error.message`
  → `message`；都挖不到才退回取首行（非 JSON 的 shell 报错仍看得到）
- **飞书回推**也要带原因 —— 通知渠道的意义就是「你现在就知道发生了什么」

这是 11.8 那条教训「报错信息不进 stderr 等于没报」的残留：
当时做到了「进 stdout」，但没做到「**进库**」，而库里才是事后能查的地方。

#### 11.9.8 规划中（**尚未实现，不得当契约用**）

以下两条来自对 nanobot / Hermes Agent / GenericAgent 的对照，**当前代码里没有**。
列在这里是为了让「为什么不做」可追溯，做的时候才不会再被当成已有能力。

- **配对流程** —— 治「第一次装时手里没有 `open_id`」的死循环：陌生私聊里 bot 回一条
  带配对码的卡片，用户把码粘回终端，码过期即失效。
  ⚠️ 配对**不能削弱边界 1**（11.9.1 白名单失败关闭）：它只解决
  「怎么拿到 `open_id`」，拿不到仍然拒绝启动。
- **卡片按钮 → 合成命令** —— 把卡片点击翻成合成命令（如 `/card button {...}`），
  走现有派发链路，于是 `/start` `/done` `/pause` 在飞书里点一下即可。
  ⚠️ 与 11.9.4 是**两件事**：那条是「谁来批准这次本地操作」，
  这条是「批准之后怎么复用同一套命令派发」。两者都做完，
  飞书里点一下才能既执行又改状态，而不必等这一步。
  ⚠️ 飞书侧必须同时开「交互卡片」能力并订阅卡片动作事件，
  **少一处会「发送成功但点击报错」**（实测：`code: 200671`，
  而事件其实已经到了 —— 见 11.9.4 留档）。

### 11.10 执行器注册表（规范性，V1.9；**尚未实现，不得当契约用**）

11.8.1 把**协议知识**收进了版本化适配器，但注册表里目前只有 `opencode` 一个
执行器，且**没有任何用户可见的入口** —— 用户无法知道有哪些执行器可用、更无法
在不写 SQL 的情况下问一个执行器问题。

本章规定多执行器的**用户可见面**。协议层仍归 11.8.1，本章不重复。

> **落地状态**：⬜ **全部未实现**。本章是规范，不是既成事实。
> 已有的地基只有 11.8.1 那个 `ExecutorAdapter` 注册表（`services/executors.py`），
> 它是**协议**注册表 —— 本章要加的是**能力**注册表与它的用户入口，两者不是一回事。

#### 11.10.1 叫「执行器」，不叫「Agent」（术语，规范性）

本项目里「Agent」这个词**已经被两个东西占了**：第三章的**角色**（人演的，不是
程序）与 11.8 的委派对象。若再引入「Agent」当第三种含义，同一段话里
「让 agent 处理」就分不清是在说角色、在说执行器、还是在说本仓自己。

所以：

| 说法 | 指什么 | 出处 |
|---|---|---|
| **角色** | 人演的职责身份 | 第三章 |
| **执行器** | 外部程序，FreeAgent 把活交给它 | 11.8 |
| **本仓 / FreeAgent** | 自己 | —— |

**不引入第三个「Agent」**。11.8.1 已经用「执行器」这个词，改回去是倒退。

#### 11.10.2 能力探针：**探测**，不解析自由文本（规范性）

一个自然的想法是让用户直接写：

```text
/agents opencode, claude, gemini
```

**这个交互有一个静默失败模式**：手写标识符。`claud`、`gemin`、`opencode2` ——
系统要么报错（用户学到了什么？），要么**猜**（更糟：猜错之后用户以为在用
Claude，其实在用别的）。11.8.1 已经吃过同一种亏：字段名对不上时
**不报错**，配置被静默忽略，闸门失效。

所以**用户不输入标识符，输的是名字；系统自己探测**：

```text
/agents
```

列出的是**探针结果**，不是用户输入的字符串。每个条目自带：

| 字段 | 含义 |
|---|---|
| `name` | 给人看的名字（`opencode`、`claude`） |
| `installed` | 探到了可执行文件吗 |
| `detected_major` | 探到的版本（探不到是 `None`，**不是 0**） |
| `dispatchable` | 满足 11.8.1 的版本闸门吗 |
| `verified` | 对着真实实例验过接线吗 |
| `capabilities` | 能力集合，见 11.10.3 |
| `unavailable_reason` | 不可派发时，**给一句能照着做的话** |

`unavailable_reason` 沿用 11.8.1 `version_mismatch_reason()` 的纪律：
**「不认识」与「认识但没验过」必须给不同的理由**，因为该做的事不同
（升级本仓 vs. 对着真机实测）。合成一句话「不可用」等于让人自己猜下一步。

> 探针**不静默回落**：`adapter_for()` 取不到就返回 `None`（11.8.1 规范 3）。
> 同理，探针探不到执行器就报「没装 / 探不到版本」，**绝不**默认挑一个装着的。

#### 11.10.3 最小权限集：三桶，不是三十个 flag（规范性）

要给每个执行器配权限，直觉是照抄工具面 —— `read` / `write` / `bash` /
`webfetch` / `browser` / ……。**flag 多到没人能读，就等于没有闸门**：
用户会一路点「同意」，而 11.8.1 已经实测过这个后果
（"问到最后就是无脑点" —— 那比不设更糟）。

所以权限**只对执行器分三桶**，由适配器自己映射到该版本的字段名：

| 桶 | 含义 | 映射到 opencode |
|---|---|---|
| `read` | 只读地看这个项目的文件 | `read` / `grep` / `glob`：`allow` |
| `write` | 改动文件或跑命令 | `edit` / `bash`：`ask` |
| `approve` | 每次都问人 | 上两者都 `ask`，且由本仓逐次裁决 |

三桶**穷尽**且**互斥有序**：`read ⊂ write`，`approve` 覆盖 `write`。
新增能力时**先问它属于哪一桶**，而不是新增一个 flag。

> **桶 → 字段名的映射是适配器的活，不是本仓的活。** V1→V2 字段名全变那件事
> （11.8.1 版本陷阱表）之所以曾经危险，正是因为映射散在业务代码里。
> 三桶是**稳定语义**，字段名是**易变实现** —— 分开才接得住下一次改名。

#### 11.10.4 轮次预算：Agent 套 Agent 会指数增长（规范性）

执行器可以自己再拉子代理（11.8.1 的配置里 `task: deny` 已经堵了这条路），
但**用户重跑一次 `/ask` 就是新的一轮**。没有上限时，「问一个问题」可能变成
一条几十分钟、几十次工具调用的链，而每一环都可能要人点。

所以有**硬预算**：

| 项 | 规则 |
|---|---|
| 单次 `/ask` 的工具调用次数 | 有上限，超了就**停下来报告**，不续跑 |
| 单次 `/ask` 触发的审批次数 | 有上限（与 opencode `once` 语义叠加） |
| 执行器自己拉子代理 | **deny**，不因为「预算还够」而放行 |

超预算**不静默截断** —— 沿用 3.6 的纪律：报告「已用尽预算，还剩什么没做完」。
半途停下而不说，用户会以为它跑完了。

#### 11.10.5 绝不自动触发委派（规范性，与第七章同构）

**这一条否掉「让本仓自己判断什么时候该问执行器」这个想法。**

理由与第七章「排序必须是透明弱信号」**完全同构**：本仓判断「这个问题适合
问 Claude」是一个**弱信号 + 不可复核**的组合 ——

- 用户**看不到**为什么派（排序信号至少附了理由与权重）
- 用户**没法反驳**（没写「不要问 Claude」的地方）
- 派错了**代价不对称**（多一次审批、多一轮等待，而收益是「可能答得更好」）

而 11.8.1 的整条纪律是**默认朝关开**（探不到版本就拒绝派发）。自动触发
是这条纪律的反面：默认朝关开、偶尔朝关关。**方向反了。**

所以 `/ask` **必须由人显式发起**，`/agents` 只看。本仓**不做**
「读到某个信号就自动派给某个执行器」。

> 将来若真要做，至少要先满足两条：(1) 派发理由**与权重一起呈现**
> （第七章格式），(2) 有一个**可写死的排除名单**让用户永久关掉某些执行器。
> 缺任何一条都还是不可反驳的弱信号。**现在两条都没有，所以不做。**

#### 11.10.6 `/ask` 的形状：问答，不是接管

`/ask` **只做一件事：把一个问题交给一个执行器，把答复拿回来。**

它**不是** 11.8 委派 —— 委派要落库、走三道闸门、产出 artifact、写 `TaskRecord`。
`/ask` 不落库、不进今天视图、**不问任何审批**（它不改任何东西，所以没有
「有副作用」可拦）。

| | `/ask` | 11.8 委派 |
|---|---|---|
| 落库 | ❌ | ✅ 一条事务 |
| 三道闸门 | ❌ | ✅ |
| 审批 | ❌（无副作用） | ✅ 逐次授权 |
| 进今天视图 | ❌ | ✅ |
| 产出 artifact | ❌ | ✅ |
| 轮次预算 | ✅ 有 | ✅ 有 |

**这样切的理由**：`/ask` 门槛低到可以随手用，才有人用它去**了解**有哪些执行器；
而它**碰不到任何真东西**，所以不需要闸门。把两者混在一起（「问一句话」也要走
三道闸门）会让人干脆不用。

> **一个诚实的例外**：如果将来 `/ask` 允许执行器**写文件**（比如让它生成一份
> 报告草稿落到项目里），那它**立刻**变成 11.8 委派，必须落库走闸门 ——
> 不能因为「入口叫 `/ask`」就绕过。**判据是「有没有副作用」，不是「从哪进来」。**

#### 11.10.7 明确不做的

- **不做多执行器并行** —— 先串行。一次问一个，理由与第 4 项（多设备强一致）
  同源：并行会引入「哪个先返回」「冲突了听谁的」，而这些在单人事务助手里
  一次都不需要。
- **不做执行器之间的直接互调** —— 执行器**不知道彼此存在**。它们只与本仓说话。
  否则「执行器 A 派活给执行器 B」会绕过本仓全部三道闸门。
- **不做执行器市场的动态加载** —— 注册表是**代码里的一份元组**
  （11.8.1 的 `_ADAPTERS`），不是运行时下载的插件。理由与「不采纳 plugin
  化架构」同源（17.1/17.4）：那会毁掉「零依赖、克隆即跑」。
- **不做自动触发** —— 11.10.5。
- **不做永久授权** —— 11.9.7 已定；半年后它就是绕过闸门的后门。
- **不做执行器的自修改配置** —— 隔离环境（`XDG_CONFIG_HOME`）必须**只由本仓**
  写。用户配置漏进来是 fail-open（11.8.1 实测）。

### 12.1.1 白话入口的路由契约（规范性）

白话入口按**职责**分三层，**不按话题**分。混淆这两者是本项目已经犯过的错。

| 职责 | 干什么 | 由谁做 | 理由 |
|---|---|---|---|
| **理解** | 这句话是「要一个视图」「要记一件事」「要改已有」 | 规则判定意图 + 视图**词表优先**（见下） | 无界自然语言 → 有界结构；**但写侧判定必须保守** |
| **事实** | 今天有什么、为什么排第一、在等什么 | **规则**，读库渲染 | 答案必须**等于**数据；模型重述会漏条/造条，而用户照着它行动 |
| **副作用** | 建事务、建/改角色 | **白名单** | 不可逆的部分 |

**分流顺序是规范性的：只读视图先试，然后才谈写。**

两条能力的**后果不对称** —— 只读答错只是读错一次，写错是往用户的角色结构里
塞脏数据（角色还反过来驱动分类，污染会自我强化）。所以先走不后果的那条路。

推论（**必须遵守**）：`RECORD` 之所以危险，正因为它是默认分支 ——
「没被认出来」等于「当成要记的事」。因此新增任何只读视图时，
**必须**接入 `ChatService.try_view()`；不得让入口自己先调 `read_intent`
再决定要不要问它。

> **实测过的违反后果**：`全部未结束的事` 没有疑问词，`read_intent` 判成
> `RECORD`。`ChatService.respond` 内部加了只读优先后它被正确路由，
> 但终端/飞书走 `Repl._natural`，那里自己先调 `read_intent`、
> 从不调用 `respond` —— 于是防线被完全绕过，真的建出了一条垃圾事务。
> 修法是 `try_view` 升为**公开接口**，两个入口都必须先问它。

**「一份能力一份实现」是硬约束。** 同一能力（白话问答）只能有一份实现；
任何入口都不得自建第二份判流逻辑。分叉的表现极隐蔽：Web 对话框正常、
终端和飞书错，而两边各自都测过。参见 `tests/test_routing_eval.py`。

**兜底必须自报家门。** 视图没命中时兜底到「今天」是允许的（永远有答案
好过「我不知道」），但答复必须**明说**「没听懂，先按今天答」——
未标注的兜底会把「我不知道」伪装成答案，比直接答错更坏。
数据侧标记 `ChatReply.inferred`，正文侧由 `_INFERNED_NOTICE` 承担，两者都要有。

> **实测反驳（2026-09-29，这条被判定为「不够」）**：上面那条只管**只读**
> 视图，而**写**这一侧仍然是「兜底就 RECORD」。真实对话里三句话暴露了它：

> | 用户说 | 实际发生 | 原因 |
> |---|---|---|
> | `你好` | **建了一条事务** | 不命中任何意图 → `read_intent` 最后一行 `return RECORD` |
> | `你可以做什么？` | 答「今天没有排进来的事务」 | help 词表有「**能**做什么」，没有「**可以**做什么」 |
> | `如何安排呢？` | 答「今天没有排进来的事务」 | 「如何」在 `_QUESTION_NOISE` 里，被当疑问词剥掉 |
>
> 真库里因此有**两条**「你好」事务（`0277e93d` inbox、`0fbbdb13` blocked）
> —— 不是偶发。

##### 写侧兜底：**默认问，不默认记**（规范性）

**RECORD 需要一个「正向信号」才成立**，三个信号**任一**满足即可：

1. 以 `_TASK_VERB_PREFIXES` 里的动词**开头**（「修窗户」「交周报」）
2. 含**时间/紧迫标记**（下周二、下午三点、别忘了、要交…）
3. **够长**（≥ 10 字）—— 长句自带语境，而「你好」「ok」「在吗」都很短

三个都没有 ⇒ **不记，改成反问**（`ChatReplyKind.CLARIFY`）。

> 为什么是「三个都没有才问」而不是「三个都有才记」：
> **代价不对称。** 问错一句 = 多一轮对话；记错一条 = 往用户的角色结构里塞脏数据，
> 而且角色**反过来驱动分类**，污染会自我强化（见上面「后果不对称」那节）。
> 所以失败方向必须是「多问一句」。

> **诚实记下这条规则的代价**：「等对方回复合同条款」这类**短句**会被问一次
> （「等」不在动词表里，也没时间标记）。这是**故意接受**的 ——
> 宁可多问一句，不要静默建一条垃圾事务。若这类句子在真实使用里变多，
> 该加的是「等 / 待 / 得 / 需要」这类**正向**动词到信号表，
> **不是**把「先问了再说」这条规矩取消掉。

##### 「能不能做什么」用结构判断，不用词表（规范性）

`_is_help_request` 原来枚举 `("你能做什么", "能做什么", "会什么", "帮助", "怎么用", "help")` ——
「你可以做什么」就 miss 了，**差一个字**。

改成**结构**：`(能|可以|会|能够)\s*(做|干|搞|办)?\s*(什么|啥|哪些|哪个|嘛)`
外加原有的 `帮助 / 怎么用 / help`。理由：**词表是无底洞** ——
补了「可以」还会有「能干嘛」「有啥功能」「能帮我做什么」。
判结构才覆盖得住下一种说法。

##### 不猜的时候给选项（规范性）

反问时**必须**给出可点的选择，而不是让用户猜该怎么措辞：
读类给 `_VIEWS` 的前几项，写类给「记一件事 / 都不是」。
飞书侧用**卡片按钮**（机制见 11.9.4，已实机验证），终端/网页用文字选项。


**路由必须有评测，且量两个指标。** 否定断言（问句不许写数据）只守住
「不伤害」，守不住「做对」：一个把所有问题都路由到「今天」的实现能通过
全部否定断言。因此 `tests/test_routing_eval.py` 维护**黄金语料**，
每条标注期望路由，量**路由准确率** + **自报正确率** + **误写率（恒为 0）**。
基线（2026-09-29）：路由 14/15、自报 13/15。数字只许显式提升，不许无声下滑。

#### 12.1.2 「理解」可以交给模型，但**默认不交**（规范性）

第一性原理说「非确定性只买理解」，于是有了 `LLMProvider.select_view()`：
让模型在一组**封闭**视图名里挑一个，事实仍由规则读库渲染。

实现齐了（协议 + `DeepSeekProvider` + 13 条接缝测试），**默认关闭**，
开关是 `llm.view_routing`。理由是**实测**（黄金语料 15 条，真 DeepSeek，
探针 `tools/probe_view_routing.py`，并带「接线自检」以防拿关键词表和自己比）：

| | 路由 | 自报 |
|---|---|---|
| 关键词表 | **14/15 = 93%** | **13/15 = 87%** |
| 模型选路 | 13/15 = 87% | 11/15 = 73% |

输在更重的那一项：模型**一次都没返回「不匹配」**。提示里明确要求挑不出就
返回 `null`，它仍每次都自信地挑一个 —— 于是「自报猜的」这条防线被拆掉。
照现状打开，系统会**更不置信也更不诚实**。

规范性约束：

- `select_view` **只能返回闭集里的名字或 `None`**。自创名字一律丢弃 ——
  闭集就是这条接口的全部安全性。
- 必须区分「**没有意见**」与「**没有意见的能力**」，故另设
  `can_select_view`：规则层恒为 `False`，于是离线时**一次网络调用都不发生**，
  行为与从前逐字一致；混起来会让每个离线问句都被标成「猜的」。
- 任何异常都回落到关键词表。选路是锦上添花，没有资格掀翻主流程。
- 开关**不进设置页**：把一个「量出来更差」的开关放到界面上只会诱使人随手打开。
  要试请直接改 `config.json`。
- 想打开它，必须先改 `tests/test_view_routing.py::TestViewRoutingIsOffByDefault`
  并附上新数字。**量出来的结论就照着量**，不凭「架构上更该这样」。

### 12.3 分层纪律（规范性）

- `domain` 零 I/O、零业务判断。
- `storage` **只存取，不判断**。顺延、权重计算、状态迁移合法性一律不在这一层。
- `services` 承载全部业务规则与不变式校验。
- `cli` 只做输入解析与渲染，不含业务判断。
- `services/llm/provider.py` **不 import `domain`**，用 `TaskRef` / `RoleHint` / `SignalRef` 作为边界类型 —— 这是替换真实 LLM 的接缝。
- `cli` 的命令解析用**派发表**（`_handlers()` → `_cmd_*` 方法），不用不断增长的 `if/elif` 链；每条命令在 `_USAGE` 里必须有用法文本，`/help` 必须列全。
- **API Key 绝不进代码库、绝不进 `config.json`、不进日志与错误信息**。来源是
  **环境变量优先、`~/.freeagent/llm.env` 兜底**（见 12.5 的决策表）。
- **密钥一律用 `SecretStr` 承载，不裸传 `str`**。取值收窄到 `use()` 一个出口，
  `__repr__` / `__str__` 只能给出分级遮蔽的预览，于是 `log.info("%s", cfg)`、
  异常里带 config、f-string 拼进日志都**不会**带出原文。
  容器上覆写 `__repr__` 只是**约定**（新写一处就可能漏），
  值本身带 mask 才是**保证**。
- 密钥**落盘是允许的**，但三条硬约束由 `secrets_file.SecretFile` 统一保证
  （飞书的 `feishu.env` 与 LLM 的 `llm.env` 共用它）：
  1. **变量名必须是白名单**，不接受自定义 key —— 往 `PYTHONPATH` /
     `LD_PRELOAD` / `EDITOR` 里塞一个路径就是 RCE，而 `^[A-Za-z_]\w*$`
     **挡不住这些**，因为它们本来就合规；
  2. **读盘容忍 BOM**（`utf-8-sig`），否则 PowerShell 写出的文件会让第一个
     变量名带 `\ufeff` 而**静默失效**；
  3. **每次读都清洗**粘连行与 `***` 占位符。
  另加一条借鉴自 Hermes 的检查：**凭据含非 ASCII 直接拒**（全角引号、零宽字符
  肉眼分不出，服务端只回 401）。
- **明文不落加密、且不假装加密**。DPAPI 只多防「其他 Windows 用户」，而同用户
  进程照样能 `CryptUnprotectData` 解开，所以防那个威胁的是会话令牌，不在密钥文件。
  相比「只走环境变量」，落盘确实把「其他同用户进程」的暴露面从「进程运行期间」
  扩到「任何时刻」—— 这一点如实记下，靠「文件不在仓库内 + 写入受会话令牌保护 +
  响应只给掩码」降低，不靠保证。
- `services/channel.py` **零依赖、不碰传输**：去重表与 bot 身份由 `feishu/` 通过
  `Deduplicator` 协议注入，默认实现是内存表。所以 11.9.2 的落盘是传输层的选择，
  核心包 `dependencies` 依然为空。

### 12.5 模型层（规范性）

智能层有两种实现，同一个 `LLMProvider` 协议：

| 实现 | 何时使用 | 特点 |
|---|---|---|
| `RuleBasedProvider` | 无 Key / 显式停用 / 模型失败兜底 | 纯规则、离线、确定性 |
| `DeepSeekProvider` | 有可用凭据时 | 真实模型。**名字是历史遗留**：它其实是标准 OpenAI 兼容客户端（`messages` / `Bearer` / `choices[0].message.content`），同一个类服务注册表里全部服务商 |

**多家 LLM（12.5）**

`services/llm/providers.py` 是唯一的「有哪些服务商」来源。每家声明
`id` / `label` / `default_base_url` / `default_model` / `key_env_var` /
`needs_key` / 精选模型 / `note`。当前收录 6 家**全部是 OpenAI 兼容**：

| id | 服务商 | Key 变量名 | 默认地址 |
|---|---|---|---|
| `deepseek` | DeepSeek | `DEEPSEEK_API_KEY` | `https://api.deepseek.com/v1` |
| `kimi` | Kimi / 月之暗面 | `MOONSHOT_API_KEY` | `https://api.moonshot.cn/v1` |
| `qwen` | 通义千问（DashScope 兼容模式） | `DASHSCOPE_API_KEY` | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| `openai` | OpenAI | `OPENAI_API_KEY` | `https://api.openai.com/v1` |
| `ollama` | Ollama（本机、不联网） | `OLLAMA_API_KEY`（`needs_key=False`，留空即可） | `http://127.0.0.1:11434/v1` |
| `custom` | 其它兼容服务（vLLM / LM Studio / one-api） | `OPENAI_COMPATIBLE_API_KEY` | **无默认，地址与模型自填** |

没有 `llm.provider` 的旧配置一律落到 `deepseek` —— 那个值是**字面量**而不是
从注册表导入，因为它表示「这份配置产生于多 provider 之前」，语义上永远是
DeepSeek。哪天把 `deepseek` 从注册表删掉，正确做法是**迁移旧配置**，
而不是让旧配置指到别家去。

`llm.env` 的**白名单由这张表推导**（`all_key_env_vars()`），不另抄一份：
抄的那份会漂 —— 加了 provider 忘了加白名单，表现是「界面保存成功了、
重启后 Key 没了」，而界面上还显示「已配置」。

**范围刻意只到兼容族。** Claude / Gemini **不是这个形状**：鉴权头、请求体、响应
都不同，有的还不支持 `response_format`。硬接进来的后果**不是报错，是静默劣化** ——
`provider.py` 五个方法里有三个硬依赖 JSON 输出质量（`classify` 要结构化 JSON、
`draft` 要带 `[TODO]` 骨架、`suggest_schedule`）。换一家 JSON 不可靠的实现，
`classify` 会频繁返回 `need_clarification`，用户看到的是「这助手老是反问我」，
而日志一片正常。**要接它们，得先扩协议、加一层结构化输出能力声明**
（provider 自己说支持 `json_schema` 还是 `json_object` 还是「仅靠 prompt」），
**声明不了就不接** —— 而不是接了在生产里悄悄降级。

**配置：秘密与非秘密分开**

| 内容 | 来源 | 理由 |
|---|---|---|
| **API Key** | 环境变量优先，`~/.freeagent/llm.env` 兜底 | 秘密。`config.json` **永远不会有**（`Config` 压根没有 `api_key` 字段，是现读的 property，靠类型防住而非靠约定） |
| provider | `config.json` 的 `llm.provider`，或 `FREEAGENT_LLM_PROVIDER` | 非秘密 |
| model / base_url / timeout | `config.json` 的 `llm` 段，或 `DEEPSEEK_MODEL` / `DEEPSEEK_BASE_URL` / `DEEPSEEK_TIMEOUT` | 非秘密 |
| 精力档位 | `config.json` 的 `energy_windows` | 非秘密（同时让 `ENERGY_FIT` 真正可触发） |
| 总开关 | `FREEAGENT_RULES_ONLY=1` 强制走规则层 | 演示 / 离线排查 |
| 降级开关 | `FREEAGENT_ALLOW_FALLBACK=0` 禁止自动降级 | 宁可报错也不要悄悄降级 |

**为什么环境变量优先于文件**（这点与 Hermes 不同，Hermes 把 `.env` 载入
`os.environ`，等于只有一个来源）：环境变量是**显式动作**（临时 `set` 一次做对比
测试，跑完就消失），文件是**持久配置**。界面上会**如实显示当前生效的是哪一个**
（`Config.key_source`）—— 不显示的话，用户在界面上重填了 Key 却发现没生效
（被环境变量压住），会以为设置坏了。

**不认识的服务商 id 必须在加载时报错**，不静默回落到 DeepSeek。静默回落的
表现是「下拉里选着 Kimi、请求却打到了 DeepSeek」，而界面上看不出任何异常。

优先级：内置默认 → 配置文件 → 环境变量。`/llm` 只显示「已配置 / 未配置」，
另加一行「Key 来源」。**降级原因里带的是真实服务商名** —— 用 Kimi 出错时不能
显示成 deepseek，否则用户会去查错的那家的账单和限流。

**HTTP 只用标准库** `urllib` —— 文档 12.1 的「唯一第三方依赖是 pytest」不因此破例。

**传输层可注入**：`transport(url, payload, headers, timeout) -> 响应体`。
测试全程打桩，**零网络请求**。Key 走 `headers`，**不进 payload** —— payload 容易被日志打印。

**输出必须过校验**（模型会编造，这是既定事实，不是假设）

| 风险 | 防线 |
|---|---|
| 编造角色名 | 角色名**白名单**：不在已知角色列表里的一律丢弃 |
| 丢弃后零候选 | **强制追问**，绝不把事务塞进猜出来的角色 |
| 输出非法 `kind` | 白名单 `{action, wait, reminder}`，否则报错 |
| 置信度越界 | 钳到 0..1；≥ `ROLE_MATCH_THRESHOLD` 才免追问 |
| 草稿漏掉「未知」标记 | 强制补齐 `## 目标` / `## 完成标准` / `## 材料` / `## 待确认` 四段，且必须存在 `[TODO]` |
| 步骤不是列表 | 无任何列表标记时视为解析失败，退回规则层脚手架 |

**降级必须告知**：模型失败时退回规则层，原因记入 `last_degradation`，
CLI **如实打印**「（模型不可用，已退回规则推断：…）」。
**禁止静默劣化** —— 用户必须知道刚才那句判断是规则猜的。

### 12.6 Web UI（规范性）

除终端外提供**本地 Web 界面**：`python -m freeagent.web`，默认 `http://127.0.0.1:8770/`。

**技术选择**：Python 标准库 `http.server` + 单页 HTML，**零框架、零外部资源**
（无 CDN、无字体文件）。理由：这是本地工具，断网必须照常能用；且不破坏
12.1 的「唯一第三方依赖是 pytest」。不选 `tkinter` 是因为列表/详情视图在
tkinter 下又丑又难写。

**分层纪律**：`web/serialize.py` 只做领域对象 → JSON，**不含任何业务判断**。
顺延、排序、状态迁移全部仍由 `services` 决定 —— 两个入口共用同一套规则，
绝不允许 Web 层自己再算一遍。

**并发**：`ThreadingHTTPServer` + 连接 `check_same_thread=False`，但 SQLite 连接
**不能被两个线程同时使用**，所以每个请求都持有 `App.lock`（`threading.RLock`）。
这是硬约束，不是优化。

**安全边界**

| 项 | 规则 |
|---|---|
| 监听地址 | **只允许回环**（`127.0.0.1` / `localhost` / `::1`）。`create_server` 对其他地址**直接抛错** |
| 鉴权 | **无**。正因只监听回环才成立 |
| 写操作 | **白名单**：新建事务、状态迁移（开始/等会再做/放一放/做完/放弃）、排期/移出排期。草稿采纳、角色合并、改名、静置、删除**一律 404**，仍只能去终端 |
| 角色选择 | Web 建事务**必须显式选角色**，不做推断（推断是自然语言路径的事） |
| 响应头 | CSP（`default-src 'none'`，禁一切外部资源）、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store` |

**不许在 UI 里丢掉的东西**（有测试守着）

1. 每条排序信号的**理由**必须显示；响应里 `signals[].reason` 是必填字段。
2. 免责标记「启发式提示，不是评分」必须出现在页面与每个列表响应里。
3. 「助手不替你决定先做哪个」这句要在页面上。
4. 视图切换只是**换个角度读同一份数据**，不给「筛选掉某些事」的选择权。

**明确不做**：编辑草稿、拖拽排期、实时推送（WebSocket）、登录鉴权。
提醒仍需进程在跑 —— **Web 界面不解决「终端关了收不到提醒」这个核心缺陷**。

**状态名 ≠ 动作名**：目标状态是领域概念（`ALLOWED_TRANSITIONS` 给出 `active`），
动作是接口概念（`start`）。这个映射由**接口层**翻译成 `allowed_next_states[].action`
给前端 —— 前端若把状态名直接当动作 POST，会得到 404。这个坑踩过两次，故有测试守着。

### 12.7 飞书通道控制面（规范性）

12.6 解决了「用浏览器操作事务」，但**飞书通道管不了**——它是独立常驻进程，
而 Web 界面是请求-响应模型，关掉浏览器就没了。现场表现：开终端、粘 Secret、
盯 `data\feishu.log`、猜「它到底连上没有」。本节把「看状态 / 看日志 / 启停 / 配凭据」
收进同一个界面。

**位置**：并入现有 `python -m freeagent.web`，**不新开入口**。少一个进程、少一个
端口，状态与事务同屏。

**状态传递用文件，不用 HTTP 端点**（规范性）：桥接周期写
`<state_home>/bridge_status.json`（与 `feishu_seen_events.json`、
`feishu_bot.json` **同目录**，因此 `--db` 换位置时跟着走 —— 沿用 11.9.2 的
同一条规则），Web 读文件。理由是**零网络暴露面** —— 起一个
HTTP 端点就要处理端口冲突与 CSRF，为这点便利引入攻击面不划算。

**状态文件格式**（规范性，`updated_at` 为 Unix 秒）：

| 字段 | 含义 | 用途 |
|---|---|---|
| `updated_at` | 最后一次心跳 | **判活**：超期即视为「桥接已死」 |
| `pid` | 进程号 | 「是不是我起的那个还活着」 |
| `state` | `starting` / `ready` / `degraded` | 一个字段说清「能不能用」 |
| `connected` | 长连接是否已建立 | 与 `state` 分开：连接断开≠进程死 |
| `bot_open_id` / `bot_name` | 探测到的身份 | 群聊 @ 门控的依据；**没有就是失败关闭** |
| `allowed_users_count` | 白名单人数 | 为 0 是致命配置（启动即拒） |
| `lock_port` | 单实例锁端口 | 「另一个桥接在跑」是「突然不响应」的头号原因 |
| `dedup_entries` | 去重表条数 | 跨重启去重是否真的在工作 |
| `last_error` | 最近一次可读错误 | **出问题时的第一手线索** |

⚠️ **`updated_at` 是必需的，不是装饰**：进程被强杀时状态文件会**留在磁盘上**，
界面若照着它显示「已连接」，就会对着一个几小时前死掉的进程报健康。
所以「陈旧」必须能显示出来，且判定逻辑只有一处。

**日志就地看**（规范性）：读桥接日志文件的尾部，不要求用户另开编辑器。
**但日志落盘要显式开**——桥接默认只写 stdout，所以从界面启动时必须带日志重定向，
否则界面「日志」区永远空白，而空白会被当成「没出错」。

**改配置必须明说「要重启才生效」**（规范性）：凭据写盘 ≠ 长连接重连。
界面在检测到配置变更而进程未重启时，**显著提示**，并提供一键重启。
不提示的话，用户改了配置什么都没变，会判定「这界面没用」或「配置错了」——
两个都错，而且都很难自己发现。

**启停由控制面代劳（规范性）**：目标是消掉「另开一个窗口跑脚本」这一步。
规定：

- 动作只走 **POST** `/api/feishu/bridge`，`action ∈ {start, stop, restart}`。
  **刻意不注册 GET 别名** —— 浏览器预取、爬虫、`<img src>` 都会自动发 GET，
  能杀进程的操作绝不能挂在这种方法上。
- 「是否已在运行」只有一个真相来源：桥接自己的单实例锁
  （`PortLock`，bind 而不 listen）。探测方式是「试着 bind 一下」。
  ⚠️ **探测用的锁必须立刻释放** —— 不释放的话 Web 进程会一直占着端口，
  而它刚启动的那个桥接永远拿不到锁，自己把自己堵死，症状是「点启动永远
  说端口被占用，而占用者是自己」。
- **只停本界面启起来的进程**。进程句柄只存在内存里；拿不到句柄时**如实
  报错**，**禁止**照状态文件里的 pid 去终止 —— pid 可能已被系统回收给
  **另一个进程**，那会杀掉毫不相干的程序。代价是「Web 重启后停不掉此前
  那个桥接」，如实说明即可。
- 端口被别人占着时**不硬顶**：顶掉一个可能正在正常收消息的桥接，比报错
  坏得多。此时界面要说「端口被占着、管不着」，而**不能**说「已停止」——
  两者的正确后续动作完全不同。
- 启动前先自检配置，**配置不全就不许起进程**；起进程后短暂等待并**抓早退**
  （桥接秒退是常态：缺 Secret、凭据不对），当场报退出码并指出日志路径，
  绝不报「已启动」。日志**追加**写入 `feishu.log`（即状态页读的那个路径）。

**三条状态必须分开显示，不可合并成一个「在跑 / 没跑」**：①进程活着且是本
界面启的 ②进程已退出（带退出码）③端口被占但无证据是自己的桥接。合并了
就等于把「有东西在跑、但我管不着」谎报成「干净」。

**凭据存储（规范性，修订 12.6 的鉴权前提）**：12.6 写「鉴权无，正因只监听回环」，
而本节要让界面能**写** App Secret，**这削弱了该前提**。规定：

- 落 `<state_home>/feishu.env`，**明文**，格式 `KEY=VALUE`。
  写盘用临时文件 + `os.replace`（原子），**保留原文件权限**。
  读盘必须容忍 **BOM**（`utf-8-sig`）—— PowerShell 写出的 `.env` 带 BOM，
  用 `utf-8` 读会让第一个变量名带上 `\ufeff` 而**静默失效**。
- **每次读都清洗**（规范性）。两种已知的损坏形态必须能自愈：
  1. **两对 `KEY=VALUE` 粘在一行**（中间少了换行）→ 按已知变量名拆开；
  2. **残留的 `KEY=***` 占位符**（上次写到一半被打断）→ 视为未配置。
  只在**已知变量名**上做拆分，避免值里恰好含大写加 `=` 被误切。

- ⚠️ **变量名是固定白名单，不接受自定义 key**（**规范性，安全硬约束**）。
  Hermes 的环境变量写入器专门维护一份 denylist，理由写在它的注释里：
  往 `PYTHONPATH` / `LD_PRELOAD` / `NODE_OPTIONS` 里塞一个路径，
  下次起子进程就会**在 main 之前加载攻击者的代码**；
  往 `EDITOR` / `BROWSER` 里塞值 = 下次调用时 **RCE**。
  而 `^[A-Za-z_][A-Za-z0-9_]*$` 这种正则**挡不住这些** —— `PYTHONPATH` 完全合规。
  所以本项目的规定比它更严：**只认下面 5 个名字，其余一律拒绝**，
  连「自定义变量」这个入口都不提供。

  | 变量 | 秘密 | 说明 |
  |---|---|---|
  | `FEISHU_APP_ID` | 否 | 飞书应用 ID |
  | `FEISHU_APP_SECRET` | **是** | 32 位密钥 |
  | `FEISHU_ALLOWED_USERS` | 否 | 逗号分隔的 open_id |
  | `FEISHU_DOMAIN` | 否 | `feishu` / `lark` |
  | `FEISHU_LOCK_PORT` | 否 | 单实例锁端口 |

- **读取优先级：环境变量优先，`feishu.env` 兜底**（规范性）。
  规则只有一条：**环境里有的键，环境说了算；环境里没有的，文件补。**

  理由：环境变量是「这一次运行我明确要什么」，文件是「平时用的默认值」。
  反过来会让 `set FEISHU_APP_ID=...` 这类一次性覆盖失效 —— 而 doctor、
  测试、CI 都依赖它。

  按**键是否存在**判断，而不是「值是否为空」（规范性）。否则
  `set FEISHU_APP_SECRET=`（故意清空）会被文件里的值悄悄填回来，
  而那恰好是最不该被悄悄推翻的一种意图。

  显式传入一份 `env` 时**完全不读文件**（规范性）：传了就是「我就是要用
  这一份」，测试与 doctor 依赖这个封闭性，顺带也让这条路径没有隐形的磁盘 IO。

  ⚠️ **这条优先级的连带后果（踩过的坑）**：既然环境变量压过文件，那么
  **启动脚本就不得再设这 5 个变量**，否则它在界面保存新配置之后再启动，
  会用脚本里的旧值把文件里的新值**静默压掉**——用户看到「已保存」，桥接
  用的却不是那份。`tools\run_feishu.bat` 曾把 App ID 和白名单硬编码在
  脚本里（现已移除），Secret 也曾无条件交互提示并覆盖文件值
  （现改为**文件里已有就不问**）。脚本判断「是否还需要问」必须调用
  `merged_env()`，不要在批处理里自己猜优先级——那正是当初出问题的原因。

- **会话令牌是必需项，不是可选项**（规范性）。令牌由
  `secrets.token_urlsafe(32)` 在**进程启动时生成、退出即失效**，注入页面，
  校验用 `hmac.compare_digest`（**恒定时间**，防时序侧信道）。
  理由：明文 Secret 落盘后，**本机任何进程**都能直接读那个文件 ——
  令牌防不住「读文件」，但防得住**通过 HTTP 接口读写**，
  包括 CSRF（诱导浏览器替你 POST）。
  这条**推翻 12.6 的「鉴权无」**。

- **为什么不用 DPAPI**（规范性决策，附理由以免反复）：
  两种威胁要分开看 ——

  | | 防「其他用户」 | 防「本机其他进程」 |
  |---|---|---|
  | 明文 + 令牌 | ❌ | ✅ |
  | DPAPI + 令牌 | ✅ | ✅ |

  DPAPI 只多防了「其他 Windows 用户」。而**同用户的进程照样能调
  `CryptUnprotectData` 解开** —— 所以 DPAPI 对「本机进程」这个真正的威胁
  **毫无作用**，而令牌恰好解决它。多花一份实现成本去防次要威胁不划算，
  且 DPAPI 会把配置**绑死在 Windows 账户**上，跨平台就读不出来。
  追求更高保护时可选启用，但**不是本节的默认要求**。

- 界面上 Secret **只显示掩码预览**（如 `kRZ6…KyNa`），可确认「是那个值」而不泄露；
  **任何接口都不许把明文 Secret 回传给浏览器**。
- 「读 Secret」这类端点要**限流**（Hermes 用 5 次 / 30 秒），防本机反复试探。

**白名单按多层 ID 匹配（规范性，修订 11.9.1 的单 open_id 做法）**：飞书同一个人有三层标识，
权威性/稳定性依次是：

| 标识 | 作用域 | 换飞书应用 | 说明 |
|---|---|---|---|
| `open_id`（`ou_`） | **应用级** | **会变** | 只有它能直接在开放平台查到 |
| `user_id`（裸串，如 `2d1b7bec`） | 租户级 | 不变 | **需应用申请对应权限**；事件里没带就当没有 |
| `union_id`（`on_`） | 开发者级 | 不变 | 飞书目前基本不下发 |

规定：

- **事件带哪几层就比哪几层**：把事件携带的**全部**标识与白名单求交集，任一命中即放行。
  刻意**只认一层是错的** —— 用户填了 `user_id` 却静默无效、换应用后 `open_id` 失效
  而无从查证，这两条都源于此。
- **不降级到名字匹配**（规范性）。身份必须**由事件本身携带、可被验证**；名字可重名、
  可冒用，不能作为「谁能指挥本机执行代码」的判据。
- **`user_id` 需权限**（规范性）。应用没申请时事件里就不带它，此时只配 `user_id` 等于
  没配 —— 界面必须说明这一点，而不是让人以为配好了。
- **拒绝时必须打出双方对照**（规范性）。日志形如
  `事件侧=['ou_x', '2d1b7bec']，白名单=['ou_y']`；只写「不在白名单」等于把排查
  成本全推给用户。
- **`oc_` 开头的是会话 id，不是人的 id**，保存配置时**直接拒绝**。填进去不会立刻报错，
  而是一直等到「提醒永远发不出去」才暴露。
- **控制面要显示实际见到的 ID**（规范性）。从飞书发一句话（私聊直接发、群里 @ 它）
  就会出现，用户照着填而不必翻日志。**只记身份、不记消息正文**；群里**只记主动 @ 过它
  的人**，不记全部群成员。

**白名单自检（规范性）**：`open_id` 是**应用级**的，换飞书应用就会变，
于是白名单**静默失效**——现象是「bot 一句话不回」，而原因在日志深处。
所以界面必须能回答「**我的 open_id 在不在白名单里**」，
`doctor` 也要有对应一项。`doctor` 现在只报「已授权 1 人」，答不了这个问题。

**明确不做**（沿用 12.6 纪律）：卡片按钮交互、消息编辑、拖拽排期。
界面上**任何「已连接」的显示都必须有陈旧判定兜底**，
因为整个界面唯一的真相来源是一个可能被进程遗弃的文件。

### 12.4 命令表（规范性）

`/help` 输出以本表为准。新增能力必须同时给出命令入口，否则等于未交付。

**视图**

| 命令 | 作用 |
|---|---|
| `/today` | 今天视图：先顺延，再全局排序，附每条信号理由 |
| `/all [open\|closed\|all]` | 全部事务；默认只列未结束 |
| `/roles [all]` | 角色脉络；默认只列活跃，`all` 含静置 |
| `/role <名字\|id>` | 该角色下的事务（含被合并进来的） |
| `/task <id>` | 打开事务，返回完整恢复契约 |

**建事务与产物**

| 命令 | 作用 |
|---|---|
| `/new <角色> \| <描述>` | 显式创建，跳过角色推断 |
| `/draft <id> [要求]` | 生成结构化草稿骨架（`[TODO]` 标未知处） |
| `/revise <id> <内容>` | 局部重做，**产生新版本**，旧版保留 |
| `/artifact <id> [版本]` | 查看草稿版本链 / 某一版全文 |
| `/accept <id> [版本]` | 采纳某一版 |
| `/steps <id>` | 拆成几步（**只拆，不排序**） |
| `/plan <id>` | 按命中信号给排期参考，不给结论 |

**状态与调度**

| 命令 | 作用 |
|---|---|
| `/start` `/pause` `/done` `/drop` `<id>` | 开始 / 等会再做 / 完成 / 放弃 |
| `/kind <id> <action\|wait\|reminder> [等谁]` | 改形状；改成等候类须说明在等什么 |
| `/wait <id> <等谁>` | 放一放并记下在等什么 |
| `/followup <id> <日期\|off>` | 设/清跟进时间（驱动 `OVERDUE_WAIT`） |
| `/today-pin <id> [日期\|off]` | 排进今天 / 指定日期 / 移出排期（移出不改 `state`） |
| `/note <id> <内容>` | 记一笔进度 |
| `/dod <id> <标准\|off>` | 改这条事务的完成标准 |

**委派**（见 11.8）

| 命令 | 作用 |
|---|---|
| `/delegate <项目绝对路径> \| <角色> \| <需求>` | 建一条委派事务；执行器是独立进程 `python -m freeagent.delegate` |

**角色与归属**

| 命令 | 作用 |
|---|---|
| `/move <id> <角色>` | 只挂到目标角色 |
| `/unrole <id> <角色>` | 摘掉一个角色标签（不允许摘到空） |
| `/role-add <名字> [备注]` | 新建或更新备注（备注参与角色推断） |
| `/role-rename <名字> <新名>` | 改名 |
| `/role-silence <名字> [on\|off]` | **省略 = 静置**，`on` = 恢复活跃 |
| `/role-dod <名字> <标准\|off>` | 该脉络的默认完成标准 |
| `/role-del <名字>` | 删除；要求该角色下无事务，否则提示改用 `/merge` 或 `/move` |

**其它**

| 命令 | 作用 |
|---|---|
| `/tick` | 手动检查提醒 |
| `/llm` | 查看当前智能层与配置（**不显示 Key**） |

约定：所有 `<id>` 都可只输前几位；角色/事务都按名字或 id 前缀匹配。

## 十三、功能范围（V1）

### 13.1 做的功能

每项都对应 12.4 节里的实际命令，缺一条即视为未交付。

1. **新建事务**：自然语言进入，自动推断 `kind` 与角色候选，`intent` 可后补。 → `/new`、直接说话
2. **角色管理**：增删改、折叠/静置、**合并（重定向）**、设置默认完成标准。 → `/role-add` `/role-rename` `/role-silence` `/role-dod` `/role-del` `/merge` `/roles`
3. **视图**：
   - 今天视图（含**顺延标记**）
   - 按角色视图
   - 所有事务视图（可切 `open` / `closed` / `all`）
   → `/today` `/role` `/all` `/roles`
4. **状态与调度操作**：开始 / 暂停 / 完成 / 放弃 / 改 `kind` / 排期 / 移出今天 / 改完成标准。 → `/start` `/pause` `/done` `/drop` `/kind` `/today-pin` `/dod`
5. **提醒**：到点通知、错过标记、合并摘要。 → 每轮自动 + `/tick`
6. **等候**：`WaitingOn` 记录与跟进提醒（`follow_up_at` 可更新）。 → `/wait` `/followup`
7. **进度记录与回放**：`TaskRecord` 只追加日志 + `progress_note` 重建。 → `/note` `/task`
8. **草稿辅助（最简版）**：`Artifact` 版本化 + 采纳 + 局部重做。 → `/draft` `/revise` `/artifact` `/accept`
9. **恢复契约**：返回完整 `RestoreView` 与 `next_actions`。 → `/task`
10. **透明弱排序**：信号 + 理由展示；给单条事务的排期参考。 → `/today` `/all` `/plan`
11. **跨角色改归属**：移到别的角色视图 / 摘掉角色标签。 → `/move` `/unrole`
12. **拆步骤**：把大事务拆成几步（只拆，不排序）。 → `/steps`
13. **本地 Web 界面**：今天 / 全部 / 已结束 / 角色四视图 + 恢复契约详情页（含状态迁移按钮）+ 新建事务（可排期）。仅监听回环地址。 → `python -m freeagent.web`

### 13.2 先不做的（V1）

- 多渠道自动采集（邮件 / 日历 / 聊天）—— **断点 1「入口散」因此未被验证**。
- 复杂优先级打分算法 —— 只有透明的确定性弱信号。
- 跨应用 Computer Use / 浏览器操作。
- 多设备强一致同步 —— 原型本地单库。
- **角色知识的语义检索**（向量那一腿）—— BM25 + 近期回落已实现（3.6），
  向量刻意不做：要 embedding 就得联网，而「断网照常能用」是硬性质。
- **角色知识的写入入口**（CLI / Web 命令）—— 服务层已就绪，
  接线时再补；不先做是因为入口散（第一条）本身还没解决。
- 流式输出 / 多轮对话上下文 —— 每次调用都是**无状态单轮**，上下文由恢复契约（第八章）显式提供。
- **FreeAgent 主动打断 agent 提问**（V1.14 更正）—— V1.13 这里写的是「委派途中的
  插话在 V1 上无解」，**那是把两件事混成了一件**。实测区分清楚：
  - **agent 提问、用户答 → V1 完全可行**，且答案附在挂起的 tool 调用上、
    **不污染主线**（实测闭环 9.2 秒，见 11.8.1）。
  - **FreeAgent 主动插话 → 才真的无解**：依赖 `session.generate`，V1 没有；
    子会话（`parentID`）与 `fork` 实测都不继承上下文（对照组继承、两者不继承）。
    唯一的 `/session/{id}/message` **必然写进历史**。
  所以待取舍的只剩第二种：接受主线被污染（能力优先），还是不做（干净优先）。
  倾向能力优先 —— 但这是**产品决策**。需求方已明确「不要实时看过程」，
  而「中途插一句」属于**另一件事**，别混为一谈。
- **委派的常驻执行器**（V1.14 换理由）—— `--watch` 实测**能**常驻并自动取走委派，
  但先不把它做成服务。**理由已换**（V1.13 那两条不再是主因）：
  ① **交互要求执行器全程存活**（见 11.8.1），而 `run_once` 跑完就退、`--watch`
  只会空转 —— 这不是「监控」问题，是**交互链断在这里**；
  ② 等待答复期间必须**阻塞在库上并由答复唤醒**，不能靠固定间隔轮询；
  ③ 真机点一次飞书卡片仍未验（见 11.8.1 落地状态表），**先验那一米**。

- 任务软删除 / 归档。
- Web UI 的写操作仅限白名单（新建 / 状态迁移 / 排期）—— 编辑草稿、拖拽排期、实时推送、登录鉴权都不做。

## 十四、V1 假设与成功判据

> V1.0 最上层的问题：它把多渠道采集排除在外，而「入口散」正是四大断点之一 —— 于是 V1 并未验证自己的核心假设，做完可能只得到一个「更好看的 todo list」。

### 14.1 待验证假设

- **H1**：角色视图能降低跨角色切换时的上下文恢复成本。
- **H2**：显式 `state` / `kind` 正交 + 恢复契约，能让中断事务在极短交互内恢复。

### 14.2 判定标准

- **H1**：在 5 个以上角色的数据集下，跨角色事务的「重新捡上下文」次数相比无角色视图的基线下降。
  ⬜ **未测** —— 连数据集都还没有。
- **H2**：场景 S5（跨角色中断恢复）中，从打开事务到拿到下一步动作，**交互轮数 ≤ 2**。
  ⚠️ **已被测量，但只到「未被推翻」**（V1.9，`tools/probe_h2_recovery.py`）：
  6 个自造场景全部 ≤ 2 轮。S5 的定义是那次补上的（见 8.3），场景由同一个探针挑选、
  且「够不够可执行」有一部分判据写死在探针里 —— **这不是证明**。真人用才算。

> **一个方法论备注。** 探针跑出来的东西里，最有价值的一条不是「6 个场景
> 全达标」，而是它顺手抓到 8.2 那处**假文案**（逾期行说「已顺延」，而
> `/task` 不触发 rollover）。那个 bug **读代码看不出来** —— 文案挺顺，
> 而且还有一条测试把它锁成了期望行为。**只有真跑一遍、对着库里的实际
> 状态核对，才会露出来。**
>
> 这也是 17.3「先量再改」那条纪律的又一个证据：探针的价值常常不在它要测
> 的那个数，而在它**顺带撞见**的东西。

### 14.3 风险

- **H1 失败** → 角色视图只是心理安慰，应砍掉多角色设计，退回单列表 + 标签。
- **H2 失败** → 恢复契约信息量不足，需补更多上下文投影（此时才值得上脉络级记忆）。
- **两者都失败** → V1 退化为「一个更好看的 todo list」，应重新审视问题定义。

## 十五、不做什么

- 不把任何事都自动变成事务。
- 不设计成每天需要填很多字段才能用的系统。
- 不在没被问的时候高频扰民（顺延与提醒一律合并成摘要）。
- 不强求角色分类永远准确 —— 允许改、允许模糊、允许合并。
- **不替用户做真正的价值取舍** —— 只把信息摆清楚（弱信号必须可解释、可反驳）。
- 不伪造事实 —— 助手生成的草稿只复述已知信息，未知处标 `[TODO]`。

- **多执行器（"Agent 之上的 Agent"）**：规范**已写**（11.10），⬜ **代码未实现**。
  入口是 `/agents`（看能力探针结果）与 `/ask <执行器> <问题>`（**只做问答，不接管**）。
  **刻意不做自动触发委派** —— 理由见 11.10.5。地基是 11.8.1 那个适配器注册表。
- 角色冲突提示更明确：哪些事同时在竞争同一段注意力。
- 完成标准控制细化：按角色 / 按任务的松紧调节。
- 更强的执行能力：授权后接入本机 / 浏览器操作。
- 通知渠道扩展：桌面通知（需先解决「系统不运行时漏提醒」这一 V1 限制）。

各扩展方向的**取舍依据与外部参考**见第十七节 —— 本节只说「要做什么」，第十七节说「凭什么这么做、哪些不做」。

## 十七、外部 harness 借鉴评估

> **性质：非规范性。** 本节记录对 `deepseek-harness`（下称 **dsh**）与 `Qwen-Live-Harness`（下称 **qlh**）的评估结论与取舍理由，**不构成实现契约**。任何一项进入实现前，仍须按第十二章的技术选型与分层纪律落地。
>
> 评估日期 2026-09-30，依据两个仓库当时的源码与官方文档。

### 17.0 前提：类别错位，评估的本来不是同一类东西

dsh 与 qlh 都是**通用编码 agent 基础设施**。dsh 的 `packages/` 有 60 个包，含 `lsp` `mcp` `ssh` `terminal` `browser-use` `computer-use` `sandbox` `subagent` `ptc-runtime` `spill` 等；qlh 围绕实时音视频模型构建、面向 macOS 桌面。

本项目是**个人事务助手**，唯一通往「本地执行代码」的能力是委派（11.8），其余全是事务 / 角色 / 提醒 / 视图。

**所以大部分架构层经验不适用** —— 把本项目改造成 harness 是类别错误，且会直接毁掉「零依赖、克隆即跑」这一现有性质（见 17.4）。真正值得借鉴的只有两类：

1. **机制** —— 恰好命中本项目**已在文档里承认**的缺口：9.2 的漏提醒、13.2 的角色级可检索记忆、11.8 的委派后端硬编码。
2. **纪律** —— 文档与流程的组织方式，几乎零实现成本而长期收益高。

### 17.1 结论一览

| 来源 | 借鉴对象 | 结论 | 落点 |

| dsh `packages/schedule` | 持久提醒记录 · 显式时区 · 重复规则 · 乐观并发 | **采纳（部分）** | 9.2、9.3、11.8 |
| qlh `src/adaptor/acp-adaptor.ts` | ACP 开放协议替代硬编码后端 | **分两步，先做接缝** | 11.8 |

| dsh `docs/` | 复盘 · 持久化变更记录 · 文档契约校验 · SAFETY.md | **采纳** | 工程流程 |

### 17.2 Tier 1：直接命中已记录缺口

#### 17.2.1 持久提醒（dsh `packages/schedule`）

**对方的做法。** 提醒是**独立于会话激活的持久记录**，由 Host 定时器投递回原会话。规则支持 `after` / `at` / `every` / `daily` / `weekly` / `cron`（Vixie 五字段，规范化后存储）。三个关键细节：

- **只存规范化 UTC 目标时刻 + 原始重复规则**，原文的理由是「replay never depends on ambient time-zone state」；`daily` / `weekly` 另存**显式 IANA 时区**。
- **补发只取最新一条**，原文：「it sends only the latest due occurrence... Missed occurrences do not accumulate」。
- 改期走**乐观并发**：提交完整 `expected` 记录，与当前记录不符则报冲突而非覆盖。
- 夏令时：空洞跳过，重叠取更早的 instant。

**本项目的缺口。** 9.2 的提醒是**纯轮询 · 无时区 · 无重复规则**，`reminder_time` 是单个瞬间。后果有二：

1. 「每天早上八点」这类**墙钟重复提醒无法表达** —— 一旦遇上夏令时切换，语义即漂移。
2. 同一个 `reminder_time` **只会触发一次**（去重令牌 `at:<iso>`），改期之外没有第二次机会；「系统不运行时不会通知」这个 V1 限制因此**没有任何补救路径**。

**采纳什么。** 时区显式化 · `daily` / `weekly` 重复规则 · 提醒与委派状态变更的乐观并发。

**不采纳什么。** 补发策略**不抄**。dsh 的「只发最新一条」对编码会话合理（补一大串旧事件只会挤占上下文），但对个人事务助手**更差** —— 告诉用户「你错过了 3 件事」比「你错过了这件事」更糟。**保留 9.3 / 9.4 现有的「如实标注已错过 + 合并摘要」语义**，只把触发机制从「靠进程活着」换成「靠持久记录 + 定时器」。

#### 17.2.2 委派后端接缝（qlh `src/adaptor/acp-adaptor.ts`）

**对方的做法。** 用 **ACP（Agent Client Protocol）** —— JSON-RPC over stdio 的开放协议 —— 对接 Qwen Code / Qoder CLI / Codex / Claude Code / Gemini CLI，每个后端一个适配器。dsh 内置 `packages/acp`，同样走这条协议。

**本项目的缺口。** `services/opencode_server.py` 是 450 行手写 HTTP/SSE 客户端，**只对接 opencode 一个后端**，并把该后端的字段名写死在闸门判定里。这正对应 11.8 记下的坑：opencode 升到 V2 后 permission 字段名全变，旧字段被**静默忽略**、闸门随之失效，目前只能靠「查主版本，不是 V1 就拒绝派发（退出码 2）」兜住。

**采纳什么 —— 分两步，顺序不可颠倒。**

1. **先做接缝。** 把后端特有字段名（`bash` / `external_directory` / `{"reply":"once"}` / V1 权限模型）关进一个**带版本号的适配器接口**后面。此后 V2 改名就从「运行时闸门失效 + 退出码 2」退化成「改一个文件」。
2. **再评估 ACP。** 只有当**多后端确有需求**时才上。`--tool-gate` 需要的「挂起 → 卡片 → 回答 → 继续」与 ACP 的**权限请求 / 响应机制**语义吻合，qlh 的 `permissions/permission-broker.ts` 与 `permission-delivery.ts` 就是这一层的实现，技术上通；但具体方法名与时序须在实现时对照协议版本核实，本节不作断言。真正的代价在上 ACP 会失去 `opencode_server.py` 里那套**配置隔离**（`XDG_CONFIG_HOME` 是全替换、`OPENCODE_CONFIG` 是合并语义的 fail-open 差异，见 11.8.1）与 **Windows 进程组收口**（14 次探针各漏一个进程、累计约 12.5 GB），**每个适配器都要重做一遍隔离**。这笔代价必须认。

#### 17.2.3 角色知识的混合检索与来源自报（qlh `src/memory/`）

**对方的做法。** 记忆模块约 20 个文件，检索是 **BM25 + 向量 + tail 混合**。值得抄的不是规模，而是**返回值的形状**：它报告自己**是怎么找到的**，而不只报告找到了什么 —— 命中来源分解、是否被截断，都在返回值里。

**本项目的缺口。** 13.2 与第十六章都记着「角色级记忆只有 `Role.note` 自由文本，没有可检索的脉络知识」。

**采纳什么。** 角色知识检索走**混合**（BM25 一半由 SQLite FTS5 承担，**零依赖不破**），且**自报来源**。

「自报来源」这一条尤其该抄，因为它与本文档已有的立场同构：第七章要求每条排序信号必须附理由、必须标注「启发式提示，不是评分」。**检索同理** —— 回答「你凭什么这么说」时只列结果不列来源，等于要求用户盲信。

**不采纳什么。** qlh 的「多个记忆库（新建 / 选择 / 重命名）」在角色维度上**弱于**本项目第三章的角色模型（本项目有多对多归属、`/merge` 原子重定向不丢历史、`/role-silence`、按角色默认完成标准）。**保留第三章的角色代数，只在其上补可检索知识。**

### 17.4 明确不借鉴

1. **Cordis / everything-is-a-plugin（dsh）**。本项目核心 `dependencies` 为空、飞书是 optional extra，「无需安装依赖即可运行」是**真本事**而非妥协。引入插件框架等于引入依赖 + 生命周期 + 失败模式，换来对一个单用户个人助手无用的东西。dsh 自身也把整个项目标为 developer preview 且明示「会有破坏性变更」。
2. **流式输出 / 多轮对话上下文（dsh / qlh）**。13.2 把「无状态单轮」列为**不做**，而这是**设计立场、不是待修缺陷**：第五章的 `TaskRecord` 是唯一真源，上下文由第八章的恢复契约显式提供。加一段可变的聊天历史，等于引入第二个可能与日志矛盾的事实源。dsh / qlh 解决的是开放编码会话的问题，不是本项目的问题。
   - 顺带澄清一处**易被误读处**：13.2 记的「`/draft` 产出质量取决于输入信息量」，正确解法**不是**加历史，而是让 `/draft` 与 `/steps` 也吃**恢复契约**（`RestoreView` 已存在）。**用本项目自己的解法修，别引入一个外部机制来绕。**
3. **编码工具链那一整片**（`lsp` / `mcp` / `terminal` / `ssh` / `browser-use` / `computer-use` / `sandbox` / `spill` / `ptc-runtime` / 子 agent 团队）。与本项目问题域无关。
4. **实时音视频 / 视觉监控（qlh）**。qlh 自己就写明采样与推理会带来延迟与误判、「monitoring is not a safety-critical alarm system」。本项目的提醒是「时间到点」这一类**确定性条件**，不需要模型在环 —— 引入模型判断只会把 9.2 的确定性换成不确定性。

### 17.5 借鉴时不得破坏的现有性质

本节任何一项落地，都**不得**破坏下列已成立的事实。它们是本项目相对两个 harness 的真实优势，**不是待优化项**：

- 核心零依赖 + 飞书可选 extra，「克隆即跑」成立。
- `services/llm/provider.py` **刻意不 import `domain` / `storage`**，自带 `RoleHint` / `TaskRef` / `SignalRef` 窄投影。
- `TaskRecord` 只追加日志为唯一真源；`progress_note` 是派生缓存；`Artifact` 永不原地覆写。
- 恢复契约 `RestoreView` 缺项即失败。
- `FrozenClock` 注入 → 顺延、提醒、排序全部确定性可测。
- `can_select_view` 区分「看了没匹配上」与「压根不做选路」，避免离线路径给每句话挂免责声明。
- 降级如实打印「已退回规则推断」，且降级原因带**真实服务商名**。

## 十八、附录：交互流程示例

> 以下示例已按 V1.1 模型更新，与正文规范一致。

### 示例一：新事务进来

用户：
> 「下周二要交的销售周报初稿，先理一版。」

助手内部：
1. `classify()` 推断 `kind = ACTION`（无等候/提醒特征）。
2. 角色匹配「销售周报」→ 候选「工作项目 A」，置信度达标，**无需追问**。
3. 识别出「下周二」→ 建议 `scheduled_for`；「初稿」→ `definition_of_done` 线索。

助手回复：
> 已记下，角色「工作项目 A」。
> 「下周二要交的销售周报初稿」— 动作类，排在下周二（周二=日期），完成标准暂取角色默认值。
> 需要我先理一版草稿吗？

用户确认后：
- 创建事务：`state=INBOX`、`kind=ACTION`、`role_ids=[工作项目A]`、`scheduled_for=下周二`。
- 追加 `TaskRecord(type=created)`。
- 用户若回答「先理一版」→ `state=ACTIVE` + 创建 `Artifact(v1, DRAFT)`。

### 示例二：今天视图

早上用户输入 `/today`：

1. **先执行顺延检查**：`上周就该交的材料` 原定 09-20，被顺延到今天，并产出一条合并摘要。
2. **再全局排序渲染**，每条附命中信号与理由。

实际输出（**由实现生成，非手写**）：


Web 界面（`/api/today`）拿的是同一份数据，只是把信号拆成独立条目：

```text
1. 【家庭】孩子周四要交的材料清单  [60 分]
     该催 孩子带回来 了（跟进日已过 1 天）  (+50)
     排在今天  (+10)
2. 【家庭】上周就该交的材料  [15 分]
     排在今天  (+10)
     还没开始  (+5)
```

注意等候那条排第一 —— `OVERDUE_WAIT +50` 权重最高，**理由里点名了要催谁**。
助手没有说「你应该先做它」，只是把这条线索摆在最显眼的位置。

### 示例三：做事中断

用户在「销售周报初稿」里让助手写了初步草稿，中途被叫走。

助手：
- 追加 `TaskRecord(type=artifact_created)`，存 `Artifact(v1, DRAFT)`。
- 追加 `TaskRecord(type=note, content="草稿写到有了框架，还没填数据")`。
- `state = ACTIVE`，写入 `last_resumed_at`，更新 `progress_note`（派生缓存）。

用户回来输入 `/task <id>`，得到**恢复契约**返回的 `RestoreView`：

```text
销售周报初稿 · 动作 · 进行中
角色：工作项目A        生效完成标准：先给我能用的就行（来自角色默认值）
草稿：version 1（草稿）— 有框架，缺数据
进度：有框架了，还没填数据
下一步建议：
  · 草稿已到 version 1：继续改，还是重写
  · 先把第二部分数据按你给的数重填
```

用户直接说「把第二部分数据按我给的那个数重填一遍」即可 —— 恢复成本 ≤ 2 轮。
