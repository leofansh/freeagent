## 顶导览

### 0.1 一句话

一个**本地优先**的个人事务助手：把「今天该做什么」这件事从你自己的记忆里搬到
一个**可审计、可反驳、不替你决定**的系统里；再把真正需要写代码的那部分，交给
外部执行器（OpenCode），自己在中间当**闸门**而不是**代理人**。

### 0.2 执行摘要（为什么长成这样）

原型面对的痛点不是「记不住事」，而是**四件互相打架的事**：

| 痛点 | 解法 | 落在哪一章 |
|---|---|---|
| 1. 角色多，事情杂在角色之间来回切 | 角色是**视图**，不是文件夹；事务可挂多角色 | 二 |
| 2. 优先级冲突靠直觉，缺少明确依据 | 给**带理由的弱信号**，必标「不是评分」 | 三·3 |
| 3. 事情中断后回不来，助手失忆 | **恢复契约**：打开事务必须返回 7 项齐备 | 三·4 |
| 4. 反复提醒同一件事，但漏了没记录 | 提醒**两阶段**（查+ 送达确认），不承诺恰好一次 | 三·5 |

后来长出两条更硬的主线，是 V1.2 之后加的：

- **委派治理**：让外部程序改你的代码，但**闸门在服务层**、**逐次授权**、
  **沉默≠同意**。见第四章。
- **通道多路化**：Web / 飞书 / 微信**对等**，一份能力一份实现。见第六章。

> **市场定位（V1.61）**：市面 Today AI（此间无限，齐俊元）与 OpenAI Dots（2026-09 DevDay）
> 都是「商业云 AI 同事」，强在跨应用连接与自主执行；FreeAgent 刻意不做的正是这两点
> （本地优先 / 零依赖 / 不做子任务 / fail-closed）。对齐点在「连续性 + 人在回路」，
> 分歧点在「是否替你对外行动、是否读外部数据源」—— 后者是 FreeAgent 的护城河，不是短板。
> 三者差异化并排见 `现状速读.md` §10；系统如何守住「不替你发 / 不替你决定」的边界，见原契约
> **§11.22 显式触发边界清单**。

### 0.4 术语表

| 术语 | 含义 | 不是什么 |
|---|---|---|
| **角色**（Role） | 人演的职责身份，事务的归属**视图** | 不是文件夹，一个事务可挂多个 |
| **执行器**（executor） | **外部程序**（OpenCode 等），真正动手改代码 | **不叫 Agent** —— 见下 |
| **通道**（channel） | 用户能触到FreeAgent 的一个入口（终端/Web/飞书） | 不是执行器，通道不干活 |
| **闸门**（gate） | 服务层里的授权检查函数 | 不是 UI 逻辑，UI 只是调用方 |
| **弱信号** | 确定性的、可解释的排序理由 | 不是评分，不构成结论 |
| **顺延**（rollover） | 未完成事务自动带到今天 | 不是「逾期分区」 |
| **恢复契约** | 打开事务时必须返回的 7 项结构 | 不是摘要，是可验证的结构 |

> **术语硬约束**：「Agent」这个词在本项目里**已被外部程序占用**。
> 因此内部程序一律叫「**执行器**」。禁止引入第三个「Agent」含义 ——
> 「角色」是人演的职责身份，「执行器」是外部程序，两者正交。

## 一、问题与原则

### 1.1 问题定义

用户的真实场景不是「事情多」，而是**角色多**：既是学生又是开发者又是家庭成员，
每件事都属于某个身份，而身份之间没有共同的时间轴。所以待办清单里最贵的成本
不是记录，而是**在事情之间切换时重新装载上下文**。

由此推出四个可验证的目标：

- 打开任意一件事，**≤ 2 轮对话**内能开始下一步（量化指标 H2）。
- 任何排序结论都能**指出理由**，并允许用户反驳。
- 任何状态变更都有**只追加的记录**，可回放。
- 任何触碰外部系统的动作都有**显式授权**。

### 1.2 核心设计原则

1. **本地优先、单库、断网可用。** 不引依赖，不引服务端。
2. **正交建模。** `state` / `kind` / `scheduled_for` 三字段各管一件事，不混成 `status`。
3. **可以恢复上下文。** 任何事务都能被打开，且打开后信息足够决策下一步。
4. **确定性优于聪明。** 需要判断的地方才用模型，且降级必须告知。
5. **人在回路里。** 不可逆动作前必须有一次显式确认。

### 1.3 什么不算问题

- 「缺少优先级打分算法」——**不是问题**。见1.4。
- 「需要多设备同步」——V1 不做，理由见九·3。

### 1.4 对「优先级」这个伪问题的正面回答

V1.0 自相矛盾：痛点说「优先级冲突靠直觉、缺少依据」，答案却是
「助手不替你排序，把今天的事摆出来」。如果今天有 5 件事，用户仍要自己从头排——
决策负担没降低，只是从 8 件事变成 5 件事。

**结论：不追求「替你排对」，追求「让你排得更省力」。** 做法是给确定性、
可解释、可反驳的弱信号（第三章），而不是做一个隐藏的评分模型。
理由：隐藏评分模型一旦出错，用户无法察觉、无法反驳，而他会照着它行动。

## 二、领域模型

### 2.1 角色是视图，不是文件夹

`Role` 是「人演的职责身份」。关键设计：**事务到角色是多对多**。

- 事务可挂多个角色 → 一件事跨身份时不必复制。
- 角色可静置（`/role-silence`，省略参数即静置）→ 折叠当前不关心的脉络。
- 角色可**合并**（`/merge`，原子重定向，历史可回看）→ 脉络演进不留疤。
- 角色有 `note`（**参与角色推断**）与 `default_dod`（默认完成标准）。

`Role.default_agent` 字段存在，用于指定该角色默认派给哪个执行器（见 4.6）。

### 2.2 事务模型：三字段正交

V1 把「进行中/已放弃/在等谁/排期到明天」混进一个 `status`，导致
「等谁」和「做完」互相覆盖。V1 正交化为：

| 字段 | 管什么 | 取值 |
|---|---|---|
| `state` (`TaskState`) | 这条事务**处在哪个阶段** | `inbox` / `active` / `waiting` / `done` / `dropped` |
| `kind` (`TaskKind`) | 这条事务的**形状** | `action` / `wait` / `reminder` |
| `scheduled_for` | 它**排在哪天** | ISO 日期或空 |

三字段互不覆盖：`kind == WAIT` 且 `state == ACTIVE` 是「在等某人」；
`scheduled_for` 是明天而 `state == ACTIVE` 是「今天没排上但还没放弃」。

合法迁移由 `ALLOWED_TRANSITIONS` 给出（领域概念，给出**目标状态**）；
**动作名 ≠ 状态名**：动作是接口概念（`start`/`pause`/…），映射由**接口层**翻译成
`allowed_next_states[].action`。前端若把状态名直接当动作 POST，会得到 404。
这个坑踩过两次，故有测试守着。

### 2.3 等候：事务背后是人

`kind == WAIT` 时必须有 `WaitingOn`，记录**在等谁**（`waiting_on`）与
**从什么时候开始等**（`waiting_on.since`），并可设 `follow_up_at`。

- `waiting_on` 回答「这条事务卡在别人身上」。
- `follow_up_at` 驱动 `OVERDUE_WAIT` 弱信号（第三章）。
- 关系对象目前是自由文本、不可检索 —— 这是已知缺口，见附录 C·5。

### 2.4 记录是唯一真源

`TaskRecord` 是**只追加**的日志，事件类型见 `RecordType` 枚举。
所有进度由它重建（`progress_note`），不另存一份「当前进度」字段 ——
两份会漂。

草稿走 `Artifact`：**版本化**。`/revise` 产生**新版本**，旧版保留；
`/accept` 采纳某一版。版本链是给人回看的，不是覆盖写。

### 2.5 删除：不可恢复的硬删（V1.42）

`DROPPED` 是终态但**可逆**（记录全保留）。用户要的是真删，于是 V1.42 加了
`TaskService.delete_task/delete_many`，返回被删快照。

闸门（fail-closed，理由互相可区分）：

- 委派正在跑（复用 `attempt_state` 同一份推导）→ 拒
- 有待批项（`pending_for_web` 过滤 `task_id`）→ 拒

副作用：FK 级联清 `roles`/`artifacts`/`records`/`deps`；删前清 `delegate_progress`
悬空行。`pending` 判定以注入的 `has_pending` callable 注入（tasks ↔ approval
不互相依赖，`app.py` 装配时用 `ApprovalStore.pending_for_web`）。

入口三处：Web 详情页按钮 + 多选批量（两道浏览器 confirm）、终端
`/task-del <id> confirm`（同一命令敲两次，**避免在命令层嵌 `input()` 把 Web
请求线程挂死**）。

## 三、今天、排序、恢复、提醒

### 3.1 今天视图与顺延

`/today` 的顺序是**先顺延，再全局排序**。顺延有收口：未完成事务自动带到今天，
并留**顺延标记**（不是「逾期分区」）。

`rollover` 的规定（原文见 6.3）：顺延发生在读取时而非写入时，
所以「今天」这个概念必须由可注入 `Clock` 提供，测试用 `FrozenClock` 冻结。

### 3.2 排序：透明弱信号

每条信号产出 `(code, weight, reason)`：

- `reason` 是**面向用户的中文说明**，必须与任务一起展示。
- 输出必须标注「**启发式提示，不是评分**」。
- 用户可以反驳任一信号。

#### 7.2 信号权重表（规范性）

> 表中同时给出**枚举名**与**枚举值** —— 代码里 `SortSignalCode.OVERDUE_WAIT` 的
> `.value` 是小写 `overdue_wait`，落库与测试断言都用小写形式。

| code（枚举名 / 枚举值）| 权重 | 触发条件 |
|---|---|---|
| `OVERDUE_WAIT` / `overdue_wait` | +50 | `waiting_on.follow_up_at` 已过，且仍未跟进 |
| `DEADLINE_RISK` / `deadline_risk` | +40 | `due_time` 距今 < `DEADLINE_RISK_HOURS`(24) 小时，且未完成 |
| `DEPENDED_ON` / `depended_on` | +30 | 该事务被其他未完成事务依赖（V1 用 `Task.blocked_by: list[str]` 手工标记） |
| `RESUME_STALE` / `resume_stale` | +20 | `state == ACTIVE` 且距「最后一次恢复或最后一次更新」超过 `RESUME_STALE_DAYS`(3) 天（`last_resumed_at` 为空时回退 `updated_at`，这样「刚 start 完就再没碰过」也算中断） |
| `WAITING_TOO_LONG` / `waiting_too_long` | +15 | `kind == WAIT` 且 `waiting_on.since` 距今超过 `WAITING_TOO_LONG_DAYS`(7) 天 |
| `SCHEDULED_TODAY` / `scheduled_today` | +10 | `scheduled_for == today` |
| `INBOX_UNSORTED` / `inbox_unsorted` | +5 | `state == INBOX` |
| `ENERGY_FIT` / `energy_fit` | +8 | `reminder_time` 落在用户设置的精力档位（早晨 / 下午 / 晚上） |

权重与触发条件均为**规范性**内容，代码中的 `SORT_SIGNAL_WEIGHTS` 常量必须与此表
逐项一致。

**排序算法**：① 排除 `state ∈ {DONE, DROPPED}`；② 逐条计算命中信号求和；
③ 总权重**降序**，同权重按 `entered_at` **升序**（先进先出）；
④ **每个任务携带全部命中的信号**，不是只有最高那条。

**精力档位**：固定三档（早晨/下午/晚上），V1 不做自定义。`ENERGY_FIT` 依据
`reminder_time` 或 `scheduled_for` 落在哪档命中；未设置档位则不命中。

### 3.3 恢复契约

原则「可以从任何事务进入，恢复上下文」在 V1.0 里只是一句愿望。V1.1 把它变成
**可验证的结构**：打开事务必须返回 7 项齐备的 `RestoreView` ——
`task`、`records`、`artifacts`、`waiting_on`、`depended_by`、`next_actions`、`signals`。

**量化目标 H2：从打开到下一步 ≤ 2 轮。**

### 3.4 提醒：两阶段，不承诺恰好一次

原设计有个消费型 `check()`，把「查询」和「送达」混在一起，于是无法回答
「到底送没送到」。现规范是两阶段 API：

- `ReminderEngine.due()` —— **纯查询**，返回该发的。
- `acknowledge()` —— **送达确认**。

**明确不承诺恰好一次**。宁可重复也不静默漏，因为重复的代价（多看一条）远小于
漏掉的代价（彻底忘记）。超过 `MISSED_AFTER` 未跟进的提醒标记为「错过」。

轮询式提醒的**已知边界**：两个进程都关就收不到。Web 界面**不解决**这个缺陷。

## 四、委派治理

> 本章收拢原契约 11.8（逐次授权）、11.12（职责边界与委派契约）、11.13（提示词归谁写）、
> 11.16（飞书进度卡动态更新）、12.7.2（两阶段委派）、12.8（Web 实时委派）、
> 12.9（产出验收）、12.10（反馈回流）、12.11（恢复与备份）—— 一条主线。

### 4.1 为什么要委派

有些事用户根本不该亲手做：改代码、跑测试、迭代修复。让模型「给建议」是不够的，
因为**建议不落到磁盘上**。于是有了外部执行器。

但一旦引入外部程序，就出现三个新风险：**它会改错东西**、**它会跑到没授权的地方**、
**它会做一半停下来**。本章其余小节都是为这三条风险写的。

### 4.2 三道闸门（规范性）

派发之前必须依次过：

1. **项目路径白名单** —— 三层校验：`is_duplicate`（原始路径非绝对路径直接拒）→
   绝对路径 → `resolve()` 后仍在白名单内。用 `relative_to()` 而非字符串前缀
   （`D:\proj` 会匹配 `D:\project-x`）。
2. **必须先 `/start`** —— 没进 `active` 的事务不派。
3. **逐次授权** —— 见 4.3。

闸门在**服务层函数**里，不在 UI。UI 只是调用方。

#### ⚠️ 闸门必须先跑，这是本条不可协商的部分

顺序是：**查执行器 → 用白名单过滤 → 把过滤后的结果喂给 LLM → LLM 提方案 → 用户确认 → 执行**。

为什么第2 步不能省：若把「所有已知项目」喂给 LLM，它会挑一个**当前无权访问**的
项目，然后满口答应「我去 OpenMOS 里查」—— 实际执行时才被闸门拒掉。用户的体感是
「它说能做，结果没做」，**这比一开始就说「你没授权」坏得多**。

这条与 5.5「绝不自动触发委派」同源：**不可复核的信号不许驱动动作**。
LLM 的判断就是这种信号 —— 它可以错，而闸门不会因为它自信就放行。

同理：**名字解析不放进闸门**。`check_project_allowed` 里有会起子进程的调用时，
闸门内部会抛 `FileNotFoundError`（执行器没装），失败方式不可预测。
名字→路径解析放在**闸门之前**，闸门仍然只收路径、只认白名单。

### 4.3 执行期逐次授权

执行器每一步工具调用都挂起，发一张卡，**允许 / 拒绝 / 停止**三路。

**三条纪律（规范性）：**

1. **沉默≠同意。** 超时未答按**拒绝**处理，不按「默认放行」。
2. **只有发起人能批。** 发起身份（`requested_by`）与兜底身份是两个字段，
   V1.40 修的就是「两个语义打架」—— 一条 Web 发起的委派被 Web 面板误判成
   「飞书发起、不可决」。现在兜底身份从发起身份里**拆出去**。
3. **允许范围有上限。** 工具步数上限 + 时间上限，超限自动挂起。

授权判定是事后要能对账的东西，所以**不能纯删除**（V1.41）：执行中只保**当前挂起卡**
（发下一张前撤掉已定案旧卡，`_retire_settled_cards`），但收尾进度卡正文改为
「统计 + 最近判定明细（末 5 条 + 共 N 条）」，**全量明细在库里**
（`pending_approvals` 逐条：动作、结论、谁批的）。

旧卡上的「停止这条委派」按**凭据**生效（`is_stop_requested(credential)` 只认
当前 pending 凭据），所以撤掉已定案卡**不损失任何停止能力**。

> ⚠️ **已纠正的错误**：曾想用「不传 `--auto`」当闸门。这是错的 ——
> 缺省值不等于授权，攻击面/误用面都在。改成**默认拒绝 + 显式逐次授权**。
>
> ⚠️ **真机验证状态**：允许/拒绝已真机点过（11 连点带真 message ID）；
> **「停止」按钮真机未验**。这是信任关键路径，见附录 C·6。

### 4.4 两阶段委派交互

实测痛点（2026-10-05，用户原话「用户体验回到了终端时代了」）：

```
/delegate OpenMOS |默认脉络 | 检查用户密码定期修改完成情况
[拒绝] 项目路径必须是绝对路径，收到「OpenMOS」。
/delegate D:/PyCharmOpenMOS | ...
[拒绝] 「D:\PyCharmOpenMOS」不在白名单里。当前白名单：...
```

暴露两件错：**白名单是过期的**（用户已在控制面授权过），而**没有一个字告诉他
能填什么**。于是只能猜路径。

| 阶段 | 谁做 | 产出 |
|---|---|---|
| 一 | **LLM 沟通** | 意图、角色、项目、需求 |
| 二 | **用户确认「怎么执行」** | 一份可核对的方案（不是一句「好的」） |
| 三 | 执行 | 逐次授权那道卡**仍在**，一道不减 |

配套三条：

- **名字即引用。** 项目用名字引用（大小写不敏感 —— 实测三个项目的显示名与
  目录名大小写全不同：`FreeAgent`/`freeagent` 等），路径由系统解析。
  **用户不该被要求抄绝对路径。**
- **「列出来≠ 已授权」要守住。** 未授权项目**灰掉**而不是藏起来 —— 藏起来用户
  会以为系统坏了。
- **Plan / Build 模式。** Plan 允许追问、改方案、读项目，拒绝建事务/委派/改文件；
  Build 允许建事务与委派（授权卡仍在）。
  **一处刻意偏离 OpenCode**：`build` 的权限集里**不**设 `question: deny` ——
  遇到不确定时应允许**只读式追问，但问完必须停下等回答**，不许连问带做。

**Plan 状态必须落盘**（12.7.2，规范已写代码未实现）：通道已按 chat 保存 `Repl`
实例，但那个 dict 是 **LRU** 的，`max_chats` 触发淘汰时会**静默丢弃** Plan ——
用户回来发现助手失忆了而**没有任何提示**。这与「状态文件假绿灯」同型：
**东西没了但没人说，比报错更糟**。

### 4.5 职责边界与委派契约

**三分法（一条可以判的线）：**

| 层 | 判据 | 例子 |
|---|---|---|
| FreeAgent | 需要人的授权/取舍 | 今天该做什么、能不能派这个项目 |
| 执行器 | 判定已定，改代码达到它 | 怎么改、先改哪个文件 |
| 人 | 价值取舍与对外承诺 | 这件事该不该做 |

**人不可外包的三件事**：定优先级、决定对外承诺、判断「够了没有」。

**模式必须是委派的属性，不是会话的状态**（`DelegationPolicy.mode`）——
否则「我明明开了规划模式」这句话在另一个通道发起的委派上不成立。
会话级管**沟通**，委派级管**执行**；落地时**先做委派级**。

**撤销归OpenCode**：用OpenCode 自带的快照，FreeAgent 只做**预检**。

### 4.6 提示词归谁写

**判据：知识归谁所有，就归谁维护。**

| 知识 | 归谁 |
|---|---|
| 怎么写代码、项目的约定与历史 | OpenCode（AGENTS.md / 专家文件） |
| FreeAgent 特有的三件事 | FreeAgent 注入 |

FreeAgent 只注入 OpenCode **不可能知道**的三件：① 这是个人事务助手；
② 事务上下文（角色、恢复契约、命中的信号）；③ 硬约束（路径白名单）。

**硬约束：brief 必须单行**（实测，不是风格偏好）。

由此得出唯一要补的字段：`Role.default_agent`。

> **评估结论**：**不需要「高级开发工程师」这一层。** OpenCode 原生就有承载它的机制
>（专家文件 + 权限表）。正确形态是**一个文件，不是一个层**。

**WorkBuddy 的四格（模式／专家／技能／连接器）不搬进来**，三条已付过学费的理由：
① 多一套概念就多一处漂移；② 编程场景的阶段指定要而规范已写（Plan/Build），
不引入新机制；③ 「通过专家完善提示词」的完善者是**被选中的那个 agent 文件**，
不是一个中间层。

### 4.7 产出验收

原承诺「待你验收」是**空头** —— 界面上没有任何按钮能接住「做完了」。

补的动作只有两个：**采纳**与**开新版本**（没有「不合格」这个结论）。
三种拒绝给三句话，不给「不合格就重来」的模糊回环。

**不放宽的两处**：一条服务，两个界面（不新增第二套逻辑）；验收结论回流进
`/feedback` 的分母。

### 4.8 反馈回流与恢复

- `/feedback` 是**只读**的，从 `TaskRecord` 现推结局/验收结论/错因频次，
  **只摆事实不给建议**。
- 成功率的分母**只算「真跑过」的**（被闸门拒掉的不进分母）。
- 失败错因**回流进下次派发的简报**。
- **委派恢复**：进程死了不是终点，委派状态落盘，可续。
- **每日备份**：一次线上备份，滚动 7 份。

## 五、执行器注册表

> 收拢原契约 11.10全节。

### 5.1 叫「执行器」，不叫「Agent」（术语，规范性）

见 0.4。这不是文字游戏：三个「Agent」含义并存时，「这次委派是谁批准的」这类
问题就再也答不清了。

### 5.2 能力探针：探测，不解析自由文本

`/agents` 回答四件事：**有哪些执行器、装了没、什么版本、能不能派**。**只看不派。**

做法是执行一个固定的探针调用并读**结构化字段**（版本号、能力声明），
**不解析** `--help` 或自然语言输出 —— 解析自由文本必然在版本漂移时静默出错。

### 5.3 最小权限集：三桶，不是三十个 flag

| 桶 | 含义 |
|---|---|
| `read` | 只读项目 |
| `write` | 改文件 |
| `approve` | 请求授权（会挂起等人批） |

三桶足够。多到几十个 flag 时，配置本身就成了新的理解负担。

### 5.4 轮次预算

**Agent 套 Agent 会指数增长。** 所以问答类调用必须带轮次上限，
`/ask` 强制只读配置 + 轮次预算 + 遇到授权请求一律中止。

### 5.5 绝不自动触发委派

与 7 章同构：**不可复核的信号不许驱动动作**。系统可以在你明确要求时帮你挑一个
执行器，但绝不自己发起。

### 5.6 `/ask` 的形状：问答，不是接管

**只读**：不改文件、不建事务、不产出artifact、**不问任何审批**。问的是
**当前目录**，输出里必须写明是哪个目录。

## 六、通道与界面

> 收拢原契约 11.9（远程通道）、11.11（通道多路化）、12.6（Web UI）、
> 12.7（飞书控制面）、12.7.1（白名单管理）、12.8（Web 实时委派）。

### 6.1 通道是一等公民

三个入口 ——终端（REPL）、**本地 Web**（`127.0.0.1:8770`）、**飞书**（长连接）——
**对等**，共用同一套服务层。

**通道之间不广播。** 一条事务在哪儿被创建就在哪儿被处理，不因为「多个入口
都开着」而重复处理。

**「回推」在两个通道上答案不同**：飞书能主动发卡片，Web 只能轮询。
所以「同一件事在两个通道上表现不同」不是 bug，是通道性质的必然。

### 6.2 飞书通道：门控与安全边界

| 规则 | 内容 |
|---|---|
| **群聊@ 门控** | 必须@ bot 自己，否则不响应 |
| **事件去重** | 必须**跨重启**（落盘 + TTL + 条数上限） |
| **单实例守卫** | `PortLock`（bind 而不 listen） |
| **白名单** | `FEISHU_ALLOWED_USERS` 为空则**拒绝启动**（fail-closed） |
| **bot 身份** | 探测不到 `bot_open_id` 即**失败关闭** |
| **日志** | 落盘必须**显式开**，否则界面「日志」区永远空白，而空白会被当成「没出错」 |
| **改配置** | 必须明说「**要重启才生效**」 |

去重与身份状态落在**同一个状态目录**（`feishu_seen_events.json`、
`feishu_bot.json`、`bridge_status.json`），因此 `--db` 换位置时跟着走。

**本地操作的确认闸门**：飞书上任何本机副作用操作（杀进程、改文件）都必须先发确认卡。

**配对**（11.9.8，两条已实现）：`/pair <码>` 把飞书某个人加进白名单，码由 bot
**私聊**签发。它只解决「怎么拿到 open_id」，**白名单为空仍拒绝启动**。

`services/channel.py` **零依赖、不碰传输**：去重表与 bot 身份由 `feishu/`
通过 `Deduplicator` 协议注入，默认实现是内存表。所以落盘去重是**传输层的选择**，
核心包 `dependencies` 依然为空。

### 6.3 飞书控制面：把「看日志 / 配凭据」收到一处

**位置**：并入 `python -m freeagent.web`，**不新开入口**。

**状态传递用文件，不用 HTTP 端点**：桥接周期写 `<state_home>/bridge_status.json`，
Web 读文件。理由是**零网络暴露面** —— 起一个 HTTP 端点就要处理端口冲突与 CSRF。

| 字段 | 用途 |
|---|---|
| `updated_at` | **判活**：超期即视为「桥接已死」 |
| `pid` | 「是不是我起的那个还活着」 |
| `state` | `starting` / `ready` / `degraded`，一个字段说清「能不能用」 |
| `connected` | 与 `state` 分开：连接断开 ≠ 进程死 |
| `bot_open_id` / `bot_name` | @ 门控的依据；**没有就是失败关闭** |
| `allowed_users_count` | 为 0 是致命配置（启动即拒） |
| `lock_port` | 「另一个桥接在跑」是「突然不响应」的头号原因 |
| `dedup_entries` | 跨重启去重是否真的在工作 |
| `last_error` | 出问题时的第一手线索 |

⚠️ **`updated_at` 是必需的，不是装饰**：进程被强杀时状态文件会**留在磁盘上**，
界面若照着它显示「已连接」，就会对着一个几小时前死掉的进程报健康。

#### 「活着」与「是我启的」必须分成两个字段

`running` 回答的是「我们 spawn 的那个子进程还在吗」，依赖内存里的进程句柄。
于是三种情形会**一并**被报成「没在跑」：

| 情形 | 实际| `running` |
|---|---|---|
| 桥接由计划任务 / 开机自启拉起 | 在跑，连得上 | **False**（不是本 Web 的子进程） |
| 桥接在别的终端里手开 | 在跑，连得上 | **False** |
| **Web 自己重启过一次** | 在跑，连得上 | **False**（句柄随进程没了） |

第三行最要命：Web 重启是升级和崩溃后的**常规动作**，之后界面会一直报故障，
而用户明明能收发消息。

所以 `bridge_state()` **增列 `alive_observed`**：**只看心跳新鲜度**
（`not is_stale(raw)`），**不问进程是谁拉起来的**。

- `alive_observed and supervised` → 「在跑（本界面启动）」
- `alive_observed and not supervised` → 「**在跑，但不是本界面启的，因此管不着**」
- `not alive_observed` → 「没在跑」

**这条只加旁证，不改判定**：`is_stale()` 的语义与签名**一个字都不动**。
⚠️ **严禁**把「进程存活」塞进 `is_stale()` —— 试过一次，给它加一个 `started_at`
上限，看着更严，实际会把**连续运行超过阈值的健康桥接**判成陈旧。零收益、纯伤害，
已回滚。

**三条状态必须分开显示，不可合并成一个「在跑 / 没跑」**：①进程活着且是本界面启的
②进程已退出（带退出码）③端口被占但无证据是自己的桥接。合并了等于把
「有东西在跑、但我管不着」谎报成「干净」。

**启停规定：**

- 动作只走 **POST**，`action ∈ {start, stop, restart}`。**刻意不注册 GET 别名** ——
  浏览器预取、爬虫、`<img src>` 都会自动发 GET，**能杀进程的操作绝不能挂在这种方法上**。
- **只停本界面启起来的进程。** 拿不到句柄时**如实报错**，**禁止**照状态文件里的
  pid 去终止 —— pid 可能已被系统回收给**另一个进程**（实测 2026-10-04：原桥接的
  pid 已被别的进程占用）。**会误杀毫不相干的程序**。
- 端口被别人占着时**不硬顶**：顶掉一个可能正在正常收消息的桥接，比报错坏得多。
- 启动前先自检配置，**配置不全就不许起进程**；起进程后**抓早退**，当场报退出码，
  绝不报「已启动」。

**开机自启由此成为可能**：一旦存活判定不再依赖父子关系，桥接就能由计划任务独立拉起。
在此之前接自启是**有害的** —— 界面会把健康的自启桥接报成「没运行」。

### 6.4 委派白名单由控制面管理

三道闸门里的「项目白名单」此前**只能手改 `config.json`**，而内容是一串绝对路径。

#### 候选的**来源**与**准入**是两件事（V1.22 修正）

⚠️ **实测暴露的缺口**（2026-10-09）：拿一个**全新的空目录**做端到端测试时，
它在界面上**根本不出现** —— 因为候选清单唯一来源是执行器的项目注册表，
而那个目录从未被打开过。于是「授权一个新项目」**只能手改配置文件**。

根因是一条规范**把两件事绑死了**：「不复制成第二份真源」是对的（项目名、图标、
颜色由执行器拥有，抄一份必然漂移），但它顺带把「候选从哪来」也定成了唯一来源。

**修正：拆开。** 本仓已用过同一原则 ——
`check_project_allowed` 的 `aliases` 参数：**aliases 只提供候选路径，不提供放行**。

**候选 = 三个来源的并集**，每条带 `source`：

| `source` | 说明 |
|---|---|
| `opencode` | 执行器项目注册表（最省事的一条） |
| `whitelist` | 已在白名单、但注册表不知道的 —— 现在界面上只是一行文字，**看得见、撤不掉** |
| `picker` | 用户从「可授权根」里点选出来的（新增） |

**「可授权根」是新增的硬约束**：配置项 `delegate.browse_roots`，**默认为空 =浏览关闭**
（与 `delegate.projects`、`FEISHU_ALLOWED_USERS` 同一个「默认朝关」原则）。
理由：允许挑任意目录 = 把准入权交回给「谁在操作界面」。划一个根之后，
**可选范围仍然是你预先圈定的**。

五条实现约束，每条对应一种绕过手法：

1. 浏览接口**只列目录**，不列文件（列文件是噪音，还诱使人点文件）。
2. **绝对路径由服务端拼**，客户端只传「第几个根 + 根内相对路径」。
   收到绝对路径即非法 —— 接受就退化成「路径由用户输入」。
3. 拼接后 `resolve()` 再验「仍在根内」，用 `relative_to()` 而非字符串前缀。
4. **跳过符号链接**（`is_symlink()`）。`D:\root\link → C:\Windows` 是越过根的
   最省事手法，且报错文案会变成「不在允许范围内」—— 用户完全不明白自己点错了什么。
   所以在**列目录时**就不给它出现。
5. 授权仍是 POST 显式动作，写入仍是 `config.json`（安全配置必须留在人能 review
   的纯文本里）。

**「列出来 ≠ 已授权」**：列表里出现一个项目**不等于**授予权限 —— 否则
「在执行器里加一个项目」就等于「悄悄授权 FreeAgent 去改它」，而这种授权**不可审计**。

### 6.5 Web UI

**技术选择**：Python 标准库 `http.server` + 单页 HTML，**零框架、零外部资源**
（无 CDN、无字体）。理由：这是本地工具，断网必须照常能用。

**分层纪律**：`web/serialize.py` 只做领域对象 → JSON，**不含任何业务判断**。
两个入口共用同一套规则，绝不允许 Web 层自己再算一遍。

**并发**：`ThreadingHTTPServer` + `check_same_thread=False`，但 SQLite 连接**不能被
两个线程同时使用**，所以每个请求都持有 `App.lock`（`threading.RLock`）。
这是硬约束，不是优化。

**安全边界：**

| 项 | 规则 |
|---|---|
| 监听地址 | **只允许回环**（`127.0.0.1` / `localhost` / `::1`）。`create_server` 对其他地址**直接抛错** |
| 鉴权 | 回环 + 会话令牌（`secrets.token_urlsafe(32)`，校验用 `hmac.compare_digest`恒定时间比较） |
| 写操作 | **白名单**：新建、状态迁移、排期/移出、验收、删除。草稿采纳、角色合并、改名、静置仍只能去终端 |
| 角色选择 | Web 建事务**必须显式选角色**，不做推断 |
| 响应头 | CSP（`default-src 'none'`）、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store` |

**不许在 UI 里丢掉的东西**（有测试守着）：

1. 每条排序信号的**理由**必须显示（`signals[].reason` 是必填字段）。
2. 免责标记「启发式提示，不是评分」必须出现在页面与每个列表响应里。
3. 「助手不替你决定先做哪个」这句要在页面上。
4. 视图切换只是**换个角度读同一份数据**，不给「筛选掉某些事」的选择权。

**明确不做**：编辑草稿、拖拽排期、登录鉴权。
**Web 界面不解决「终端关了收不到提醒」这个核心缺陷。**

### 6.6 Web 实时委派

WebSocket 换成**只读轮询**：轮询时**比对签名、不重建 DOM**（否则整页闪）。
写操作（允许/拒绝/停止/答问）单独走 POST 端点，且与飞书**共用同一条服务**。

### 7.3 分层纪律（规范性）

- `domain` 零 I/O、零业务判断。
- `storage` **只存取，不判断**。顺延、权重计算、状态迁移合法性一律不在这一层。
- `services` 承载全部业务规则与不变式校验。
- `cli` 只做输入解析与渲染，不含业务判断。
- `services/llm/provider.py` **不 import `domain`**，用 `TaskRef` / `RoleHint` /
  `SignalRef` 作为边界类型 —— 这是替换真实 LLM 的接缝。
- `cli` 的命令解析用**派发表**（`_handlers()` → `_cmd_*`），不用不断增长的
  `if/elif` 链；每条命令在 `_USAGE` 里必须有用法文本，`/help` 必须列全。

### 7.4 白话入口的路由契约（规范性）

白话入口按**职责**分三层，**不按话题**分。混淆这两者是本项目已经犯过的错。

| 职责 | 干什么 | 由谁做 |
|---|---|---|
| **理解** | 这句话是「要一个视图」「要记一件事」「要改已有」 | 规则判定意图 + 视图**词表优先** |
| **事实** | 今天有什么、为什么排第一、在等什么 | **规则**，读库渲染 |
| **副作用** | 建事务、建/改角色 | **白名单** |

**分流顺序是规范性的：只读视图先试，然后才谈写。**
两条能力的后果不对称 —— 只读答错只是读错一次，写错是往用户的角色结构里塞脏数据
（角色还反过来驱动分类，污染会自我强化）。

推论（**必须遵守**）：`RECORD` 之所以危险，正因为它是默认分支 —— 「没被认出来」
等于「当成要记的事」。新增任何只读视图时**必须**接入 `ChatService.try_view()`；
不得让入口自己先调 `read_intent` 再决定要不要问它。

> **实测过的违反后果**：`全部未结束的事` 没有疑问词，`read_intent` 判成 `RECORD`。
> `ChatService.respond` 内部加了只读优先后它被正确路由，但终端/飞书走 `Repl._natural`，
> 那里自己先调 `read_intent`、从不调用 `respond` —— 于是防线被完全绕过，
> 真的建出了一条垃圾事务。修法是 `try_view` 升为**公开接口**，两个入口都必须先问它。

**「一份能力一份实现」是硬约束。** 任何入口都不得自建第二份判流逻辑。分叉的表现
极隐蔽：Web 对话框正常、终端和飞书错，而两边各自都测过。

**兜底必须自报家门。** 视图没命中时兜底到「今天」是允许的（永远有答案好过
「我不知道」），但答复必须**明说**「没听懂，先按今天答」。数据侧标记
`ChatReply.inferred`，正文侧由 `_INFERNED_NOTICE` 承担，两者都要有。

### 7.5 模型层（规范性）

| 实现 | 何时使用 | 特点 |
|---|---|---|
| `RuleBasedProvider` | 无 Key / 显式停用 / 模型失败兜底 | 纯规则、离线、确定性 |
| `DeepSeekProvider` | 有可用凭据时 | 真实模型。**名字是历史遗留**：它其实是标准 OpenAI 兼容客户端 |

**服务商注册表**（`services/llm/providers.py` 是唯一来源，加一家是加一行表项）。
当前收录 6 家**全部是 OpenAI 兼容**：

| id | 服务商 | Key 变量名 | 默认地址 |
|---|---|---|---|
| `deepseek` | DeepSeek | `DEEPSEEK_API_KEY` | `https://api.deepseek.com/v1` |
| `kimi` | Kimi / 月之暗面 | `MOONSHOT_API_KEY` | `https://api.moonshot.cn/v1` |
| `qwen` | 通义千问（DashScope兼容模式） | `DASHSCOPE_API_KEY` | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| `openai` | OpenAI | `OPENAI_API_KEY` | `https://api.openai.com/v1` |
| `ollama` | Ollama（本机、不联网） | `OLLAMA_API_KEY`（`needs_key=False`） | `http://127.0.0.1:11434/v1` |
| `custom` | 其它兼容服务 | `OPENAI_COMPATIBLE_API_KEY` | **无默认，自填** |

`llm.env` 的**白名单由这张表推导**（`all_key_env_vars()`），不另抄一份 ——
抄的那份会漂：加了 provider 忘了加白名单，表现是「界面保存成功了、重启后 Key 没了」，
而界面上还显示「已配置」。

**范围刻意只到兼容族。** Claude / Gemini **不是这个形状**：鉴权头、请求体、响应都不同。
硬接进来的后果**不是报错，是静默劣化** —— 五个方法里有三个硬依赖 JSON 输出质量。
换一家JSON 不可靠的实现，`classify` 会频繁返回 `need_clarification`，用户看到的是
「这助手老是反问我」，而日志一片正常。**要接它们，得先扩协议、加一层结构化输出
能力声明**，**声明不了就不接**。

**配置：秘密与非秘密分开**

| 内容 | 来源 | 理由 |
|---|---|---|
| **API Key** | 环境变量优先，`~/.freeagent/llm.env` 兜底 | 秘密。`config.json` **永远不会有**（`Config` 压根没有 `api_key` 字段，是现读的 property，靠类型防住而非靠约定） |
| provider | `config.json` 或 `FREEAGENT_LLM_PROVIDER` | 非秘密 |
| model / base_url / timeout | `config.json` 或对应环境变量 | 非秘密 |
| 精力档位 | `config.json`的 `energy_windows` | 非秘密（让 `ENERGY_FIT` 真正可触发） |
| 总开关 | `FREEAGENT_RULES_ONLY=1` | 演示 / 离线排查 |
| 降级开关 | `FREEAGENT_ALLOW_FALLBACK=0` | 宁可报错也不要悄悄降级 |

**为什么环境变量优先于文件**：环境变量是**显式动作**（临时 `set` 一次做对比测试，
跑完就消失），文件是**持久配置**。界面上必须**如实显示当前生效的是哪一个**
（`Config.key_source`）—— 不显示的话，用户在界面上重填了 Key 却发现没生效
（被环境变量压住），会以为设置坏了。

**不认识的服务商 id 必须在加载时报错**，不静默回落到 DeepSeek。静默回落的
表现是「下拉里选着 Kimi、请求却打到了 DeepSeek」，而界面上看不出任何异常。

优先级：内置默认 → 配置文件 → 环境变量。**降级原因里带的是真实服务商名** ——
用 Kimi 出错时不能显示成 deepseek，否则用户会去查错的那家的账单和限流。

**HTTP 只用标准库 `urllib`。传输层可注入**（`transport(...)`），测试全程打桩，
**零网络请求**。Key 走 `headers`，**不进 payload**（payload 容易被日志打印）。

**输出必须过校验**（模型会编造，这是既定事实，不是假设）：

| 风险 | 防线 |
|---|---|
| 编造角色名 | 角色名**白名单**，不在已知列表里的一律丢弃 |
| 丢弃后零候选 | **强制追问**，绝不把事务塞进猜出来的角色 |
| 输出非法 `kind` | 白名单 `{action, wait, reminder}`，否则报错 |
| 置信度越界 | 钳到 0..1；≥ `ROLE_MATCH_THRESHOLD` 才免追问 |
| 草稿漏掉「未知」标记 | 强制补齐 `## 目标` / `## 完成标准` / `## 材料` / `## 待确认` 四段，且必须存在 `[TODO]` |
| 步骤不是列表 | 无任何列表标记时视为解析失败，退回规则层脚手架 |

**降级必须告知**：模型失败时退回规则层，原因记入 `last_degradation`，CLI
**如实打印**「（模型不可用，已退回规则推断：…）」。**禁止静默劣化。**

### 7.6 密钥与秘密（规范性）

**API Key 绝不进代码库、绝不进 `config.json`、不进日志与错误信息。**

**密钥一律用 `SecretStr` 承载，不裸传 `str`。** 取值收窄到 `use()` 一个出口，
`__repr__` / `__str__` 只能给出分级遮蔽的预览。容器上覆写 `__repr__` 只是
**约定**（新写一处就可能漏），**值本身带 mask 才是保证**。

密钥**落盘是允许的**，但三条硬约束由 `secrets_file.SecretFile` 统一保证：

1. **变量名必须是白名单**，不接受自定义 key —— 往 `PYTHONPATH` / `LD_PRELOAD` /
   `EDITOR` 里塞一个路径就是 RCE，而 `^[A-Za-z_]\w*$` **挡不住这些**，
   因为它们本来就合规。
2. **读盘容忍 BOM**（`utf-8-sig`），否则 PowerShell 写出的文件会让第一个变量名
   带 `\ufeff` 而**静默失效**。
3. **每次读都清洗**粘连行与 `***` 占位符。

另加一条：**凭据含非 ASCII 直接拒**（全角引号、零宽字符肉眼分不出，服务端只回 401）。

飞书侧白名单固定 5 个变量：`FEISHU_APP_ID` / `FEISHU_APP_SECRET` /
`FEISHU_ALLOWED_USERS` / `FEISHU_DOMAIN` / `FEISHU_LOCK_PORT`。
读取优先级：**环境变量优先，文件兜底**，按**键是否存在**判断而不是「值是否为空」
—— 否则 `set FEISHU_APP_SECRET=`（故意清空）会被文件里的值悄悄填回来，
而那恰好是最不该被悄悄推翻的一种意图。

**明文不落加密、且不假装加密。** DPAPI 只多防「其他 Windows 用户」，而同用户进程
照样能解开。所以防那个威胁的是**会话令牌**，不在密钥文件。落盘确实把「其他同用户
进程」的暴露面从「进程运行期间」扩到「任何时刻」—— 如实记下，靠「文件不在仓库内+
写入受会话令牌保护 + 响应只给掩码」降低，**不靠保证**。

| `/task-del <id> confirm` | **不可恢复地删除**一条事务。第一次只说后果与出路，再输 `confirm` 才真删；正在跑或有待批项时拒删 |
| `/kind <id> <action\|wait\|reminder> [等谁]` | 改形状；改成等候类须说明在等什么 |
| `/wait <id> <等谁>` | 放一放并记下在等什么 |
| `/followup <id> <日期\|off>` | 设/清跟进时间（驱动 `OVERDUE_WAIT`） |
| `/today-pin <id> [日期\|off]` | 排进今天 / 指定日期 / 移出排期（移出不改 `state`） |
| `/note <id> <内容>` | 记一笔进度 |
| `/dod <id> <标准\|off>` | 改这条事务的完成标准 |

**委派**

| 命令 | 作用 |
|---|---|
| `/delegate <项目绝对路径> \| <角色> \| <需求>` | 建一条委派事务 |
| `/redispatch <id> [原因]` | 让一条委派**可以重新派发**。被拒（白名单不符/ 没闸门）不会自动重试 —— 改配置前重试多少次都是同一个结果 |

**角色与归属**

| 命令 | 作用 |
|---|---|
| `/move <id> <角色>` | 只挂到目标角色 |
| `/unrole <id> <角色>` | 摘掉一个角色标签（不允许摘到空） |
| `/role-add <名字> [备注]` | 新建或更新备注（备注参与角色推断） |
| `/role-rename <名字> <新名>` | 改名 |
| `/role-silence <名字> [on\|off]` | **省略 = 静置**，`on` = 恢复活跃 |
| `/role-dod <名字> <标准\|off>` | 该脉络的默认完成标准 |
| `/role-del <名字>` | 删除；要求该角色下无事务，否则提示改用 `/merge` 或 `/move` |
| `/merge <源> <目标>` | 合并角色，原子重定向，历史可回看 |

**其它**

| 命令 | 作用 |
|---|---|
| `/tick` | 手动检查提醒 |
| `/reset-data <确认口令>` | 恢复出厂：清空全部事务数据（脉络/配置保留，强制先备份） |
| `/agents` | 执行器探针：有哪些、装了没、什么版本、**能不能派**。**只看不派** |
| `/ask <问题>` | 问执行器一句就把答复拿回来。**只读**：不改文件、不建事务、不产出artifact、**不问任何审批** |
| `/pair <配对码>` | 把飞书某个人加进白名单。码由 bot **私聊**签发 |
| `/llm` | 查看当前智能层与配置（**不显示 Key**） |
| `/help` `/quit` | 帮助 / 退出 |

约定：所有 `<id>` 都可只输前几位；角色/事务都按名字或 id 前缀匹配。

### 8.2 做的功能（V1）

每项都对应 8.1 里的实际命令，缺一条即视为未交付。

1. **新建事务**：自然语言进入，自动推断 `kind` 与角色候选 → `/new`
2. **角色管理**：增删改、静置、**合并（重定向）**、默认完成标准 → 8 个 `/role-*` + `/merge`
3. **视图**：今天（含**顺延标记**）/ 按角色 / 所有事务 → `/today` `/role` `/all` `/roles`
4. **状态与调度**：开始/暂停/完成/放弃/改 kind/排期/移出/改完成标准 → `/start` 等
5. **提醒**：到点通知、错过标记、合并摘要 → 每轮自动 + `/tick`
6. **等候**：`WaitingOn` 记录与跟进提醒 → `/wait` `/followup`
7. **进度记录与回放**：`TaskRecord` 只追加 + `progress_note` 重建 → `/note` `/task`
8. **草稿辅助（最简版）**：版本化 + 采纳 + 局部重做 → `/draft` `/revise` `/artifact` `/accept`
9. **恢复契约**：完整 `RestoreView` 与 `next_actions` → `/task`
10. **透明弱排序**：信号 + 理由 + 单条排期参考 → `/today` `/all` `/plan`
11. **跨角色改归属** → `/move` `/unrole`
12. **拆步骤**（只拆，不排序）→ `/steps`
13. **事务硬删**（V1.42）→ `/task-del` + Web 按钮
14. **本地 Web 界面**：四视图 + 详情页 + 新建 + 委派实时面板 + 验收。仅监听回环

### 8.3 先不做的（V1）

- 多渠道自动采集（邮件/ 日历 / 聊天）—— 「入口散」因此未被验证。
- 复杂优先级打分算法 —— 只有透明的确定性弱信号。
- 跨应用 Computer Use / 浏览器操作。
- 多设备强一致同步 —— 原型本地单库。
- **角色知识的语义检索**（向量那一腿）—— BM25 + 近期回落已实现，
  向量刻意不做：要embedding 就得联网，而「断网照常能用」是硬性质。
- **角色知识的写入入口** —— 服务层已就绪，接线时再补。
- 流式输出 / 多轮对话上下文 —— 每次调用都是**无状态单轮**，上下文由恢复契约显式提供。
- **FreeAgent 主动打断 agent 提问** —— V1.14 更正：
  - **agent 提问、用户答 → V1 完全可行**，答案附在挂起的 tool 调用上、**不污染主线**（实测闭环 9.2 秒）。
  - **FreeAgent 主动插话 → 才真的无解**：子会话与 `fork` 实测都不继承上下文，
    唯一的 `/session/{id}/message` **必然写进历史**。

## 九、判据与边界

### 9.1 成功判据

| 编号 | 判据 |
|---|---|
| H1 | 打开任一事务，恢复契约 7 项齐备，**无需追问**即可判断下一步 |
| H2 | 从打开事务到开始下一步 **≤ 2 轮**对话 |
| H3 | 每条排序结论都带**可读理由**，且理由可被用户反驳 |
| H4 | 任何委派动作都能回答「谁批的、什么时候批的、批的是什么」 |

### 9.2 决定不做的事（连代价一起写）

| 不做 | 代价 | 为什么接受 |
|---|---|---|
| 隐藏式优先级评分 | 用户无法反驳一个看不见的分数 | 换取可审计性 |
| 向量语义检索 | 知识只能关键词召回 | 「断网可用」是硬性质 |
| WebSocket | 实时性略差 | 换零依赖与零攻击面 |
| 主动打断提问 | FreeAgent 不能插话追问 | 唯一的可用接口必然写进历史 |
| 让执行器自己读配置 | 执行器需重定向 HOME | 配置隔离是安全边界 |

### 9.3 已知边界（诚实记账）

1. **提醒是轮询式** —— 两个进程都关就收不到。Web 界面不解决。
2. **飞书把文字当指令，非文字消息「收下而非丢弃」（V1.48 收下 + V1.50 入队）** —— 图片/文件下载到 `attachments/` 并落入待处理收集器（`/pending` 列出、`/pending N` 一键澄清成事务）；富文本仍只回提示；都不建事务。
3. **执行期授权的「停止」按钮真机未验** —— 允许/拒绝已验。
4. **委派看得见执行器配置** —— 插件/MCP 列表不再隔离（V1.31 放弃隔离后的代价）。
5. **委派白名单候选** —— 三源并集已落地（V1.43）：OpenCode 注册表、白名单历史行（现在带撤销按钮）、可授权根点选（`delegate.browse_roots`，**默认空 = 浏览关闭**）。12.7.1.2 的重启提示机制化仍不做。
6. **Plan 状态已落盘（独立表 + 24h TTL），恢复时也会说清（V1.46）** —— 会话因淘汰/重启而恢复时，会在下一条回复前明确告知「上次的规划还在，已记下 N 条」，不再静默接续。
7. **执行器注册表未真正落地** —— hermes 已登记未接线。
8. **关系对象仍是自由文本** —— 不可检索、不可聚合。

## 附录 A：演进账本（噪音沉淀）

> 原契约正文中大量「已纠正的错误」「外部借鉴」「诚实记账」旁注在此汇总。
> 它们**不是规范**，但**不可删** —— 删了就会有人重新踩同一个坑。

| 主题 | 坑 | 结论 |
|---|---|---|
| 闸门形态 | 用「不传 `--auto`」当闸门 | 缺省≠ 授权。改默认拒绝 + 逐次授权 |
| 排序形态 | 一开始想用隐藏评分 | 用户无法察觉错误，却照着它行动 |
| `is_stale()` | 往里塞「进程存活」判定 | 会把连续运行的健康桥接判成陈旧，零收益纯伤害，**已回滚** |
| 授权卡留存 | 一开始想「全删」旧卡 | 授权判定要能对账。改为「只保当前挂起卡 + 全量明细在库」 |
| HTTP 方法 | `urllib_transport` 的「空载荷 = GET」旧约定 | DELETE 被静默改写成 GET，HTTP 200、码 0、**撤回变成读取**。已改为显式 method 优先 |
| 委派交互 | 第一版只支持「一轮半」问答 | 换成 Plan/Build 模式切换，Plan 期零副作用、可多轮 |
| 候选来源 | 「不复制成第二份真源」把「候选来源」也绑死 | 拆成候选来源（三源并集）与准入权威两层 |
| 恢复上限 | 恢复自省容易被模型「美化」 | 恢复视图是**模板填空**，不许自由生成 |
| 身份字段 | `requested_by` 两个语义打架 | 兜底身份从发起身份里拆出去 |
| LRU 淘汰 | 通道按 chat 缓存 `Repl`，淘汰静默丢状态 | 东西没了但没人说，比报错更糟 |

**外部借鉴的结论汇总**：OpenCode 的权限表（Plan/Build 隔离）值得照抄，
但 `question: deny` **刻意不抄**（执行模式要允许只读式追问）；
WorkBuddy 的四格概念**不搬**；Hermes 的 denylist 思路被采纳为**更严的白名单**。

## 附录 B：产品定位与改进路线图（非规范性）

### B.1 定位

FreeAgent 不与通用助手比「什么都会」，它占的位置是：**个人事务的单一真相源**。
竞争力来自三件事：本地优先（数据不出机器）、可审计（每个决定都有理由）、
不越界（不替你决定、不替你发消息）。

### B.2 改进清单（按人本优先级，非实现顺序）

> 格式：**第一性原理 → 现状 → 建议**。每条新增建议**都不得侵蚀 0.3 的十条底线**，
> 冲突时以底线优先。

**① 连续性个人模型**
第一性原理：Personal 的本质是「跨会话积累对人的理解」；无状态即每次从零。
现状：`services/llm` 明确「无状态单轮」；个人节奏只靠 `energy_windows` 与
`Role.note` 自由文本。
建议：`TaskRecord` 是**只追加日志**，已存全部承诺/完成/顺延事件 —— **直接从它
派生**一个轻量个人模型：典型精力曲线、常见角色切换、拖延/卡住模式。
**规则统计即可，不引向量库**。✅ **已实现（V1.49，见原契约 11.17；V1.59 升级）**：
`/model` 从 `TaskRecord`/`Task`/关系/承诺/记忆现推**结构化画像**——
节奏（完成时段分布、顺延次数与反复顺延清单、卡住的等候 ≥7 天、角色活跃度）+
关系账（只列跟谁还有未结清的账）+ 承诺与目标（对外承诺 + 记忆里的约定/目标）；
纯只读聚合、零新依赖、不写库、不排序打分、不给建议、不判违约。记忆一期刻意不做
自动 consolidation（见 3.7.5），但本功能是**规则统计**而非 consolidation，与「不自带 RAG」定位一致。

**② 周回顾 `/week`**
GTD 的核心仪式是「定期夺回掌控感」。现状：有 `/today` 与 rollover收口，
但**没有「本周做了什么 / 下周承诺了什么 / 卡在哪」**。
建议：从 `TaskRecord` 聚合一个 `/week`，复用今天的信号与恢复契约。低成本、高掌控感。✅ **已实现（V1.44）**：设计文档 6.5 + `services/week.py`（只读五分区，复用 today 的顺延，不排序不给建议）。

**③ 通知节奏：尊重人的时刻**
Calm Technology：push 在错的时间点是负担。
现状：提醒轮询式，两个进程都关就收不到。
建议：① 把「提醒守护」做成极轻的系统层看门狗；② 加**安静窗口**，
**直接复用 `energy_windows`**（晚上 = 低打扰）。✅ **已实现（V1.45），但建议被否决**：安静窗口做成独立的 `quiet_hours`（本地墙钟跨天区间，缺省关闭），**刻意不复用** `energy_windows` —— 后者是排序分类桶、`evening=(18,24)` 没有低打扰语义，复用会导致 18 点起全网静音。理由见设计文档 9.8。

**④ 主动但不越界：起草不发送**
`/draft` 已强（只填 `[TODO]` 不编造），`waiting_on` 已识别「事务背后是人」。
建议：基于 `waiting_on`（「等张总回合同」）proactively 生成一条**待发送**的跟进
草稿，人一键确认才发。⬜ 未实现。

**⑤ 关系作为一等公民**
事务的连接点是人，不是标签。✅ **已实现（V1.51 contacts 表 + V1.52 等候也挂
关系 + V1.53 `/contact <名字>` 一页账 + V1.54 Web「关系」视图）**：关系对象可检索、
可按人聚合，承诺与等候两面都挂；`/contact <名字>`（单参数已存在）返回「一页账」——
见这个人之前最该先看的一页（我欠他的 / 我在等他的 明细）；Web 顶部导航「关系」
视图点开即看一页账，不用记命令（易用性主线）。

**⑥ 补「停止这条委派」真机验证**
人必须随时能真正叫停一个正在改 ta 代码的 agent。
建议：① 优先补「停止」真机验证（信任关键路径）；② 首次真跑委派时显式提示
「本次为首次真跑，请盯紧执行器日志」。⚠️ 允许/拒绝已验，停止未验。

**⑦ 反馈驱动权重校准**
权重表目前是硬编码规范。建议：用户「驳回某信号 / 改了某排序」记为个人偏好，
在规范表之上**叠加一层「个人校准」**。⬜ 未实现。

**⑧ 捕获摩擦：图片/文件收下而非丢弃**
GTD：先捕获，后处理。对忙碌的人，**丢掉比摩擦更糟**。
现状：✅ **已实现（V1.48 捕获 + V1.50 澄清，见原契约 11.9.10 / 11.18）**——图片/文件下载到 `attachments/` 并落入待处理收集器，`/pending` 列出、`/pending N` 一键澄清成事务；富文本仍只回提示；下载失败记引用照样入队（`media_key` 是重新下载的凭据）；全程不建事务。
~~建议（下一刀）：抽到 inbox 等后处理队列~~ → **V1.50 已落地**（命名避开 `TaskState.INBOX` 占用的「inbox」，叫「待处理收集器」）。再下一刀是语音转写 / 批量倾倒等入口（19.6 阶段 4）。

**⑨ 执行器注册表真正落地**
「已登记未接线」比不登记更危险。建议：让多执行器真可插拔且都过同一探针，不留半成品。⬜ 未实现。

**⑩ 隐私张力的正面声明**
现状：放弃隔离后，委派「看得见你的执行器配置」。
建议：建单时**显式告知「本次委派将读到你的 X」**。⬜ 未实现。

### B.3 如果只能先做三件

1. **① 连续性个人模型** —— Personal 与通用助手的分水岭，零新依赖。
2. **② 周回顾 `/week`** —— ✅ **已实现（V1.44）**。低成本、高掌控感，契合设计哲学。
3. **⑥ 补「停止」真机验证 + 首次真跑提示** —— 信任关键路径。

> **但录入摩擦（⑧）仍是最高优先级的隐藏短板** —— 以上三条都不解决
> 「数据先进来」的前提；若三件之外还能挤时间，**先降摩擦，再谈能力**。
