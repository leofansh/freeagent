# v1 · 基线

> **这份是重建的，不是当时写下的。** v1 从来没有文档，这里按
> 「当前 schema 减去 `_MIGRATIONS` 记录的四步增量」反推。
> 依据是 `storage/db.py` 里项目自己的纪律（见该文件第 36-37 行）：
>
> > 「每一步都必须能在已有库上原地跑：`init_schema` 只建新表，
> > 不会给已存在的表加列，所以列变更必须显式 ALTER。」
>
> 也就是说**列变更只经由 `_MIGRATIONS`**，所以减法是可靠的。

**不确定的部分照实标注，不编。** 见文末。

## 存在的表

| 表 | 作用 |
| --- | --- |
| `roles` | 角色脉络。`merged_into` 自引用支撑 `/merge` 的重定向语义 |
| `tasks` | 事务。`state` / `kind` / `scheduled_for` **三个正交维度** |
| `task_roles` | 事务 ↔ 角色的多对多，带 `ord` 保序 |
| `artifacts` | 草稿，带 `version` 与 `supersedes`；`UNIQUE (task_id, version)` |
| `task_records` | **只追加日志，唯一真源**。事务上下文全靠它重建 |
| `task_dependencies` | 事务间依赖，驱动 `DEPENDED_ON` 排序信号 |

## tasks 的列（v1）

```text
id                   TEXT PRIMARY KEY NOT NULL
title                TEXT NOT NULL
state                TEXT NOT NULL          -- 生命周期
kind                 TEXT NOT NULL          -- 动作 / 等候 / 提醒
intent               TEXT
definition_of_done   TEXT
scheduled_for        TEXT                   -- 排进哪天（与 state 正交）
due_time             TEXT
reminder_time        TEXT
waiting_on           TEXT
entered_at           TEXT NOT NULL
created_at           TEXT NOT NULL
updated_at           TEXT NOT NULL
completed_at         TEXT
dropped_at           TEXT
last_resumed_at      TEXT
progress_note        TEXT                   -- 派生缓存，可从日志重算
current_artifact_id  TEXT REFERENCES artifacts(id) ON DELETE SET NULL
```

**v1 没有** `project_path` 与 `delegate_chat_id` —— 那是 v2、v3 加的。
委派能力整体是 v2 之后才有的。

## 索引

```sql
idx_tasks_state          ON tasks(state)
idx_tasks_scheduled_for  ON tasks(scheduled_for)
idx_tasks_kind           ON tasks(kind)
idx_tasks_reminder_time  ON tasks(reminder_time)
idx_task_roles_role      ON task_roles(role_id, ord)
idx_records_task_ts      ON task_records(task_id, ts)
idx_artifacts_task_ver   ON artifacts(task_id, version)
idx_deps_depends_on      ON task_dependencies(depends_on_task_id)
```

**没有** `pending_approvals` 表（v4 才建）。

## v1 的关键性质（这些到 v5 都没变）

1. **`TaskRecord` 是唯一真源。** `progress_note` 只是派生缓存，
   随时能从日志重算 —— 所以它可以是 nullable 且不精确，
   丢了也能恢复。
2. **`Artifact` 永不原地覆写。** 改一次产生新版本，旧的 `supersedes` 指向它。
3. **多值字段用关联表，不用 JSON。** 约束由数据库保证。
4. **时间存字符串、不带时区换算。** 为了让 `FrozenClock` 下的断言能精确比字符串。

## 标为「不详」的部分

- **各列具体是哪个版本加的，只有上面那四步有记录。** 如果历史上有人绕过
  `_MIGRATIONS` 直接改过 `_SCHEMA`（比如给 `tasks` 加了 `icon` / `color` /
  `current_artifact_id` 却没有对应迁移），这里就**查不出来**了 ——
  减法只能反推「v1 缺哪四样」，不能反推「v1 当时恰好是哪几列」。
- **v1 当时有没有 `PRAGMA user_version` 值异常**，无从查证。
- 真实的 v1 库可能因手工干预与本文档不符。**以 `_SCHEMA` + `_MIGRATIONS`
  为准，本文档只作推理辅助。**

## 怎么验证一个库是不是 v1

```sql
PRAGMA user_version;                          -- 期望 1
SELECT name FROM pragma_table_info('tasks')    -- 期望没有 project_path
  AND name = 'project_path';                   --   与 delegate_chat_id
SELECT name FROM sqlite_master
  WHERE type='table' AND name='pending_approvals';  -- 期望空
```

四条都对得上，就是干净的 v1。跑一次 `migrate()` 会升到 5。
