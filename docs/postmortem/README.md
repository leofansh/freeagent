# 复盘目录

编号 + 日期的独立复盘。每篇回答四件事：

1. **错信了什么** —— 而不只是「出了什么 bug」
2. **根因** —— 为什么会这样，而不只是改了什么
3. **为什么难发现** —— 这一条最容易被跳过，也最重要
4. **留下的规矩** —— 要能被后来的人当规则用

命名：`NNNN-<短横线 slug>.md`，编号只增不改。

## 同目录的另一份：`lenses.md`

本目录是**事后**的：一篇一个事故，够格的标准是「按文档做也会踩」。
[`lenses.md`](lenses.md) 是**事前**的：把这里（以及设计文档、AGENTS.md 里）
散落的教训按「改代码时会撞上的形状」重排成 8 条 lens，动手前对一遍。

两者分工是刻意的：

- 复盘回答「当时到底怎么坏的」，给的是**理解**；
- lens 回答「这个形状我见过」，给的是**提醒**。

**复盘不会自己变成 lens** —— 一篇写完就沉在编号里，第三篇之后没人会回头查
「这次改动像不像 0002」。所以新增一篇复盘时，顺手看一眼 `lenses.md` 有没有
对应的那条；没有就加一条，把这篇挂上去。这也是 `lenses.md` 唯一会失效的方式：
**没跟上新复盘，且没有测试会报红。**

## 三篇的共同主题

回头看，这三篇是**同一个主题的三次显形**：

> **默认行为必须朝「宁可多问、宁可重发」的方向倒。**

- 0001：权限系统默认 `allow` → 闸门不存在
- 0002：意图判定默认「没认出来 = 要记」 → 污染自我强化
- 0003：去重令牌默认「查出来就落库」 → 未送达被误判为已送达

三处的形状都是一样的：**一个方向选错的默认值，在出错之前看起来完全正常。**

所以判断一段代码要不要改，问的不是「有没有 bug」，而是：

> **它的默认行为，在出错的那一刻，是朝「宁可多问一句」还是「宁可放行」的方向倒？**

## 什么时候该写一篇

不是所有 bug 都够格。够格的标准是**「按文档做也会踩」** ——
也就是文档、注释或测试里**已经把它说成是对的了**。

那种 bug 最贵：它不是「漏写了」，是「写反了」，而写反的东西看起来总是很像对的。
