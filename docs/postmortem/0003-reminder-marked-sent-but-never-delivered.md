# 复盘 0003：提醒被标记成「已送达」，而用户从没收到

> 状态：已修复 ｜ 影响范围：全部三条提醒渠道 ｜ 设计文档 9.2

## 现象

用户报告：**提醒没到**。

不是「延迟」也不是「漏了某一条」，而是某条提醒**从此再也没出现过** ——
而它确实已经到点了。它没有出现在终端、没有出现在飞书、没有出现在 Web。

## 根因

`ReminderEngine.check()` **同时做两件事**：

1. 查出到期且未发的提醒
2. **落去重令牌** `REMINDER_FIRED`

而真正的推送，由调用方在 `check()` **返回之后**才执行。

于是令牌在推送**之前**就落库了。进程死在中间、或推送失败时，那条提醒
已经被**永久标记成「已发过」** —— 而用户从没收到。连 9.3 的「已错过」分支
也不会再触发它（因为它已经被「发过了」）。

### 代价函数说明

去重令牌是对「**已送达**」的记账，不是对「**已检查**」的记账。
两者合一的时候，「检查过」被当成了「送达了」，于是**未送达被误判为已送达**。

## 三条渠道各自的坑

| 渠道 | 具体的失效方式 |
| --- | --- |
| `GET /api/reminders` | **GET 有副作用**。刷新、prefetch、探活、监控轮询都会吃掉提醒；并发双加载时第一个消费掉、第二个拿到空；handler 或序列化一抛，令牌已落、提醒永久丢失 |
| 终端 / `/tick` | `_say()` 写 stdout 失败（管道断裂、编码错误）时令牌已落 |
| 飞书 | `_notify_operators` 逐个吞掉发送异常且**不报结果**，调用方无从得知失败 —— 全部失败时照样落令牌 |

飞书那条最隐蔽：它连「抛异常」的机会都不给，**函数正常返回**。
`bridge._run_reminders` 的 `except` 块对发送失败永远不会触发。

## 修法：取与确认分离

```text
ReminderEngine.due() -> ReminderDigest        # 纯查询，不写库
ReminderEngine.acknowledge(digest) -> None    # 送达确认后才落令牌
```

**删掉**消费型的 `check()` —— 留着它等于给回归留后门。

确认点各渠道不同，因为「送达」的含义不同：

- 终端 / `/tick`：`_say()` 成功返回之后
- 飞书：`_notify_operators()` **必须报出「至少送达一个」**；bridge 拿到 True 才确认
- Web：handler 先查、构造出 payload、**再**落令牌（整个 handler 在 `app.lock` 内，
  查与确认之间不会被另一个请求插进来）

## 明确接受的代价：不再承诺恰好一次

送达失败时令牌不落库，提醒下一轮还会来。也就是**允许重复送达**。

个人事务助手的代价函数里，**重复提醒的代价远小于静默吞掉一条提醒**。
这个权衡是刻意的，所以写进了 9.2 的规范性条款，而不是藏在实现里。

## 留下的规矩

**「检查」与「提交」必须分开。** 凡是「查出来的东西会被记成已完成」的地方，
都要问一句：记的那一刻，**用户真的收到了吗**？

同类形状的问题还有：删除、发送、扣款。凡是「做了一半就可能失败」的外部动作，
令牌都不能提前落。

## 顺带修正的一处文档漂移

这个 bug 之所以能存在，是因为源码里有一句注释**把风险写成了别人的责任**：

> 「通道必须自己保证调用频率，否则提醒会丢。」

那句话是对的（通道确实必须自己推），但它掩盖了真正的责任归属：
**丢失是引擎的记账时机错了，不是通道调得不够勤**。
修完之后这句话连同它的警告一起删了。

相关：复盘 0001（默认值方向错了）、0002（失败方向没选对）——
三个复盘其实是同一个主题：**默认行为必须朝「宁可多问、宁可重发」的方向倒。**
