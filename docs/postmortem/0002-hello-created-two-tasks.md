# 复盘 0002：「你好」建了两条事务

> 状态：已修复 ｜ 影响面：白话入口的意图判定 ｜ 证据：真实库事务 `0277e93d` / `0fbbdb13`

## 现象

用户在对话框里打了「你好」，系统建了**两条**事务。

## 根因

`read_intent()` 的最后一行是 `return RECORD`。

于是判定逻辑变成了「**没被认出来** = **要记一件事**」。而「你好」既不是问句
也不是指令，它只是**没被认出来** —— 于是被当成了一条待办。

同类污染不止「你好」：「收到」「ok」「在吗」「嗯」全都会走同一条路。

## 为什么代价比看起来大

角色是整个模型的组织结构，而**角色反过来驱动分类**。

也就是说：一条垃圾事务会带出一个垃圾角色，垃圾角色又会影响后续所有事务的
角色推断 —— **污染会自我强化**。

所以代价是**不对称**的：

- 问错一句 = 多一轮对话
- 记错一条 = 往用户的角色结构里塞脏数据，而角色会反过来驱动分类

**代价不对称，所以失败方向必须往「问」倒。**

## 修法

1. **`InputIntent` 三值枚举**（`RECORD` / `QUESTION` / `MUTATE`）而不是一个
   「是不是任务」的布尔值。混成布尔值就会在「问」和「改」之间漏判。
2. **`is_confidently_recordable()` 兜底**：不通过就**反问**，而不是记下。
   判定是「**三个正向信号，任一满足**」：

   - 以任务动词开头（写 / 修 / 交 / 买 …）
   - 含时间或紧迫标记（明天 / 下周二 / 别忘了 / 要交 …）
   - **够长**（≥ 10 字）—— 长句自带语境

3. **10 字是量出来的，不是拍脑袋的。** 短命令（修窗户 / 交周报）由信号 1 兜住，
   带日期的长任务由信号 2 兜住，剩下的短句（你好 / ok / 在吗）由信号 3 挡掉。

## 留下的规矩

**信号表要往「更容易接受」的方向加。** 第 2、3 条刻意做成**正向**表 ——
往里加词只会让更多句子**更愿意被记**，那正是我们要的方向。

反之若做成**负向**黑名单，加词会让系统更爱乱记。这是同一个表里最容易搞反的方向，
所以写下来。

> 另一个符号也要留意：序数指代（「第一个改个时间」）的主体不是动作，
> 是上一轮的某一条 —— 判「是不是要记」时不能只看句首动词。
