# 复盘 0001：「不传 `--auto`」不构成保护

> 状态：已纠正 ｜ 影响面：委派闸门 ｜ 原文位置：README「委派执行器」一节

## 错信了什么

README 原来写「不传 `--auto`（dangerous!）」是委派的**第三道闸门**。

这句话听起来非常合理 —— 一个「危险」开关，不传它总该更安全。实际去量的时候
才发现，**不传它和传它效果一样**：目录内写文件执行、**写出目录外也执行**，
且**不产生任何授权事件**。也就是说这道「闸门」根本不存在。

## 根因

不是「没有权限系统」，而是**默认值是放行**。

opencode 官方 V1 文档原文：

> Most permissions default to `allow`

当时本机配置里又有 `external_directory: allow`，把本来的默认 `ask` 也覆盖掉了。
两道默认值叠在一起，于是从外面看「有权限控制」，实际上任何路径都不问。

## 为什么难发现

**闸门不存在这件事，本身不会报错。** 权限系统的默认放行和一个正确工作的
权限系统，在外观上完全一样 —— 都能写文件、能执行命令。只有在**真的需要它拦**
的时候才会暴露，而那已经是一次损失了。

这就是为什么它能以「已验证」的状态存在：当初验证的是「不加 `--auto` 也能跑通」，
而「能跑通」正是权限缺失的表现。

## 真正的第三道闸门

**执行期逐次授权**（`--tool-gate`）：agent 每要动手一次就发一张飞书卡，
卡上写明动作、影响路径、**它到底想改成什么**，等你点才继续。

- 卡上**没有 diff 的话，你点的就是「信任」而不是「确认」**
- **只有发起人能批** —— 白名单里的其他人点这张卡不生效
- 不点就算拒绝（超时自动降级为拒绝）—— **沉默不等于同意**
- `external_directory`（写出项目目录）**永远拒绝**，不逐次问

## 留下的规矩

1. **「危险开关不传」不是安全措施。** 安全必须来自**可观察的拒绝**，而不是
   「我没开那个危险选项」。验收标准是「它拦住了一次真实的越界」，
   不是「它跑通了」。
2. **默认值要往拒绝的方向倒。** 一个默认放行的权限系统，等于没有权限系统。
3. 闸门要**逐次**授权，不能只在入口授权一次 —— 入口授权管不住中途的形状变化。

## 同源的另一个坑：主版本会静默改字段名

opencode 升到 V2（2.0.6）后，permission 模型字段名**全变**
（`permission` 对象 → `permissions` 数组，`bash` → `shell`，`task` → `subagent`）。

**旧字段会被静默忽略** —— 不报错、不警告、闸门随之失效。

所以执行器启动时会**查主版本，不是 V1 就拒绝派发**（退出码 2），
不会警告后照跑。查当前版本：`opencode --version` 看第一位。

> 这条与 0001 是同一个教训的第二个面：**闸门不能靠调用方的自觉**，
> 得上调用方自己这一侧，失败时**显式停下**而不是降级放行。
